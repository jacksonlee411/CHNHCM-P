# CHNHCM-137 GitHub Actions使用与验证规范

登记信息：[registry.json](registry.json)。适用于本仓所有固定分支及后续扩展分支。
协作与发布授权遵循 005，证据登记遵循 014。CI 维护者按本规范执行正式门禁、分片和用量观察。首批发布及后续试点分别留有办理记录。[005 协作与授权](005-branches-and-documents.md) · [014 文档管理](014-document-management.md) · [首批发布](../verification/136-actions-publication.md) · [试点的用量与责任](#hosted-minutes-observation)

## 1 目的与生效边界

在保持正确性、授权、历史和提交恢复验证的前提下，尽量减少远程runner总用量。默认先消除重复触发和重复执行，再按真实影响选择测试，最后优化运行准备与分片。分支数量不是收费单位；同一交付的有效验证范围及总runner分钟是治理对象。

本规范形成项目约束。工作流实现及本地反例验证见[实施记录](../verification/136-actions-implementation.md)，首次远程发布、实际门禁及固定运行交接由[发布记录](../verification/136-actions-publication.md)持有。本轮按影响选择及限定结果复用的实现与验证见[后续记录](../verification/136-impact-selection.md)，远程生效仍以main实际工作流版本为准；包含本实现的PR须先满足三项正式门禁再合入。不得仅以文档或本地成功自行跳过未运行的必需检查。具体已实测场景与未实测边界分别登记，不把本地反例当作远程事件验收。

本规范不改变业务容量目标、固定环境更新责任、Git发布授权或原始失败记录。用户针对具体任务明确给定的范围和授权按该任务记录执行，例外不得默认为后续所有交付的规则。

## 2 术语与职责

| 名称 | 定义与责任 |
| --- | --- |
| 分支执行者 | 在固定工作树完成本地检查、稳定交付与影响说明，保护其他分支现场 |
| 集成维护者 | 核对最终PR head、base、实际受测合并引用、范围、必需检查和合并次序 |
| 验证维护者 | 维护源码到测试消费者的映射、清单完整性、失败原因与分片选择 |
| 全量 | 当前工作流合同规定的完整功能套件；默认未启用的容量等条件项另列，不宣称全产品验收 |
| 限定范围 | 依据本次完整差异及消费者选择的明确测试集合；不得称全量 |
| 明确不适用 | 分类已证明某类任务本轮不需要运行；不是实际测试成功 |
| 账单与估算 | 账单以GitHub账户为准；运行估算按每个实际分配job独立取整、包含所有attempt并去重job ID |

## 3 提交、同步与触发

**公共仓库自动运行按影响选中的远程浏览器检查。** 本地按相同范围预检。正式 PR 和 main 的全量候选包含 Chromium 前置和第 7 节规定的浏览器分片，限定候选按消费者选测。缺片、失败或取消阻止合并。等价成功结果按第 14 节核验复用。私有阶段默认本地验证，可按目标 SHA 显式启动远程检查。

1. 各分支继续并行开发。公共合同先协调负责分支和集成次序；消费者在需要该依赖或准备交付时同步main，不要求每次合并后全部分支立即同步。普通fetch、无开放PR的开发分支推送不额外要求Actions验证。
2. 准备PR交付前，完成实际受影响的本地检查、必要业务验证和生成物核对；聚合已知修复再推送稳定版本。紧急纠错可以立即推送，不能为了节流延迟必要修复。
3. 正式合并验证使用PR事件及对应的实际受测引用。`workflow_dispatch`用于明确诊断或授权的独立全量验证，不代替PR的必需检查；同一head已有足够范围的运行时，不并发手动重复启动。
4. 已被新head取代的同一PR运行可以取消，保留首失败及消耗。不同PR不得共用会相互取消的并发组。手动诊断不得取消正式PR验证；早期方案的零触发Actions只描述当批工作范围，不是永久禁用CI。
5. 草稿PR只执行轻量预检，不能形成可合并的完整验证结论；转为ready必须触发当前合并候选验证。转回draft取消旧的昂贵执行后，必需汇总不能保留旧成功作为放行依据。正式候选先完成quality，再启动所需 DB/API 和明确要求的远程浏览器任务；成功轮增加的等待时间须与节省的无效执行同时报告。
6. 自动分类不以任意PR标签为触发来源。普通标签变化不得重跑昂贵任务或取消正式运行；范围随真实差异重新计算。原`ci:geography-legal-entity`标签方案仅保留为历史，当前范围由完整差异决定。

上述自动触发实现必须显式覆盖`opened / synchronize / reopened / ready_for_review / converted_to_draft`，不能只跳过草稿却漏掉转ready事件。当前工作流已覆盖这些事件；实际远程验证范围见发布记录。

## 4 按影响选择验证

### 4.1 分类规则

分类依据完整PR差异与合并候选相对最新base的实际变化，不能只看最后一次提交。文件重命名同时检查旧路径、新路径；删除按原消费者处理。API分页未读完、文件数截断、merge-base不可确定、未知文件、依赖映射缺失或分类器异常，均不得降为较小范围。

| 分类 | 必需范围 | 判定边界 |
| --- | --- | --- |
| 纯说明与被动验证附件 | make docs；业务任务由汇总明确不适用 | 显式说明路径、资产/文档登记，以及没有被运行代码或测试读取的非可执行结果附件 |
| 前端单业务 | quality完整检查与该页面、引用消费者和必要共用页面 | 不因纯前端变化启动后端DB/API；未知前端消费者扩大浏览器范围 |
| 后端单业务 | quality、业务及正反向引用DB/API、相关页面 | 部门、企业、国家、区划、地点、法律实体的显式包及消费者映射；未分类/共用Go测试根始终纳入 |
| 多业务 | 各层受影响集合的去重并集 | 不以业务数量直接判定全量；不能只取一个标签或最后一次提交 |
| 测试与工具 | 对应执行层 | 单个浏览器spec保留前置依赖；Go集成文件可能含共用helper，运行完整DB/API；单元测试与文档工具仅完整quality |
| 共用前端、路由、前端依赖 | 完整浏览器及quality | 不自动扩大后端范围；根package.json等兼有运行/验证配置的文件仍按共用输入处理 |
| 全域核心、验证机制或未知运行输入 | 完整功能套件 | 共用Go领域内核、授权/事务/历史、全局存储/迁移、API合同、Go依赖、CI选择器/工作流、共用测试夹具及未准入路径 |

DB/API和浏览器独立选择，某层不适用不代表该层测试已执行。配置以[ci-scopes.json](../../.github/ci-scopes.json)为准，选择器逐项记录原因。新增模块先按其已知影响层扩大范围；完全未知运行输入回全量，后续补齐映射。删除和改名按旧、新消费者处理，不因文件不存在跳过。

被动验证附件只允许docs/verification/data下的JSON、JSONL、PNG、TXT、CSV和非可执行压缩日志；已有生产代码、集成/浏览器/容量测试或夹具引用的目录不得降为文档。可执行脚本、SQL、代码归档及被程序读取的资料保持运行输入身份，不把docs目录整体列入白名单。文档检查仍核对登记、引用与原证据。

### 4.2 范围清单与门禁

每轮选择必须记录head、base、实际checkout SHA/tree、工作流及选择器版本、分类理由、测试集合和分片。Go以实际编译发现的测试根为准，浏览器以实际Playwright列表为准；依赖项目、初始化测试、文件内顺序与原生缩放保持。非空套件出现空分片、重复、遗漏、未知测试或筛选零结果必须失败。页面验收的倍率和代表流程由 [012 第 6.2 节](../specs/m02/012-m02-functional-and-interaction-design.md#m02-ui-viewport-matrix)确定，已纳入本轮 CI 的用例按选择清单完整执行。

保持`quality / integration / browser`三项必需检查名称和main严格更新要求。汇总必须始终运行，检查分类成功、当前候选身份及全部计划任务结果。汇总分别标明私有仓库默认本地验证、本轮远程执行、第14节同一PR已覆盖、按完整差异不适用及第5节main等价复用；缺失分类输出、未预期跳过、失败、取消及未完成一律不放行。草稿PR不得利用不适用分支获得放行。

不能通过顶层`paths-ignore`、提交信息`skip ci`、`continue-on-error`、关闭保护或统一把skipped视为成功来节流。分类器、映射或工作流本身变化按全量验证；映射准入需包含真实清单、引用消费者及遗漏/扩大范围反例。

全量功能检查仍与专用容量、真实业务验收分开。范围缩小后的运行时间不能与全量直接比较并宣称等覆盖优化。

## 5 合并后检查与完整回归

### 5.1 同一合并候选的范围复用

复用紧接该次合并的正式PR验证，允许full、selected和docs，不建设跨分支历史测试缓存。合并后保留文档/Git上下文检查和三项门禁，必须确认：

1. 来源run属于本仓实际合入的最终head/base和正式PR合并引用，三项必需检查成功。最终候选计划执行的任务实际成功，按第14节沿用的任务也逐项核对原运行。
2. main父提交、实际代码树、工作流/选择器合同相同；用main代码重新计算完整差异的影响范围，逐项比对测试选择和分片。不能只相信产物中声称的范围。
3. 证据schema为当前版本，artifact属于当前attempt，完整读取实际job和最新attempt；最大有效期7天。失败、取消、缺失任务、伪造或不充分的范围都不能复用。
4. 两种事件下业务测试执行合同一致。main的quality仅重做文档/Git上下文检查，已经同树成功的编译、单元、生成及业务测试不重复执行。

证据无法取得、过期、base变化、树不等价或选择不同，回到完整功能验证；直接推main、squash/rebase等无法满足证据条件的场景不获得复用。首次发布这次选择器变更须先满足正式PR全量门禁。

### 5.2 全量的必要场景

全量用于全域共用核心/验证机制变化、无法可靠确定影响范围，以及缺少同树有效全量证据的重大集成/发布验收。普通业务PR按影响验证成功后，main不再无条件补一次全量；纯文档合并也不因事件变化扩大为业务全测。

若共用前端或依赖只影响一个执行层，只扩大该层。新增业务消费者、未知路径或信息不足必须在检查摘要中说明扩大原因。修复后的正式候选按完整PR差异重算验证责任，再按第14节核对可沿用的分片。

已有明确不稳定问题需要额外验证时，登记问题、范围和一次性目的；不对无变化代码每日重复全测，不新增仅为凑样本的定时Actions。main必需验证失败时记录责任并暂停新的集成；历史失败、容量目标和恢复责任继续由原记录持有。

## 6 失败与重跑

先保存原run、job、SHA、失败摘要及范围，再判断原因。明确的临时runner/网络故障、代码和验证合同未变、成功任务证据完整时，优先原run重跑失败job及其下游汇总，默认只追加一次；仍失败转诊断，不循环重跑至绿。业务断言、未知原因、时序不稳定、真实容量失败先诊断，不套用环境故障例外。

重跑不能变更SHA、选择范围、依赖或测试实现；有代码修复时产生新候选，按第4节确定范围，并按第14节逐片核实已有成功记录。跨attempt结果必须逐个核对计划job及依赖，标记“分批通过”，不得声称单轮全绿。普通测试内部`retries=0`保持。

同run同SHA、验证合同和完整覆盖可核对的失败job重跑，是本规范允许的补验；它取代旧指南中对所有部分重跑一概不接受的表述。具体任务若明确要求最终单轮全量通过，继续按该要求执行。失败、取消、未运行本身均不是通过。

## 7 分片、缓存与运行资源

完整套件使用 5 个 DB/API 分片、16 个浏览器分片。以每个托管 runner 从启动到完成不超过 15 分钟为目标，每片包含本地环境准备、运行及回收。按实际发现的 Go 测试根、Playwright 入口文件分配，先放耗时最长的项，每次放入当前累计时间最短的片。浏览器默认保留整文件。首次入职入口按实际发现的声明位置和用例数分为前后两段，同一声明的参数化用例整组执行，片内保持原顺序。新入口和新根按默认权重参与，实际清单仍须证明无遗漏、重复或空片。限定集合按所选工作的耗时估算片数，单片可提前完成。每周按第 8 节检视实测时间及输入权重。[本轮分片用量与取舍](../verification/136-hosted-minutes-pilot.md#shard-duration)

比较必须同时报告总runner分钟、完成等待时间、测试集合、条件跳过及失败；不能只报告墙钟加速。`max-parallel`只调整调度，减少分片才能减少重复准备和按job取整开销。片内workers=1、独立临时数据库与原断言保持；是否改变该边界另行验证。

缓存以锁定依赖和正确输入键为边界，不缓存测试成功结论，不恢复业务运行库替代初始化验证。当前Go已使用缓存；pnpm缓存、共享编译产物或预置镜像须先证明净收益。全量浏览器使用本轮前置或同一 PR 已核验成功的前置作业下载的 APT 包。缓存过期时按 runner 自己的索引安装；每片照常验证 Chromium 和原生缩放工具。

现阶段优先使用现有GitHub托管Linux。自托管runner是后续可选方案，需独立资源、任务隔离、临时数据回收及实际成本核验；不得占用4390等持久环境或125独占计时资源。短失败截图保持原保留规则，不为省存储删除首失败证据。

## 8 用量记录、验收与维护

每次CI策略交付及后续每周复核一次现有用量，优先使用只读查询，不新建定时Actions来统计Actions。记录运行窗口、仓库、事件、分支、范围、job、attempt、取消/失败原因、总分钟和等待时间。明确账单、估算、推演三种口径，分支开发量不同不能仅凭用量排名评价效率。

按同范围、同规模或明确归一化的每次有效交付成本比较，分别列出各个范围、样本构成、实际覆盖和失败重做。只有完成既定验证范围的交付才可计入节省额。观察 10 次自然交付或 7 天，以先到者收口。首轮 25%–33% 降幅仅有一次可比业务交付，整体结论为证据不足。后续 80% 试点按第 12.1 节另行计量。[首轮交付观察](../verification/136-actions-observation.md#6-窗口收口) · [试点窗口](#hosted-minutes-observation)

CI 策略变更时同步受影响的工作流说明、005、134、登记、检查清单和验证证据。生效前失败恢复为现行全量路径。生效后分类或复用失败须保留相应覆盖责任，按第 3 节分别派发集成和浏览器测试。汇总结果缺失则阻止合并。不得通过修改业务测试目标、隐藏失败或降低分支保护恢复绿灯。

## 9 外部依据与当前限制

2026-11-16核对以下官方资料，其作用是平台机制说明，本仓覆盖范围仍以本规范和具体任务为准：

- [GitHub必需检查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)：最新SHA/合并引用、手动事件限制、跳过与汇总。
- [GitHub重跑](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)：原SHA/ref及下游任务重跑。
- [GitHub计价](https://docs.github.com/en/billing/reference/actions-runner-pricing)：每job分钟独立取整；实际账单受套餐和共享额度影响。
- [Playwright CI](https://playwright.dev/docs/ci)：workers、分片及浏览器缓存的边界。

136 首批只能取得运行用量，实际扣费须从获权账单核对。分类、远程门禁、合并后复用和分片按各自受测构建查证。后续策略改到草稿触发、失败恢复或复用条件时，由集成维护者按第 3 至 6 节核对正式运行及原未覆盖的反例。[发布证据与限制](../verification/136-actions-publication.md) · [首轮观察结论](../verification/136-actions-observation.md#6-窗口收口)

## 13 减少正式候选的全量启动次数

**本地验证尽量并行，同范围使用与远程相同的分片数。** 先用 `make ci-preview` 确定当前候选各层的选测范围。独立检查可同时执行；有依赖的检查按工作流顺序执行。本地预检仍执行 `make ci-ready` 原定的生成核对、升级和浏览器前置。只有需要执行后续业务分片时，才按下表并行启动。分片数以当前选择器和工作流为准。

| 本地执行层 | 同范围的远程并行数 | 执行约定 |
| --- | --- | --- |
| DB/API 集成 | 不适用 0，限定 1–5，全量 5 | 同时运行选中分片，使用 `scripts/integration-shard.py` 的测试根、筛选式及分片编号。 |
| Chromium 浏览器 | 不适用 0，按耗时选片，全量 16 | 按 `scripts/ci_browser.py` 的入口清单同时运行选中分片，每片 1 个 worker。保留企业前置依赖、片内顺序和每例超时。 |

两层都需要验证时，公共前置通过后可同时派发两层分片。每个浏览器分片使用独立临时 profile、数据库、端口和结果目录，各集成分片使用各自的测试库。若本机容量不足或同时有验收环境需要保护，保留原分片编号和全部选中用例，分波执行并记录实际并行数、原因及各片结果。清单核对与实际执行结果分别记录。

开发和修复期间可在本地或草稿 PR 迭代。草稿的 quality 摘要按该 PR 的实际合并引用展示正式 PR 需要覆盖的分片数。实际派发按第14节扣除已有证据。独立可验收的页面改动可按消费者单独交付；需要一起生效的迁移、Go 实现、合同及消费者放在同一候选验证。草稿不能合并，转为正式 PR 时按当时的 base 和合并引用重新计算三项门禁。

| 本地入口 | 覆盖范围 |
| --- | --- |
| `make ci-preview` | 默认比较本地 `origin/main` 与当前工作树的完整差异，包括已提交、暂存、未暂存和非忽略的新文件。先确认本地基线已更新。`needs_base_sync=true` 表示基线已分叉，应同步后再核对。 |
| `make ci-preview CI_BASE=<基线> CI_HEAD=<候选>` | 按两个提交的共同祖先和候选文件树回放一组可独立交付的改动。输出两层分片、限定浏览器文件及原因。本地分组的结果只用于规划。 |
| `make ci-ready` | 文档候选运行文档检查。产品候选在临时副本中执行实际 `make generate` 并比较结果。本地浏览器前置从临时 profile 的固定前端构建运行。全量候选随后执行两个真实 DB 升级测试根、六个 Chromium 回归及企业依赖；限定候选先核对 Playwright 实际分片清单，再从六个回归中执行所选入口文件对应的用例。 |
| `python3 scripts/ci_usage.py` | 按 PR 的全部运行和 attempt 对账。该版本两组的具体分片都已展开且至少一片实际分配 runner 时计一次；提前拦截、只重跑失败分片、main 复用分别保留原用量。另计最终通过的 PR run 创建前已经启动的次数。 |

`current` 是现行范围。`shadow` 仅用于并排试算，首批只识别职务列表或详情 GET 的成功响应说明及其精确匹配的生成客户端注释，以及在下一号迁移中单独为职务读取表创建普通索引、Down 删除同一索引的情形。迁移试算仍保留全部 DB/API 分片，含旧库升级、失败回滚及相关 API 根。共享授权、历史写入、跨域 DDL、未登记的依赖及 CI 合同继续保留完整范围。启用任何缩减前，按已知失败检查选中范围，再用真实同类候选验证。[历史回放和启用决定](../verification/136-hosted-minutes-pilot.md#5-正式候选全量启动频次)

每次本地预检打印本轮 `result.json` 的路径。核对其中的比较基线、工作树 HEAD、Git 文件树及未提交标志。待推提交可用 `git rev-parse 'HEAD^{tree}'` 比较内容，基线和实际范围也须对应。无差异记为 `no_candidate`；运行中的记录只证明已开始。运行期间应保持工作树稳定；前后文件树核对可以发现收尾时仍存在的变化，候选变化时以新候选复验。限定浏览器清单与实际 DB/API、浏览器用例结果分别登记，跳过及未启动用例单列。每次执行的结果、阶段耗时、用例状态和遮罩截图在独立目录中查回。同候选的前次失败与复验可按文件树和基线关联。直接执行 `make ci-preflight` 可对当前内容复验指定的全量前置用例。见[本地预检计划](../archive/plans/141-local-preflight.md)。

## 14 同一 PR 的后续全量候选

正式 PR 的完整差异决定验证责任。首次全量候选默认执行旧库升级及第 7 节的完整 DB/API 分片。浏览器按第 3 节在本地验证。后续全量候选核对同一 PR 最近七天的实际作业，默认仅派发仍需执行的原编号分片。quality 摘要列出本轮数量、前置安排和沿用的来源运行。开发者可在本地用 `make ci-preview` 查看完整责任范围，实际派发数量在正式 PR 上确定。

| 候选变化 | 本轮执行 |
| --- | --- |
| 有成功 quality 后只追加说明、被动附件或相同内容 | 当前候选运行 `make docs`。按原始 quality 的合并树核对后可复用生成、构建及清单。上一轮仍欠的业务作业继续执行。 |
| 页面、业务包、测试或旅程辅助文件变动 | 重新发现真实清单。运行与本轮变化的测试入口或 Go 根有交集的分片，以及清单改变、上次失败或缺少成功记录的分片。前置的两层用例一起核对。 |
| 同步较新的 main、处理冲突 | 直接比较两次实际合并树，覆盖从 main 带入的内容和冲突解决。验证机制或共用运行输入改变时重新核对两层范围，按第 3 节派发。 |
| 明确要求正式候选运行远程浏览器 | 将仓库变量 `CI_FULL_BROWSER_HEAD` 设为目标 PR head 或 main 的完整 SHA，在对应候选重新运行完整工作流，结束后清除。按该候选的影响范围选择浏览器用例，DB/API 仍按影响核验。私有仓库的其他提交默认本地执行浏览器。仅执行旧库升级的前置记录只能证明数据库检查。 |
| 手动诊断 | 必须选择范围。只需全量浏览器时经授权选 `browser-full`，集成分片为零；`full` 用于明确要求两层全量的独立诊断。 |
| 指定一次单轮全量验收 | 用户明确要求一次完整远程验收后，对完整范围的 PR，可把仓库变量 `CI_FULL_PR_HEAD` 设为目标 head 的完整 SHA。下一次该 head 的正式运行会执行全部任务。其他 head 继续自动选测。 |

quality 在业务分片开始前留存两层清单。Go 按包和测试根识别用例，浏览器按项目、定义文件、测试 ID 和入口文件识别，企业前置依赖计入所在片。各片只采用同仓、同 PR、同验证合同、实际获配 runner 且成功的原作业。失败或取消的运行中已经成功的其他分片也可采用。较新的失败压过旧成功，缺失的证据由本轮执行补齐。合并门禁核对当前 head/base、实际作业、同一分片的最新 attempt 和引用的原件。记录按“本轮执行”和“之前已验证”分别计数。

两类汇总与 main 均可核验这些记录。合并后，最终 PR 的全部责任已覆盖且合并树等价时，main 继续轻核验。历史回放、未覆盖的偶发失败及观察边界见[136 验证记录](../verification/136-hosted-minutes-pilot.md#6-同一-pr-的后续全量候选)。
