# CHNHCM-014 文档管理规范

登记信息：[registry.json](registry.json)。适用范围：本仓编写、采用、维护和保存的文档。编号与分支规则由 [005](005-branches-and-documents.md) 持有；本规范不批准业务切片范围，也不改变 [003](../adr/003-implementation-stages.md) 的验收口径。

## 1 目的与责任

文档必须让读者区分当前约定、拟议方案、实际实现和历史证据。每条长期规则应有明确的维护位置；其他材料引用该位置，避免各自维护同一规则。

`owner_branch` 表示文档号段归属，不代表长期独占某个领域。`owner_role` 对内容维护负责，`owner` 记录已明确的具体责任人；尚未指派时保留 `null`，不得虚构人员。跨域变更需要受影响合同的维护者参与评审。审阅者应明确身份及审阅范围，工具或代理复核不能冒充人工批准。

正文使用“必须/不得”表达强制约束，“应”表达默认要求，“可”表达允许的选择。偏离默认要求时记录理由、影响和处理决定；不得用例外取消更高层协作约束。

## 2 分类、目录与权威归属

| 类型 `type` | 目录 | 维护内容 |
| --- | --- | --- |
| `governance` | `docs/governance/` | 协作、文档管理、评审及完成口径 |
| `decision` | `docs/adr/` | 单项重要决策、理由、备选方案与后果 |
| `architecture` | `docs/architecture/` | 系统与领域边界、依赖方向、跨域合同和目标模型 |
| `preservation` | `docs/assets/` | 三类资产的保留与重新验证规则 |
| `plan` | `docs/plans/` | 交付范围、任务、依赖、里程碑与执行进度 |
| `business_spec` | `docs/specs/<module>/` | 业务需求、规则、正常及异常场景 |
| `functional_spec` | `docs/specs/<module>/` | 菜单、页面、字段、交互和输出合同 |
| `technical_design` | `docs/specs/<module>/` | 切片领域、存储、接口、事务及测试设计 |
| `guide` | `docs/guides/` | 已有能力的用户、开发或运维操作步骤 |

验证记录放在 `docs/verification/`，由登记表的 `governance.verification_records` 单独登记。来源原件、基线、许可和外部依据放在 `docs/reference/`；资产实例及采用状态由 `docs/assets/inventory.json` 持有。模板放在 `docs/templates/`；已满足第 8.2 节条件的编号文档必须物理移入 `docs/archive/`，完整沿用原来在 `docs/` 下的目录和文件名。

已登记的定稿报告可以引用后来移除的源码。检查须确认源码存在于报告的完整 Git 基线。若报告针对有未提交改动的工作区编写，也可核对当时一同保存报告原文与源码的提交。迁址时依第 8.2 节更新报告中的本仓文档链接。仅存于旧快照的源码，可在核对原件后将链接固定到该提交中的原路径。现行合同和资料链接须可达，原报告的结论、受测基线及原件摘要保留。

目录按内容实际需要创建，不提前建立全部模块或空白规格。`docs/index.md` 是统一入口，按当前规则、当前交付、验证记录、来源与历史提供导航；局部 README 只提供路由和范围说明，不另行持有业务规则。

M02 的 010 按计划分类，011—013 按模块规格分类，各自的当前文件位置由登记表给出；正文及编写进展见[规格入口](../specs/README.md)。跨模块共用的长期技术约束由 `architecture/` 持有，切片技术设计引用它。

### 2.1 当前设计与来源原件

`architecture/target` 是本仓采用且可继续演进的目标设计；`reference/sources` 才是不可覆盖的来源包。本仓设计变更必须通过决策或规格说明影响，并维护本地修订链，不能回写来源原件。

ADR 解释为什么作出选择，架构或规格维护受该选择影响的当前合同。实施计划引用这些合同，验证记录引用验收条件，指南说明已实现行为。不采用“后写的文档自动覆盖前文”的规则；有冲突时必须明确修改哪项合同及其适用范围。

## 3 编号与登记合同

先在 [registry.json](registry.json) 领取编号再创建正文。文件名采用 `NNN-english-kebab-case.md`，不添加“最终版”“最新版”或 `v2-final` 等后缀。跨分支维护、改名、迁移及归档保留原 ID，已用 ID 不回收。

导航、机器索引、导入基线、源图、模板及附属验证记录不另占实施文档号。附属验证记录必须明确关联文档和验证范围，不能借用该豁免编写未登记的新决策或规格。

### 3.1 编号文档元数据

登记表 `schema_version` 为 2。以下字段均须存在；允许空值的字段必须显式写 `null` 或空数组。

| 字段 | 约定 |
| --- | --- |
| `id / title / path` | 唯一文档号、与正文一致的标题、唯一仓内相对路径 |
| `type / modules / scope` | 表中类型、M01—M20/X01—X06 模块数组（全仓规则可为空）、非空适用范围 |
| `owner_branch / owner_role / owner` | 号段分支、维护角色、具体责任人或 `null` |
| `status` | 第 6 节的文档生命周期状态 |
| `format` | 编号文档统一为 `numbered`，包括 001—009；不允许 `legacy` |
| `review` | 未审定为 `null`；否则记录 `date / reviewer / scope / result / evidence`，结果为 `accepted` 或 `changes_requested`，证据为仓内文件路径 |
| `execution_status` | 仅计划使用 `not_started / in_progress / completed / cancelled`；其他类型为 `null` |
| `superseded_by` | 替代文档 ID 数组；不得引用自身或形成循环，目标须符合第 6 节的生效条件 |
| `closure` | 文档关闭，或计划执行 completed/cancelled 时记录 `date / reason`；其他情况为 `null` |
| `archive` | 归档时记录 `date / reason / previous_path`，previous_path 记录归档前的完整路径，日期只作元数据。另见第 8.2 节 |
| `archive_deferral`（仅实质交接未完成时） | 记下 `kind`（`rules_pending` 或 `handoff_pending`）、具体 `reason`、`owner_role` 及 `recheck` 触发条件。完成交接时移除此项并登记物理归档 |

登记表持有上述元数据，正文只链接登记并解释范围和限制，不手写第二份生命周期表。需要展示状态时从登记表读取或生成。文件标题重复 ID 和 title 是阅读需要，由检查器校验一致性。

### 3.2 验证记录元数据

`verification_records` 每项记录 `path / related_documents / format / status / date / base_commit / working_tree / change_description / environment / scope / results / limitations`。路径唯一，关联文档必须存在；`status` 为 `draft` 或 `final`。

`base_commit` 为实际受测基线的完整提交号；`working_tree` 为 `clean` 或 `dirty`，后者必须描述基线外变更，宜保存受测输入摘要。不能用报告自己的最终提交号代替受测对象。`results` 每项包含 `check / result / evidence`，结果只能为 `passed / failed / interrupted / not_run`；证据引用仓内实际文件。`limitations` 保留未覆盖范围及限制。

`final` 表示记录已定稿，不表示全部检查通过。历史报告缺失的受测信息必须保留未知，不补造；本次迁移的两个旧报告允许 `historical-unspecified`，其中建仓报告的 `base_commit` 为 `null`。该例外不适用于新报告。

## 4 内容格式与编号

### 4.1 标题与自然段

编号文档只有一个一级标题：`# CHNHCM-NNN 标题`。二级标题使用 `## 1 标题`，三级使用 `### 1.1 标题`，四级使用 `#### 1.1.1 标题`；同级从 1 连续递增，子级属于当前父级，不跳级。正文内容最多三级编号，不使用五级及以下标题；过深的内容拆成章节、表格或独立文档。

普通自然段不编号。有先后顺序的步骤使用有序列表，并列条件使用无序列表；列表编号不参与章节编号。不混用“一、”“（一）”等其他章节体系。代码块中的示例标题不参与正文结构检查。

导入资料及生成物保留来源或生成格式；原验证报告的保存边界见第 10 节，不构成编号文档的格式豁免。Markdown 使用 UTF-8，表格和列表前留空行，代码块标注语言；文档内使用相对路径，避免本机绝对路径成为阅读或构建依赖。

### 4.2 稳定规则、场景和验收 ID

章节号仅用于阅读定位；需要追踪的业务规则、场景和验收条件分别使用 `M02-BR-001`、`M02-SCN-001`、`M02-AC-001` 这类模块内稳定 ID，不占用文档号段。模块范围为 M01—M20、X01—X06，每类序号为 001—999，不使用 000。标识删除后不得复用，章节调整不改变标识。

定义处使用小写显式锚点，如 `<a id="m02-br-001"></a>`。跨文档引用链接该锚点，避免仅写“见第 4.2 节”。当前定义必须跨文件唯一，草稿中的定义也占用该 ID；其他文档引用定义位置，模板示例不构成真实定义。

已登记且归档信息有效，或者状态为 superseded/retired/cancelled 的正文，按历史记录保留原 ID、标题及锚点，不参与当前定义的跨文件唯一性检查；其文档身份仍须合法，文件内同一锚点仍不得重复。不能只把文件放入 archive 目录就获得历史身份。有效规则提取后，在归档交接说明中链接现行定义；已废止的规则注明关闭原因，不伪造现行继任者。

标题中以 Markdown 链接表示的规则 ID 是引用，不需要再次设置本地定义锚点。行内链接和引用式链接的目标必须为仓内同一 ID 的显式锚点，检查目标文件及锚点真实存在；指向另一个 ID、无锚点或失效目标均拒绝。标题中未链接的规则 ID 仍按定义检查，必须有本地锚点；引用和定义同时出现时分别检查。

| 场景 ID | 业务规则 | 功能规格位置 | 技术合同 | 验收条件 | 验证记录 |
| --- | --- | --- | --- | --- | --- |
| 实际场景标识 | 链接规则定义 | 链接对应页面合同 | 链接实现约束 | 链接可核对结果 | 链接实际报告，未运行时明确说明 |

### 4.3 表述与引用

区分已观察事实、正式约定、拟议方案和待决事项。“支持历史查询”等表述必须落实为输入、权限、日期语义和预期结果。待决项写明问题、影响、负责人角色及处理节点，不以技术占位掩盖未决业务问题。

政策依据需记录发布方、标题、链接、地区、有效期间、核对日期与适用解释；版本型外部资料记录版本或来源提交。链接可访问不等于适用当前业务。普通版本由 Git 保存，涉及范围、合同或结论的变化应在对应决策、计划或验证记录中说明。

## 5 各类正文的最小内容

模板入口见 [templates/README.md](../templates/README.md)。模板只帮助组织内容，不能用未替换的占位项宣称规格已完成。不适用的章节注明理由，避免保留无意义空节。

| 类型 | 推荐章节顺序 |
| --- | --- |
| 治理/资产规范 | 目的与范围 → 术语与职责 → 规则 → 执行流程 → 例外处理 → 检查与维护 |
| 决策记录 | 背景问题 → 决策 → 备选及取舍 → 影响代价 → 适用与替代关系 |
| 架构设计 | 目标范围 → 上下文与事实归属 → 依赖与合同 → 关键约束 → 演进与验证 |
| 实施计划 | 目标 → 范围与暂缓 → 交付物 → 阶段任务 → 依赖责任 → 验收关闭 → 进度 |
| 业务需求 | 目标 → 角色前置 → 正常流程 → 异常/撤销/更正 → 规则 → 历史权限 → 验收 |
| 功能规格 | 场景映射 → 菜单页面 → 列表/详情/表单 → 字段 → 状态操作 → 提示异常 → 验收 |
| 技术设计 | 上游需求 → 模块边界 → 领域与数据 → API/事件 → 事务并发 → 权限审计 → 测试运行 |
| 验证报告 | 对象与基线 → 环境前置 → 场景步骤 → 预期与实际 → 证据 → 未覆盖项与结论 |
| 操作指南 | 适用对象 → 前置 → 操作步骤 → 成功判据 → 常见失败及恢复 |

业务场景至少包含角色、正常菜单入口、前置、动作、业务事实结果、页面反馈、失败保护及历史影响。功能字段表说明含义、输入方式、必填条件、默认来源、服务端约束与错误反馈；前端辅助校验不能成为另一套权威规则。

## 6 生命周期与完成口径

| 文档状态 | 判定条件与转换 | 负责角色及可核对的证据 |
| --- | --- | --- |
| `planned` | 按 005 预留编号及路径，正文尚未形成 | 编号维护者登记用途、路径与维护角色 |
| `draft` | 预留后形成可编辑正文，或在审稿收到修改结论而退回 | 作者登记正文与待决项。退回时关联审阅意见和受评版本 |
| `in_review` | 草稿已说明范围、影响和待决项，提交审阅 | 作者标明送审版本和审阅范围，审阅者可据此复查 |
| `active` | 实际审阅接受所提交的范围，整份文档据此采纳 | 维护者登记审阅者、范围、日期、接受结论和证据。单项采用只能证明相应条款的效力 |
| `superseded` | 原文整份有效内容由已采纳的后继承接 | 原文和后继维护者核对替代范围，登记后继编号、关闭原因及历史入口 |
| `retired` | 原规则已废止，核实没有继续适用的内容 | 维护者登记废止决定、适用范围和关闭原因 |
| `cancelled` | 预留、提案或文档工作已取消，保留编号。未形成的正文可继续不存在 | 维护者登记取消决定及原因，已有原稿和审阅结论按原记录留存 |

通常按 `planned → draft → in_review → active` 推进；评审要求修改时回到草稿。重要决策反转新增 ADR，并更新替代关系；同一规格的持续维护可保留编号。当前有效文档的小修订可以保持 active，但实质合同变更必须重新记录审阅范围和结论；需并行探索的方案用新草稿，不让未批准内容静默覆盖当前合同。

已采纳文档仅部分被替代时保留 `active`，注明剩余适用范围与替代位置。草稿或在审文档只有个别条款获独立采纳时保留原文稿状态，按[单项交接规则](#82-归档)记录。整份有效内容已有后继才使用 `superseded`。被替代、废止或取消的正文不得作为新的有效依据，引用时必须标明历史用途。

替代目标必须已有正文，且状态为 active、superseded 或 retired；后两者只用于保留曾生效、后来又被替代或废止的历史路线，不能当作当前有效规则。planned、draft、in_review 或 cancelled 的文档不能承接已经宣布完成的替代，避免原合同关闭后只剩一个未成形的提案。

计划执行状态、文档状态、资产采用状态、验证结果分别维护。计划 completed 不能推导规格失效或业务验收通过；文档 active 不能推导实现完成；验证 final 不能推导全部 passed。阶段门槛继续由 003 持有。

## 7 来源、生成物与证据保存

来源包、逐文件来源摘要和初始采用摘要不可覆盖；本仓后续修订由 [local-revisions.json](../reference/local-revisions.json) 衔接。来源体验/业务/验证资产继续分别登记，不把来源测试通过当成本仓验收。

修订链的 `id` 关联已登记文档，`revision` 为该文档的连续正整数修订序号；历史条目未填写时按 1 解释，不回写旧记录。同一文档后续修订依次追加 2、3 等序号，保留各次验证入口；每个文件的 `before_sha256` 必须衔接整条链中该文件最近一次的摘要。重复、跳号及断链均拒绝，文档号不因普通持续修订而重新分配。

目标模块数据的生成链是 `data/*-modules.json → modules/*.md / diagrams/*.mmd`，对应 SVG 由渲染器生成；具体脚本来源见 [document-tooling.json](../reference/document-tooling.json)。只修改编辑源并重新生成受影响产物，不手工制造第二份生成事实。

`build_modules.py --check` 检查其负责的 57 份文本产物是否同步；并不验证全部架构文字、SVG 图面或领域语义。渲染 `--dry-run` 只列出范围，不构成图形通过。SVG 变更还需保存工具版本、源/产物摘要和实际图面检查记录。本次文档治理不重新渲染目标图。

验证记录定稿后保留原结果。补验新增记录；勘误标明原结论、更正原因和影响，不用新结果覆盖历史失败。原始临时输出可存 `.local/`，持久结论及必要复核依据必须在仓内有可追溯位置，不能只链接可能被清理的临时文件。

## 8 维护、评审与归档流程

### 8.1 新建及修订

1. 确定文档类型、维护范围和上游合同，检查是否已有对应权威文档。
2. 新建时先登记编号，创建正文时把 planned 改为 draft；复制适用模板并替换占位内容。
3. 补齐影响、场景、验收和待决项，涉及共享合同的变更列出受影响方。
4. 评审记录范围、问题和结论；按实际结果更新登记，不能将检查脚本通过替代语义批准。
5. 同步入口、引用、追踪表及生成产物，运行受影响的检查，保存实际结果。

修订者列出本次要改的条款、适用角色与对象、现行引用方、业务差异及正常和异常样本。共享条款变更时，同时按原措辞检索仍将旧条件写在正文的现行规格。开发者关联实际实现、共用组件及消费者。评审者从相同条款独立写出预期，在同一候选上登记实际结果、首败、复验及限制。页面改动还需列出同构建参考页和返回、滚动、键盘及缩放的适用路径。[功能规格模板](../templates/functional-design.md) · [验证报告模板](../templates/verification.md)

### 8.2 归档

**应归尽归。** 已形成正文的计划在执行 `completed` 或 `cancelled` 时，已整体替代、废止或取消的其他编号文档在登记相应状态时，必须评估并办理物理归档。有效条款已有获采纳的承接位置、未结工作已明确接收方后，必须在同一变更中移动正文、更新登记和引用。原编号、标题、文件名、稳定 ID、历史章节锚点和原执行关闭依据均保留。在办计划和仍负责现行规则的长期规范按原职责维护。未形成正文即取消的预留项保留编号和取消原因，`archive` 留空。

**目录采用固定映射。** 把原路径开头的 `docs/` 换成 `docs/archive/`，其余路径逐段保留。例如 `docs/plans/511-project-standards.md` 移至 `docs/archive/plans/511-project-standards.md`，模块规格 `docs/specs/m02/<文件名>` 对应 `docs/archive/specs/m02/<文件名>`。归档日期只记入 `archive.date`，目录中不设年份层。正文只保留在归档路径。`path` 指向新位置，`archive.previous_path` 记首次归档前的原路径，整理已有归档目录时沿用原归档日期和原路径。

**每份拟归档文档须先提炼规则和标准。** 原文维护者检查正文、表格、示例和验收条件。接收方维护者按下表核对，在归档交接中逐项记录去向。确无长期条款时，记录检查范围和理由。

| 核对内容 | 交接说明须能回答的问题 |
| --- | --- |
| 每条业务、体验、技术、评审或治理规则 | 原文位置或稳定 ID、原决定与采纳依据、适用对象和触发条件、可观察结果是什么？现行合同的哪一条承接？部分适用、替代或废止各依据哪项决定？ |
| 文档状态规则 | 哪类文档在什么条件下由何角色判定或从何状态转入何状态？依据哪份审阅、登记或验收证据？项目内通用的状态规则在本规范维护。文档采纳、计划执行及关闭原因、实际验收和文件归档分别查证。 |
| 历史和未结事项 | 从定稿报告更新后的链接、历史章节或稳定 ID 能否找到所评原义及当时结论？每个未结事项由谁在何条件下复查？ |

部分承接时，原已采纳文档保留 `active` 及剩余范围。原为 `draft` 或 `in_review` 的，按单项独立采纳依据交接，保留文稿状态、整份审阅及原执行关闭原因，已否决的提议保留原结论。后继草稿先引用原定义，承接生效时同批切换唯一现行定义和现行调用方。仍有效的规则缺少已采纳的承接条款、效力有待裁定，或未结工作尚未交给接收方时，逐份登记暂缓的条款或任务、责任角色与复查条件。交接完成即移入归档目录。仍待执行的容量测试或产品事项已移交后，其实际结果继续由接收方跟踪。

**历史追溯通过更新引用路径实现。** 整份规则被替代时登记 `superseded` 及后继，按上述条件移动原文。定稿报告引用旧路径、链接数量较多、存在受评稿或需要保留原始结论，均不得成为原位保存或暂缓归档的理由。一起更新索引、现行合同、计划、定稿报告、资产和生成目录中指向当前仓库文件的链接，保留各自的原章节和具体片段。同批文件相对位置不变且仍可正确解析的链接，保留其原写法。历史报告仅调整链接目的地，保留标题、受评版本、判断和实测值。固定提交中的原文件路径、来源摘要及受评快照继续定位那个版本，不改写原件。迁移后须从现行入口和历史引用分别核验目标与原义，再运行文档检查。[稳定标识](#42-稳定规则场景和验收-id) · [计划模板](../templates/plan.md)

[现行规范目录](catalog/standards/README.md)和文档正文的默认检索范围采用同一口径，仅收录登记为 `active`、尚未归档的非计划编号文档。目录中的条款名称及链接取自问题导航和模块导航。查计划、待审文稿或历次验收时，从[文档分类目录](catalog/README.md)进入。登记、导航或报告标题变动后运行 `python3 -B scripts/document_catalog.py` 重新生成目录和检索范围，`make docs` 核对其一致性。

## 9 检查及其边界

`make docs` 使用 Python 标准库运行资料检查和治理检查器的回归用例，保持本仓自足。检查覆盖登记必填项及枚举、编号与路径、标题、类型目录、反向登记、根 Markdown、入口可达性、数字标题、稳定条目标识、替代与归档关系、验证记录结构，以及已有来源摘要与生成一致性。

状态合法性及当前字段组合可以自动校验；检查器不读取完整 Git 历史来证明所有状态转换经过批准，也不证明旧编号从未被删除后复用，这些须在变更评审中检查。链接检查以仓内文件及受控显式锚点为边界，未承诺完整 CommonMark、全部自动标题锚点或外链验证。

机器检查不能决定需求是否真实、政策是否适用、业务例外是否充分、验收证据是否足够或归档前规则是否提取完整。文档变更按实际影响验证，不因为目录存在或检查通过宣称业务完成。
