## 3 同一业务事务内的当前权限

1. **按份判断。** 复用 X03 的 `Guard`、`Decide`、`DecideReads` 和 `ReadPlan`。Go 对每份授予同时检查主体、动作、目标、字段、用途、有效期和绑定版本状态，按对象合并完整读许可。每个写动作须由一份完整授予覆盖该目标所需字段。强制限制或显式拒绝优先，必要来源无法确认时拒绝。[公开端口](../../internal/contexts/access/public/contracts.go) · [完整授予](../specs/x03/028-local-account-and-authorization.md#x03-br-004)
2. **排定授权变动与业务提交的先后。** 在原连接上依次锁定涉及的主体、实际引用的角色及策略版本，再取已有业务锁，同类身份按稳定键排序。业务办理对授权依据持共享锁，逐份撤权和共享版本停用分别对相应主体或版本持排他锁，直至提交。授予、换版及管理命令也锁定操作者的委派依据和拟引用版本。停用共享版本时，若操作者的管理范围有限，在该锁下检查是否有超出其范围的有效或待生效授予。已撤销或到期的历史授予可直接略过。[现有守卫与事务顺序](../specs/m02/013-m02-technical-design.md#612-守卫粒度与事务顺序)
3. **在写入前判断有效期。** 取齐所需锁后，按权威来源的当前归属、当前授权状态和服务端当前时刻作最终判断，紧接受保护写入。等待中依赖集合发生变化时，按现有事务规则重算或重试。业务日期只用于选择业务事实。自然到期由读取或提交当时的判断生效，共享版本停用由当前版本状态生效。[生效与收回](../specs/x03/028-local-account-and-authorization.md#x03-br-005)
4. **让各入口使用当前许可。** 核对 `Grants()`、`PolicyVersion()` 的调用方，把部门入口和候选等直接遍历旧授权的路径接到 X03。列表、树、候选先按当前获权对象及字段裁剪，再筛选、计数和返回。历史、提交结果查回和核编小计遵循同一授权语义。其他已交付对象按共用守卫的实际影响选回归。[部门读计划](../../internal/contexts/access/infra/postgres/read_plan.go) · [核编入口](../specs/m03/313-position-capacity-contract.md#5-正常入口与应用合同)

部门全选固定点击时获权的对象身份。后来新增的匹配对象不加入，无关授权变更或撤去一份仍有同权来源的授予无需重选。翻页与下载按当前权执行，CSV 对固定成员逐个核对必要读权和独立导出权、按字段裁剪。任何成员缺少必要许可，整笔拒绝且零文件。沿用既有草稿有效期、会话和业务日边界。此处无需另算全员策略版本或整批资料摘要。[118 固定身份选择](../specs/m02/118-department-business-requirements.md#m02-br-033) · [132 选择与导出决定](../adr/132-query-and-validation-boundary.md#7-第一批主线具体决定)

## 4 存量迁移与重启

1. **按实际存量迁入。** 由统一 upgrader 执行前向迁移，实施时按主线领取 goose 序号。覆盖所有存量动作。按实际授权迁入主体、动作、范围种类及目标、读写字段和原有效期。语义完全相同的不可变定义可共用，授予身份仍各自独立。沿用既有授予 ID 或保留稳定映射，来源记为「存量迁入」，未知授予人和时间留空。空权限、已撤默认动作及依赖岗位目录的条件原样保留。管理归属缺乏依据的账号由实例负责人处理。[既有约束](../../db/migrations/00001_access.sql) · [315 目录范围](../../db/migrations/lineage315/quota_grants.sql)
2. **同次切换读写与初始化。** 取消动作／范围的旧唯一限制，按授予身份及提交幂等约束写入。日常开放目录只含本批可委派动作，办理时保留账号的其他既有授权。已完成的引导在重启时只读取其结果。检查 `initialize`、`access-change`、`local-password` 和各域的补权入口，需要保留的运维命令复用 X03 写端口。开发样本仅在显式创建的可丢弃实例生成。[upgrader](../../cmd/upgrader/main.go) · [实际启动链](../../scripts/local-bu.py)
3. **在自有隔离库对账。** 用包含已撤默认权、空权限、部分字段、停用账号及两类岗位范围的旧库升级。按主体、动作、范围种类及目标、读写字段和原有效条件双向比较全部实际权限，检查漏迁、扩权和重复授予。报告给出是否一致，有差异时仅列定位所需的标识和原因。迁移沿用凭据与会话的既有状态和失效规则，业务原件及回执由原业务域保存。选一笔升级前的业务提交，由仍有权的原办理人用原提交身份查回，核对操作者和来源。[025 保留义务](../adr/025-greenfield-implementation-policy.md) · [128 持久化边界](../adr/128-authorization-evidence-removal.md)
4. **验证撤权能跨重启保持。** 选隔离旧库中确由启动脚本初始化的只读账号，在管理页面撤尽其部门读权的所有来源。用该账号验证已失权，重走包含初始化的实际启动流程，再登录复查。该结果可直接用于 028 第三组走查。空库引导、升级失败回滚和重试复用现有迁移检查。权限对账有差异须先修复再开放管理写入。切换后已有新业务写入时采用前向修复。[升级验收](../specs/x03/028-local-account-and-authorization.md#x03-ac-007)

## 6 验收与关闭

| 要回答的问题 | 在能观察该行为的层级验证 |
| --- | --- |
| 一份授权能做什么，哪些组合要拒绝？ | 用 Go 表驱动用例验证委派上限、完整授权、字段不可跨授予拼接、拒绝优先、时刻边界。用对应入口的允许、拒绝用例检查可授予项有消费者、独立受保护分支确实判权。同一共用规则可由一组用例覆盖。[028 业务条目](../specs/x03/028-local-account-and-authorization.md#5-验收条目) |
| 保存和撤权相遇时，谁先发生？ | 用两个真实 PostgreSQL 连接控制相冲突的守卫，验证业务先提交能保留、撤权先提交则无业务写入。对主体撤权、共享版本停用和等待中到期覆盖各自不同的生效路径。另由真实 API 检查旧会话失效、管理越界、结果未知重试及原子失败。[并发验收](../specs/x03/028-local-account-and-authorization.md#x03-ac-005) |
| 客户在正常菜单看到什么？ | 用 028 的[跨 BU](../specs/x03/028-local-account-and-authorization.md#x03-scn-001)、[单岗及重叠授予](../specs/x03/028-local-account-and-authorization.md#x03-scn-002)、[共享版本及重启](../specs/x03/028-local-account-and-authorization.md#x03-scn-003)三组样例，查看页面及相应响应、实际 CSV 和核编小计。页面走查覆盖各自独立的显示、提交与拒绝路径。共用布局和操作复用代表流程的视口结果，按 [012](../specs/m02/012-m02-functional-and-interaction-design.md#m02-ui-viewport-matrix)检查五种 100% 视口、关键流程原生 200%，满足触发条件再做 400% |
| 升级是否改变了权限或使已撤权限复生？ | 直接引用第 4 节的全量权限对账、原回执查回及一次真实重启结果。成功的普通读取沿用 128 的零逐次授权审计写入回归 |
| 授权查询或锁是否拖慢业务？ | 对受本次变更影响的高频查询和保存，用相同业务输入比较前后表现，已有容量目标的路径按原专项分组复测。低频开户、授予、撤销先验证操作结果。若发现慢查询、锁竞争或客户已有时延要求，再测相应路径。原组织容量专项继续按 [125](125-r6-capacity-remediation.md) 跟踪 |

一份切片验证记录可同时引用自动化结果和正常菜单走查，覆盖多个验收条目。按 014 记录基线、范围、结果、首错、复验及未覆盖项。仅在结果需定位或已有规范明确要求时附相关输出、截图或文件。无需逐阶段重交相同结果，也无需另存会话状态、业务原件或成功读取的判权轨迹。[014 文档治理](../governance/014-document-management.md) · [128 安全事实](../adr/128-authorization-evidence-removal.md)
