## 3 业务量、时延与重启

按 I2 已登记的实施假设，通过正式 Go HTTP 命令建立 20 个职级、40 份人民币月标及年标、12 份计划。每计划含 5 个职级、3 项组成，两类对象各留存 2022 至 2027 年六个生效段，合计 240 条薪标段及 72 条计划段。四个独立 `admin` 会话各有自己的更正对象，另有四个独立 `reader` 会话同时查询。每次计时从发 HTTP 到解码响应结束，同时核对所选段、原修订、申请号、权限、数值和金额解释。冷启动、造数和重启查回单列。客户上线容量可随实际制度另定。[可复跑的容量用例](../../internal/bootstrap/compensation_capacity_integration_test.go)

## 4 评审与交接

首轮从正常办理逐条对照 211、212。发现重复建标会说明冲突，但管理员只能自行返回列表查找。补上从同一错误打开已有标准的入口，按职级身份、币种及约定频率定位，仍由后端按当前授权读取。从编辑页打开已有标准时保留列表返回条件及原草稿的离开保护。未获职级来源读取权时，按已知或随机职级身份过滤均拒绝，也不会显示无法办理的新建入口。

第二轮按 012 验证部分字段撤权时的草稿。原流程收到 403 会清空整份表单，连仍可维护的下限或计划名称也要重填。现在先移除旧详情与提交缓存，按同一记录的最新权限恢复可维护的更改。薪标试用同时改下限和上限，计划试用同时改名称和固定津贴；重新保存只提交仍获权的输入。只有职级目录权的角色从旧链接也按现权读取。[共享表单规范](../specs/m02/012-m02-functional-and-interaction-design.md#m02-ui-expression)

第三轮从正常菜单完成 13 项 Chromium 场景，用时 3.1 分钟。1440×900、1440×540 分别核对列表、表单、详情和历史；在同一构建从职级阶梯和薪酬计划用键盘打开更正，两个正文顶部差异均在 3 像素内。两类配置均在原生 200% 从表单保存。三计划联验走完六月末、七月首日、十月独立津贴及撤去后的当日值与保存时依据；两类表单的部分撤权均能完成剩余获权修改。相关用例通过后，重复核对八项预期、数据归属和办理步骤，未发现新增主要业务问题。

开发验证通过 `make check`、`make boundaries`、相关实库/API 分片及上述生产页面专项。实库/API 分片包含薪酬两类对象、准确来源、公开前缀升级、精确迁移集及中断恢复。记录草稿首次文档检查因验证登记结果为空而失败；补入已执行的实库证据后复验通过。[薪标用例](../../tests/e2e/compensation210.spec.ts) · [薪酬计划用例](../../tests/e2e/compensation-plans210.spec.ts)
