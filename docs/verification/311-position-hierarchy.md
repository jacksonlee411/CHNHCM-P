## 1 业务验收路径

1. 在岗位定义中备好自2026-01-01启用的A、B、C。管理员从「设置 → 职务配置 → 岗位层级」选择「管理汇报」，查询2027-01-01，点「安排上下级」，选子岗位A、上级B，发布。记下发布版本V1。取消编辑不产生版本。
2. 查询2027-04-01，将A的上级换为C并发布V2。在当前发布版查03-31应为B、04-01应为C。在**同一个04-01**选V1，仍须显示B；返回当前资料后恢复C。切换到「职能协作」不会改管理汇报版本。清除上级并发布表示撤边，不删除岗位。
3. 以只读账号从同一菜单查日期和版本；不得有发布操作。两个管理员从同一版互设A、B为上级，最多一笔成功；败方重读后仍不能发布环。实际员工的经理关系由M04独立维护，本批不写人员、任职、容量或预留。

## 2 实现与独立断言

## 4 评审后补验：发布结果查回与草稿保留

评审时从岗位层级页面中断发布请求，观察到自动查回次数为零。随后手动查回版本冲突，编辑器关闭，子岗位和拟选上级一并丢失。本次在同一 HEAD 的工作区修复并补充[浏览器回归用例](../../tests/e2e/staffing312-hierarchy.spec.ts)，原签收记录仍对应当时的候选。

| 场景 | 回归断言 |
| --- | --- |
| 请求未到达服务端 | 按原提交号自动查回一次。收到未生效回执后仍可看到子岗位、拟选上级和生效日期，版本数不变。 |
| 服务端已发布，响应丢失 | 以新的提交号重新发布后，用同一编号自动查回成功。页面退出编辑，同一生效日期上的上级正确，数据库中仅增加一个版本。 |
| 编辑期间另一次发布成功，原草稿的冲突响应丢失 | 首次查回仍未知时禁止发布。手动查回原编号取得拒绝原因，保留拟选上级并显示最新上级。明确采用当前版本后才可用新编号提交。 |
