# CHNHCM-511 项目规范体系建设与文档治理方案

建议以现有合同为基础，为每个需要长期遵守的条款确定一个维护位置。方案作者从项目首页找到条款，开发者据此选择共用实现和对象差异，评审者用同一条款独立判断结果。本次已整理可直接使用的[项目规范导航](../governance/README.md)。下文的合同调整、归档批次及验收目标供评审，采纳及执行进度见[登记表](../governance/registry.json)。

## 1 规范应涵盖哪些方面

下表给出修订项目标准时需要回答的问题。每次变更选取受影响的行，规则落到对应的共享合同或对象合同。各主题的现行条款和参考实现见[规范导航](../governance/README.md)。

| 范围 | 应在合同中说清的决定 | 评审时核对什么 |
| --- | --- | --- |
| 业务规则与术语 | 对象身份、事实归属、角色、办理前置、状态转换、金额或数量口径、更正与撤销。涉及政策时写明适用地区、期间和依据 | 一组正常输入和一个边界或拒绝样本，各自产生什么事实。相同业务名称在接口、页面和报表中含义一致 |
| 数据、日期与历史 | 字段含义、单位、默认来源、生效区间、修订、采用和追溯。区分业务日、记录时刻和读取原件的版本 | 主数据首建、后续更改、同日办理分别取得正确日期。更正后可按准确来源查到当时的值 |
| 权限与隐私 | 操作、对象、字段、用途和数据范围，覆盖搜索、计数、导出、原件及审计 | 受限角色从菜单、直达地址、返回历史和 API 得到一致的获权范围，可见计数随撤权更新 |
| 页面布局与视觉 | 菜单及路由归属、主题、字号间距、顶栏与控制区、正文滚动、列表、详情、表单及字段分组 | 在同一构建的参考页和本页对照。桌面短屏能到达末字段、错误和操作区 |
| 交互与可访问性 | 查询草稿与应用、选择、提交、取消、并发冲突、未明结果、未保存保护、键盘和焦点、返回原位置 | 从正常入口走完一次操作和异常返回，核对事实、输入、当前行和焦点。关键流程按共享合同实测原生缩放 |
| 共用组件与页面组合 | 组件用途、输入输出、状态及键盘行为，主题和布局由谁提供，列表、表单、页签与日期轴如何组合。列出共用实现、实际消费者及对象差异 | 能定位一处实现和一个已接入的参考页面。共享修改同时验证原消费者与本次改动页面的可见行为 |
| 领域、接口与工程实现 | Go 领域判断、跨域公开端口、API 与事件、事务与幂等、数据迁移及生成物，明确源域和消费方责任 | 一个失败、并发或重试样本可验证事实与回执，能从公开合同追到所属域的实现 |
| 验证、容量与运行交付 | 独立验收预期、按影响选层、性能样本与阈值、受测构建、首败和复验，以及升级、验收环境和资源交接 | 评审能说明哪些用例实际通过、未通过或未测，容量数字有样本、负载和适用范围 |
| 文档、来源与变更治理 | 权威位置、适用范围、责任角色、稳定条目标识、采纳与替代、来源资产、计划关闭和历史检索 | 同一条规则能由方案追至实现和证据，旧版本能按原编号及基线查回 |

## 3 标准写在哪里，变更由谁决定

1. **入口按任务组织。** 建议首页提供“查现行标准”“查在办及拟议方案”“查验收记录”“查历史”四类入口。规范导航直接链接条款和对象差异。计划清单从登记表筛选 `type=plan`，按执行状态区分待办、在办与已关闭，另列文档采纳状态。已关闭计划可从历史入口检索，物理位置取登记路径和归档字段。报告按关联文档号和受测基线查。导航只维护主题和链接。[005 编号与登记](../governance/005-branches-and-documents.md) · [014 分类](../governance/014-document-management.md#2-分类目录与权威归属)
2. **长期决定写回负责的合同。** 业务对象的事实、场景与验收进模块规格。共享页面行为进 012 的共享章节，对象的业务差异进对象页面合同。组件用法补“使用条件、状态、实现、参考页、消费者、验收”对照，样式值由主题和组件实现维护。跨模块技术约束进架构文档，关键取舍进 ADR，文档及交付规则进治理规范。确有缺项且现有合同均无法承接时，由对应维护者按 005 领号、按 014 选择类型和模板，经评审采纳后接入现行导航。计划记录本批范围、顺序与未结项，验证记录保存受测结果。[领域边界](../architecture/004-repository-layout.md) · [功能规格模板](../templates/functional-design.md) · [组件与参考页对照样本](../specs/m03/308-job-foundation-contract.md#m03-page-inheritance)
3. **把条款写到能判定。** 一条约定写清触发条件、适用对象、必须／应／可的行为及可观察结果。需要追踪的业务规则、场景、验收条件沿用模块内的 BR、SCN、AC 标识和显式锚点。共享体验条款沿用已有语义锚点。对象合同只补具体业务差异、原因及验收样本。[014 标识与引用](../governance/014-document-management.md#42-稳定规则场景和验收-id) · [页面差异模板](../templates/dated-object-admission.md#page-inheritance)
4. **按影响处理冲突与例外。** 作者先核对两条约定的适用对象、采纳范围和明确替代关系。单对象差异由对象维护者说明业务理由、影响、验收依据，临时偏离另记截止或复查条件。改变共同行为时由共享合同维护者与受影响的消费方审阅同一份修订，同批更新条款、引用及预期。局部替代要指出旧条款剩余的适用范围，整体替代才登记 `superseded_by`。仍有分歧的部分在计划中列明裁定角色和处理节点，已采纳合同继续作为判断依据。[014 新建及修订](../governance/014-document-management.md#81-新建及修订)

## 4 修订、开发和评审共用一组依据

建议把以下字段放进现有计划、功能规格及验证模板的相应位置。方案为每个受影响的条款给出场景和判据，开发与评审沿用同一组链接补充实现和证据。[现有模板](../templates/README.md)

| 环节与责任 | 在现有工作产物中写什么 | 进入下一环节的判据 |
| --- | --- | --- |
| 修订方案 · 方案作者与合同维护者 | 目标场景、现行条款链接、继承或拟改之处、影响的对象和消费者、正常与反例预期。页面任务另列正常菜单、同构建参考页、共用实现及差异 | 审阅者能指出每个变化的依据，直接影响实施的待决事项已有处理决定。实质修订记录实际审阅范围与结果 |
| 开发实施 · 领域与前端实现者 | 把条款对应到 Go 业务判断、API、所用组件及页面接线。按影响验证正常办理、失败保护、历史及原消费者。发现合同缺口时回到负责的合同澄清 | 每个适用验收条件都能定位实现和独立预期，未覆盖项有具体范围与去向 |
| 评审与验收 · 评审者与验证维护者 | 从条款推导预期，再核对同一候选的实际行为，记录基线、角色、输入、期望、实际、证据和结论。结构与链接用自动检查，业务差异、取舍和证据充分性由对应维护者复核 | 差异能追到条款和复现步骤，修复能追到复验。分别记录方案采纳、计划执行和逐项验收结果。[003 完成口径](../adr/003-implementation-stages.md#4-完成与证据规则) · [137 分层验证](../governance/137-actions-and-validation.md#4-按影响选择验证) |
| 关闭与交接 · 计划及文档维护者 | 更新计划执行状态和关闭原因，关联定稿报告，交接开放项、长期定义和运行环境。同步当前入口，发起归档评估 | 从当前入口能找现行条款，从历史入口能查到原计划、原结论和后续接手位置 |

## 5 怎样处理已完成计划

按 014 先评估执行已完成或取消的临时计划，以及已替代、废止或取消的文档。每份记录原号、仍有效的条款及承接位置、未结事项及负责方、原证据、反向引用、处置理由。建议先按下列三份校准判断。[014 归档流程](../governance/014-document-management.md#82-归档)

| 试点对象 | 建议处置 | 可核对的退出条件 |
| --- | --- | --- |
| 008 编写 M02 四份文档，执行已完成 | 优先评估直接归档。核对编写任务与 010—013 的实际承接，检查 003 等现行文档和定稿报告对旧路径的引用 | 仍需的条款、后续事项各有去向，原编号和关联报告可达，才登记迁移。[008 正文](008-next-steps.md) · [003 阶段输入与输出](../adr/003-implementation-stages.md#2-阶段输入交付与退出证据) |
| 301 提示与异常恢复，执行已完成 | 先逐项裁定 17 个 AC。由 M02 维护者将有效定义交给 011 共用规则或 118 部门差异，012／119 关联相应页面行为，121 保留接入映射。已经退出的项记录依据 | 逐项有去向，每个现行 ID 只有一个定义，121 可直接指到有效条款，原失败和复验仍能按 301 查回。[121 规则归属](../specs/m02/121-dated-object-admission-matrix.md#1-规则拥有者与执行边界) · [301 原实施证据](../verification/301-user-feedback-implementation.md) |
| 500 人员路线，仍在办 | 保留交付入口。先定位 8 个场景及现有调用方，按场景确定 M01／M04 等长期接收合同，随相应修订处理 | 在办批次和引用能继续追到原场景，待执行关闭再评估物理归档。[500 场景与关闭条件](500-personnel-roadmap.md#5-验收样本与关闭条件) |

定义暂由计划持有时，目标规格先链接原锚点。实际迁移时，在同一批变更中切换现行定义、引用和归档登记。归档原文保留原 ID、标题、历史锚点与结论，正文移入 `docs/archive/<year>/<原类别>/`，登记 `archive.date / reason / previous_path` 并更新路径。分别从新入口和旧报告复查条款、证据及附件。若定稿原件的相对链接在迁移后无法解析，先把该计划列入历史入口、原位保存，记明待处理的具体引用和复查条件。按这些判据统计处置结果，可同时看到已归档和有理由留在原位的文档。[014 稳定标识与历史](../governance/014-document-management.md#42-稳定规则场景和验收-id)
