## 3 首次失败与复验

真实 API 初验中，恢复岗位的样本使用了启用记录作为锚点，返回 400。改为选择停用记录后通过。升级并存样本首次以旧主体读取新增职类字段，依据当前字段权没有该字段。只在临时库按 314 流程开通后重新从原备份复跑，核对通过。首次静态检查发现浏览器用例缺少 CI 影响范围登记，补入项目和影响映射后通过。

浏览器首次连续切换日期和部门时，较早渲染的菜单把地址里的业务日覆盖，部门合计回到今天。快速搜索再打开岗位也曾丢失列表关键字。修正条件合并、等待新结果期间的行和进入详情时携带的查询条件后，在上述五种视口复验通过。原生 400% 在两次查询之间还出现输入被重置；按日和搜索草稿保留到用户显式提交，缩放用例另检查键盘查询与返回行焦点。开发服务器的初次加载曾导致原生缩放和双人样本超时，固定构建用于复验。

完整 `make integration` 在仓库设定的 20 分钟包级上限超时，当时正在执行部门 D35 和部门范围并发案例。已回收该命令遗留的两个测试容器。按影响另跑地址、法律实体、职级、职级阶梯、岗位、层级升级、核编和存储准入。重建旧前缀的测试夹具有一次未还原旧的授权范围约束，导致再次升级失败。补齐旧前缀后，存储准入单测复验通过，也验证了缺失额度投影或禁用三个不可变触发器时拒绝运行。Outbox 故障样本首次把依赖不可用预期写为 500，按现行 API 合同修为 503 后复验通过。

| 复评问题 | 原设计依据与偏差 | 本次口径 |

| 为什么列表和详情都有“查询日期” | 313 要求指定日统计直属启用岗位和额度，315 又要求取消时保留查询日。原实现把同一 `businessAt` 从列表带进单岗详情，验收样例也在详情直接切日。普通维护的既有决策要求服务端取北京时间当日，详情按生效记录或准确来源定位。 | 岗位列表、岗位编制页无查看日期输入。查某日某部门的分配才使用“统计日期”。统计行有当日额度记录时按稳定 ID 下钻，返回恢复部门、统计日、搜索及行。将来首次核定显示尚未生效。 |

决策依据见 [123 当前维护与专项查询](../adr/123-current-maintenance-and-dated-query-boundary.md)、[012 日常详情与历史](../specs/m02/012-m02-functional-and-interaction-design.md#m02-ui-history)、[313 后台核编合同](../specs/m03/313-position-capacity-contract.md) 和 [315 实施计划](../plans/315-staffing-quota-administration.md)。

### 6.1 整改与验收依据

- 岗位与统计入口共用同一个编制页和 Go 写入口。核编只读岗位身份、生效段、启停、直接归属和来源，使用独立额度根、修订、Outbox 及回执。核编保存前后核对岗位定义来源。
- 从统计行、时间线或回执按记录 ID 定位。原记录消失时停止该目标的写入并提示重新选择。响应丢失后的查回附带获权的原件定位；删除保留删除前原件。无变化有明确反馈。
- 变更日志读取相邻不可变额度来源，按操作分组列出前后值、受影响期间和原因。删除操作取当次操作者，原件保留原修订操作者。日志支持分页、列筛选、固定上界与返回定位；审计、日期、原因按当前权限裁剪。
- 修改冲突保留可继续办理的输入，撤权后重读并清理未获权字段。删除预览由 Go 返回被删记录的原适用段和替代额度。普通更正显式清空原原因时返回字段错误。表单沿用岗位的分栏、日期控件及未保存保护。
- 部门按当日直属启用岗位计算获权合计和未核编岗数。首次核定在未来以及撤编期间计入未核编；零额度和停用岗位均不计入。搜索和分页不会缩小部门合计，岗位范围授权只计入获权对象。
