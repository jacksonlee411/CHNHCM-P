2026-11-28，员工详情的「薪酬」页签与「职务信息」并列，从人员名录选中的实际任期进入。经办人与查询者走同一菜单，分别按个人金额、历史、办理与制度来源的权限取数。设计基线为 `a075829`，首个产品提交为 `8c85ba4`，连续办理修复后的受测版本为 `9586806099aa646fbdef4d9a7747171c3ced9232`。[业务方案](../specs/m09/215-assignment-base-pay.md) · [技术合同](../specs/m09/216-assignment-base-pay-contract.md) · [方案复核](214-assignment-base-pay-design-review.md)

## 1 实库核定、权限与故障恢复

使用真实 PostgreSQL、生产 Go HTTP、两次登录会话以及实际的任职、计划和薪标。按 215 的场景核对了下列结果。[实库 HTTP 用例](../../internal/bootstrap/compensation_award_integration_test.go)

| 核对事项 | 实测结果 |
| --- | --- |
| 同一人两份任期 | 专业主岗、运营兼岗分别选计划；只获指定兼岗读权者打开主岗详情、原件及原号均被拒绝。离职间隔查不到有效任职。再聘沿用 0 号并取得新任期，初始尚未定薪。 |
| 薪带与决定按日独立 | 十一月拒绝 15,500，十二月接受 15,500 及上下限 11,000、16,000，拒绝 16,250、空额和三位小数。另一个任期十一月定为 10,500，十二月新下限 11,000 生效后仍能查到原约定。 |
| 多计划、插入、更正与撤去 | 多份合格计划需选定，纯津贴计划未入选。草稿所选计划仍有效时，新增另一合格计划能保留已选计划。十一月原笔 12,100 更正为 12,000，插入和撤去十二月决定均保留一月独立后继；原申请号仍指向原修订。 |
| 两人争办及来源变更 | 两个会话同时按空时间轴提交首笔，只有一次成功。另用两会话竞争十二月调薪和追溯降低十二月薪带上限；已取得旧带的原件保留旧上限，过期的草稿重新提交返回冲突。撤来源原件读权后仍可查询获权个人额，撤个人读权后原号和原件均不可用。 |
| 事务和原号 | 向隔离库的 Outbox 注入约束错误，服务返回失败，核定、有效段、事件及回执均回滚。主动查回与迟到原请求使用同一锁。确认未执行后，原申请者可以用原号重送；不同内容被拒，重复重送仅有一份成功结果。 |

薪酬域九项实库测试通过，包括首期薪标、计划日期、适用范围、权限和原采用。增补写入故障与来源竞争后，新核定用例再次单独通过。三项迁移用例覆盖现行迁移准入、迁移中断及既有国家地区资料升级。最后一次个人核定实测为一份获权任期、三份有效计划、两份候选、五个有效工资段，一会话连续十读共 1.06 秒。两会话的竞争另测。全仓 `make integration` 在两个包的 20 分钟时限到期，分别运行到部门 D37 与早一版薪酬用例的容器启动；全仓集成结果未取得。[迁移准入](../../internal/bootstrap/t07_storage_admission_integration_test.go)

## 2 浏览器、首败和复验

从「人员 → 人员名录」按主岗任期打开「薪酬」，覆盖了取消、金额报错定位、保存后丢失响应按原号查回、更正、调薪、跨日查询、查看当时薪标、返回核定原行和名录原行。1440×900、1440×540 的 100% 与 Chromium 原生 200% 三项全部通过。原生缩放也核对了受焦链接、返回后的原按钮及横向溢出。另有五项受影响的原功能通过，涵盖既有首单草稿、只见兼岗的职务信息、薪标与计划的并发重读、断线恢复及年薪原件导航。[薪酬页签场景](../../tests/e2e/compensation214.spec.ts) · [首单与兼岗回归](../../tests/e2e/first-hire.spec.ts)

首轮混用较早的 API 和带候选分页的前端，返回未知查询条件。对齐构建并规范首页参数后继续测试。第二轮发现断线查回期间的短等待预算和查看工资原件返回时的焦点丢失，分别改为等待服务端回执，以及在记录重新渲染时定位原行。4380 接续办理又发现，更正关闭后立即调薪可能带入旧工资版本；保存后先重新读取记录再开放下一笔，三个视口按此时序再次通过。固定环境保留第一次办理成功的首笔与更正，下一笔以独立调薪接续。

## 5 与已合并的地址类型版本对接

主线 `d474520` 已分别用 00061、00062 交付地址类型和按日启停。4380 的首个二期版本 `9586806` 在独立的 00061 下已保存四份工资修订与回执。共同版将原薪酬 SQL 原样置于 00063，文件 SHA-256 为 `073c1eb03950c787733824cb0b4055941fd58e64f79be3b838a352164829b8d5`。upgrader 保留已应用的 00061 行，按实际存储结构补齐两类对象。[共同版接入规则](../../db/migrations/README.md) · [两类旧库升级用例](../../internal/bootstrap/t07_storage_admission_integration_test.go)

首轮在 4380 的完整备份副本上发现，补建地址类型时初始四项带有待检的延迟外键，紧接着执行区间 DDL 会被 PostgreSQL 拒绝。共同版在同一迁移事务内验证这些外键后再执行 DDL。使用第二个全新备份副本连续执行两次 upgrader，原 1 至 61 的账本行、十一张薪酬、授权及人员表的行数与正文摘要完全相同，四份工资回执及其原修订一致，新建四个标准地址类型。隔离实库还验证了不可变回执触发器被关闭时拒绝升级，恢复保护后从 62 中间点重试成功。所有数据库操作均保留原业务历史。[原核定与回执号](data/214-assignment-base-pay/awards.json)
