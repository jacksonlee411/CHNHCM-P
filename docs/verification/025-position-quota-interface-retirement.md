## 2 验收预期

- 从现行岗位编制页可核编、查回丢失响应并打开准确原件。重复查回不新增回执或核编记录。撤去历史读取权限后，原件内容不再可见。
- 已登录经办人向原岗位写地址提交应得到 404。新提交号不产生核编或回执。现行接口、公开说明及生成客户端须同步撤下旧操作和专用请求类型。
- 用 00027 的原版程序办理首次核定、更正和删除，再恢复备份并前向升级。将现行入口返回的来源、记录和数值与升级前的原件核对。删除回执要能打开删除前那条记录。

## 3 首败、整改与复验

在修改运行代码前，实库测试向有效岗位的旧写地址发起新请求，实际返回 409，预期为路由已退出的 404。另一项测试由 00027 程序生成四份成功回执。首次核定 2 人、同日更正为 3 人、后续调到 4 人的三份原件都能打开。第四份删除回执把查看原件的链接指向删除后的版本，所选记录已不存在。

整改撤下 Go 路由和专用重送分支，同步删除 OpenAPI 操作、旧请求类型及生成客户端声明。查回继续使用原提交号，保持原请求摘要、结果和授权校验。服务在读取原回执时识别原始删除动作并返回删除前的来源，页面显示删除结果。历史回执中的动作和内容保持原样。[现行服务](../../internal/bootstrap/staffing_quota.go) · [结果读取](../../internal/contexts/staffing/application/quota_commands.go)

从原仓已核对提交的离线快照生成 00026（`9c490a97`）和 00027（`b647031b`）合成备份，分别还原到独立 PostgreSQL，连续执行两次 upgrader，再从当前 API 读取。00027 四笔均指向对应原件，删前原件为 4 人。原号改走现行写接口返回 409，撤去原经办人历史读权后查回不再返回原件引用。复验前后的原终态及岗位事实摘要一致。313、315 的岗位核编和部门分配实库/API 用例也通过，包括丢响应后重启查回、同号异内容冲突和旧地址返回 404。[备份恢复断言](../../internal/bootstrap/hire_upgrade_integration_test.go) · [岗位核编回归](../../internal/bootstrap/staffing315_quota_integration_test.go)

在还原的 00027 副本上，以原经办人登录当前构建，从「查看保存结果」依次打开四份原件。Chromium 实际显示 2、3、4、4 人，最后一笔显示「已删除」并打开删除前的 4 人记录，全程向旧写地址发出的请求为 0。另在临时环境跑两轮 Playwright，第一轮 7 项通过（含 5 项企业前置），第二轮 3 项通过。覆盖 1440×900、1440×540 和两角色原生缩放。两轮收尾均回收了各自的容器、卷和网络。[浏览器恢复用例](../../tests/e2e/staffing315.spec.ts)

`make check` 通过文档治理、领域边界、运行脚本回归、Go 单元与静态检查、前端类型检查及差异格式检查。独立重新生成的 API 类型与提交候选逐字节一致。实库与浏览器按此次影响定向执行。
