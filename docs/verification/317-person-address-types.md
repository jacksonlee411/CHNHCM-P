## 2 旧库与分轮评审

1. **方案评审。** 地址类型只用于分类，住址、主要标记和 M02 地址来源分别由原合同维护。预置四项用首次真实修订兼容旧客户端，旧住址的原文留在原档，首次生效日不会变成历史采用日。查回使用提交人、提交号和现权，确认未执行可以阻断迟到命令。
2. **存储与旧版评审。** 首轮发现旧前缀的离线初始化器会调用尚未安装的地址类型函数，改为按实际结构初始化。用 00058 建库，写入原人员来源、旧住址和办理终态，再执行 00061。按旧列对账，地址行正文、原修订、事务行版本、来源、回执及既有授权相符。类型引用的三列均空。重跑初始化不新增修订，也不恢复已撤的配置权。三个更早的公共前缀、Country200 迁移及 T07 准入回归通过。另用公共旧版 `9173033` 经 HTTP 实际登记人员、保存住址并导出 00038 备份。按旧列逐项比较 14 张表，并检查新加的三个采用字段全空。恢复到 00061 后一条住址原文和两个成功回执经 API 查回。前 T01、00031 与 00036 的原私有验收备份未在本机复跑。[00058 迁移用例](../../internal/bootstrap/person_address_type_upgrade_integration_test.go) · [原版备份恢复用例](../../internal/bootstrap/personnel_restore_integration_test.go)
3. **业务与恢复评审。** 将“再次提交原采用”和“向另一行新选过期项”分开实测。前者沿用原采用，后者触发重选。补测并发同编码、修订竞争、选中项锁、读写权分离、配置写入中断与原号恢复。用例首次显式传空字段对象为 null 被协议拒绝，改用符合公开合同的空对象。注入故障按实际服务暂不可用状态 503 验收。
4. **页面与治理评审。** 在真实菜单实测时发现自动化按标签精确匹配会受必填星号影响，宽松匹配又会选到列表列菜单，改为在当前弹框定位。配置试点用例独立建合成员工，通过 1440×900、1440×540、原生 200% 三组走查。各组均完成草稿离开保护、更名后保留输入并重选、停选后只改门牌。同构建对照职级列表，两档视口的顶栏宽高均为 1440×65，控制区均高 64 px。短屏两页均可纵向滚动，地址类型末项可见，键盘可打开、编辑和取消。两页均无水平溢出。原 504 地址目录选择及跨栏保存用例也通过。首轮文档治理检查指出验证记录漏登记，登记后复验。上下文清单也改为引用实际声明地址类型路由的文件。[浏览器用例](../../tests/e2e/personnel-address-types.spec.ts)
5. **跨分支集成评审。** 交付前核对所有本地 refs 及登记工作树，发现 wt-dev-c 已提交薪酬的 00059、00060。地址类型由本轮预演号改为 00061。此树要求准确的 00001 至 00058 加 00061，并校验不可变修订触发器。其他账本和关闭该触发器的库都被拒绝。合入薪酬实现时，集成者须对两条实际旧前缀分别验证，再接受完整账本。[迁移约定](../../db/migrations/README.md)
6. **重复压测与授权评审。** 正式迁移号下首轮 20 会话通过，再测两条整页链路 P95 为 1707.88 和 1691.76 ms。实验性地分散人员写锁后，锁等待峰值归零，保留原类型的整页链路仍达 1981.16 ms。数据库语句采样显示，人员办理每笔也会载入通用对象授权。合成管理员有 180 个对象授权绑定，一次读取锁定 540 条角色、范围和字段版本。诊断运行中该查询执行 1780 次，累计约 53.9 秒。改为由 X03 在人员专用授权入口核验会话、主体、人员用途、行和字段权利。真正选择 M02 地区时，目录端口在原事务获取完整对象授权并核对来源。保留原人员写锁单测 20 会话，两条整页链路分别为 1062.12 和 990.54 ms。交付采用此方案，沿用原编号、证号、处置及入职核对的锁顺序。[X03 人员授权](../../internal/contexts/access/infra/postgres/personnel.go) · [M02 地区采用](../../internal/contexts/organization/infra/postgres/geoarea.go)

## 3 成本与容量

基线与候选在同一 WSL2 主机顺序测量，Intel Core Ultra 5 125H，分配 18 个逻辑 CPU、约 19.5 GiB 内存。Go 1.26.8，PostgreSQL 18.6，API 连接池上限 12。数据库含万名人员及二十份九栏样本。初始数据含 100 名各有 21 份来源的人员及 9900 名各有一份来源的人员，九栏样本选自前一组。每一行指标在预热后二百次采样，20 会话合计二百次。每次整页办理包含保存、按原号查回、重读并逐栏核对。原实现的候选是前端固定数组。本次单会话详情限 300 ms，其余单会话限 500 ms。原 20 并发目标为 500 ms，按用户本次决定，317 临时采用 1500 ms。[容量用例](../../tests/integration/personnel_nine_sections_capacity_test.go) · [各轮样本与时延汇总](data/317-person-address-types/capacity.csv)

| HTTP 办理链路 | 基线 1 会话 P95 | 交付版 1 会话 P95 | 基线 20 会话 P95 | 交付版 20 会话 P95 |
| --- | ---: | ---: | ---: | ---: |
| 九栏详情 | 48.99 ms | 37.02 ms | 352.27 ms | 227.44 ms |
| 整页更正、查回、重读，保留原地址类型 | 126.76 ms | 125.92 ms | 1296.69 ms | 1241.89 ms |

交付构建八组共 1600 次采样、3200 次 HTTP 请求，失败和超时均为零。20 会话的候选读取、保留原类型和改选类型三组数据库锁等待峰值分别为 0、11、11。四条 20 会话链路均满足临时 1500 ms 目标。原 500 ms 比较值继续保留。基线整页更正为 1296.69 ms，中途与其他构建同时运行的诊断曾测得 2081.12 ms。00061 首轮详情曾达 824.46 ms。最终结果在本批浏览器及数据库回归结束后独立测得，各次超限均保存在容量明细中。

地址弹框按需读取身份、编码、名称及修订。实库执行计划一次按客户走 `address_type_choices` 索引，命中两个共享缓冲页，返回五项并过滤一项未来首日。办理已保存地址的普通详情无需连接词表。一次更名及调序更新一个当前项，插入一个不可变修订兼成功回执，员工资料零改写。测试中当前表及索引分别为 16 和 64 KiB，修订表及索引分别为 16 和 32 KiB。该次修改容纳在既有页内，以上是首个小词表的实测占用。

管理员打开目录后，新增经「新增 → 填写 → 保存」，改名或调序经「打开该项 → 修改 → 保存」，停选与恢复在同一表单更改选用状态。每次保存发送一笔配置命令。经办人使用原地址弹框的「应用」和整页「保存」。首个目录尚无第二个同形目录的实施成本样本。
