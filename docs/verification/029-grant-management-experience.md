# CHNHCM-029 授权页面评审与实施复验

## 1 评审结果

2026-11-28 在 wt-dev-a 对 029 送审提交 `e11050e`、028 当前合同和 4627 原页面复核。固定库的 `admin` 有 183 份业务授予，原接口一次返回全部。`x03-4627-1128` 有同一账号下的三份已撤授予、六次变更。撤销表单缺少选中目标，列表也无法区分账号启用和还有几份生效授予。依据 Odoo 的用户分组、Oracle 的版本反查及 012 共享体验确定页面结构，实际判权、版本绑定和历史仍来自 X03。[029 方案与对标来源](../archive/plans/029-grant-management-experience.md) · [028 授权合同](../specs/x03/028-local-account-and-authorization.md)

评审补正了三个具体问题。

| 情况 | 实施决定 |
| --- | --- |
| 授予换至 V2 后再查当初的 V1 | 日志按当时提交关联不可变修订，以当前权限分别裁剪前后值。单次回执按请求身份查回，浏览页码不影响查回资格。 |
| 停用前又有人采用或开出一份引用 | 复用原管理事务和版本锁，两次计算有效业务与管理引用。显示有权主体、来源、期限和分别计数。变化返回冲突，越界不传出受限身份、计数或核对标记。 |
| 同一显示角色有多份授予，或只发布了 V1 | 从逐份身份进入撤权，表单带入目标、来源、期限、编号。同名同期限在列表显示可区分编号。Go 找到一组实际可办理的同定义新绑定后才显示换版。 |

这次只使用现行数据库表、管理命令、回执和共享页面控件。表单草稿、引用列表切页与查询条件复用同一条页面路径。

## 2 实库与浏览器

| 场景 | 从正常入口办理及独立预期 |
| --- | --- |
| 甲经办人兼任本职、限期代理 | 在「设置 → 安全管理 → 授权」查账号，筛选状态、打开原代理，取消后焦点回到原按钮。提交仅撤代理，本职仍可查部门。再撤本职，经办人的部门接口返回 403。按提交记录能返回准确授予。 |
| 部门角色 V1/V2 共享 | 发布 V2 后原授予仍用 V1，仅指定授予采用 V2。按 V1 反查后可返回原版本和原行。限权者只获准看甲名下的完整授予。增加第三个引用后按旧名单停用返回 409，重读后才可办理。有效委派上限单独计数。 |
| 存量账号及管理职责 | 从账号资料进入同一授权页。默认 20 行，可切换 50、100，按角色、业务范围、来源及状态查询。查看后返回原查询。管理员的长期管理资格置于身份栏，短屏首屏可读。 |

受测实现包括 [Go 授权读取](../../internal/contexts/access/infra/postgres/management_workspace.go)、[版本引用与历史](../../internal/contexts/access/infra/postgres/management_references.go)、[管理页](../../apps/web/src/features/access/SecurityManagement.tsx)、[真实 DB/API 用例](../../internal/bootstrap/access_management_integration_test.go) 和[桌面浏览器用例](../../tests/e2e/access-management.spec.ts)。取证账号与数据均为本地开发样例。

首轮 TypeScript 检查发现管理视图的 `total` 在 OpenAPI 被列作可省略。Go 所有响应都会返回该值，已将 `total` 与页码列为必返并重新生成客户端。首轮独立临时数据库的六项管理集成通过，覆盖旧库、账户交接、共享版本和截止时刻。首轮临时浏览器 12 项通过，其中安全管理 7 项，同构建前置 5 项。后续候选增加了跨入口焦点和存量搜索用例。

## 3 固定环境与范围

本树负责的手工验收入口为 [4627 授权列表](http://127.0.0.1:4627/settings/security/grants)。部署前从同一原库读取三个样例，按稳定身份、版本、修订、状态以及日志的原提交身份留存摘要。正式客户验收由验收方另行执行。

第一版固定候选的短屏仍有重复栏目标题、只读空操作列，历史中同一撤销描述重复出现。复评后保留可聚焦的栏目标题、按需显示操作列，日志默认展示来源、目标、操作者和时刻，原修订随行展开。1440×540 首屏完整授予行从 1 行增至 3 行。

最终本地检查通过 `make check`，包括文档登记、边界、运行工具、Go 测试和 vet、Web 类型检查及差异格式。初次全检查在最后一步发现 028 文末多一个空行，修正后重跑。7 项相关真实 DB/API 用例通过。其中 23 份同名、同范围、同期限的授权验证了第 2 页定位、原回执跨页查回。另以仅委派身份对照，目录不传生效业务授予数，默认进入管理职责，无权读取业务授予及这 23 份的变更。扩展后完整浏览器分组 13 项通过（安全管理 8，前置 5），对最终工作树使用独立临时实例再跑安全管理 8 项通过，含 1440×900、1440×540 和原生 200%。另在只含本次提交的独立检出通过 `make check` 及两项授权集成。没有以早期浏览器通过数替代最终候选复验。

固定 4627 从原容器、原卷更新。管理员从设置菜单进入授权，两个桌面高度下控制区与同构建业务单元页均为 64 px。短屏可直接看到长期管理资格。原 183 份业务授予有 162 份生效，默认接口由 183 行变为 20 行。三个样例的授予身份、绑定、修订、状态和管理变更的目标、原回执摘要在更新前后一致。实页从六条历史中的撤销事件打开原授予成功。固定库的业务数据仅用于读取和对账。验收地址继续由 wt-dev-a 负责，客户验收或本树下次更新时复查。[逐项对账与视口测量](data/029-grant-management/results.json) · [1440×540 存量授权](data/029-grant-management/admin-540.png) · [1440×900 原授予历史](data/029-grant-management/history-900.png)
