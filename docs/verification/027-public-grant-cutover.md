## 3 业务事务

同库双连接通过 PostgreSQL 阻塞关系确认顺序。BU 创建由每份独立授予支持，撤代理权后另一份仍能保存，撤尽后被拒。先办理时撤权等待，先撤权时办理等待；等待中到期被拒，业务和提交终态均无新记录。覆盖共享角色与字段版本停用、显式换版、用途不符、新开户注册及同号重放。[BU 提交顺序](../../tests/integration/bu_test.go) · [重叠授权与到期](../../internal/bootstrap/access027_integration_test.go)

首单入职测试在就业事件写入处持锁，等待 Organization 判定过的最后一份 `legalpurpose.check` 到期再释放。首次收到 200，查明首单使用 pgx 保存点，外层守卫未获得内层决定。修正后由每个内层守卫独立认证，外层在同一物理事务提交前复验其限时决定。该用例返回 403，工作关系、任职、主选择、事件和该提交的回执均为零。显式重新授予后原正常流程通过。后续一轮交叉运行又收到一次 200，该次释放锁时没有采集数据库或应用时刻，原因未确证。在诊断副本中同时观察到内层决策、父守卫复验及实际截止时刻，五轮通过。测试补充提交 `a2db1b1a633c9884e7f102930a1cdbd86882aed0` 改为在持锁连接上等待该授予的入库截止，释放前核对并记录数据库和服务端两个时刻。BU 与首单入职两个原入口各连续三轮通过。产品代码与 `dc554f39` 一致。[首单入职实库回归](../../internal/bootstrap/first_hire_integration_test.go)

## 4 编号、实际时延与边界

开工实查 `wt-dev-e@933b1d09` 已有任命决定 00039，本候选取 00040。再次查询六个远端分支时 main 仍为 `1126c2b6`，e 已前进至 `dae4b1e0`，其中 00039 SQL 内容一致。a 的产品程序准入 1—38 加 40。另以同一旧库的独立副本，用 Goose 顺序执行 e 原件 00039 和 a 原件 00040，实得连续 1—40、任命版本表及全部 272 份原权限。此项只覆盖两份 SQL 的顺序和数据相容性。合流程序仍须对合并后的准确账本和各域实物重新验证。候选本地取号尚不能替其他主机完成全仓登记。

三台主机六分支协作的建议是由维护者在同一受保护远端登记号、任务、负责分支和前置迁移，只允许追加。两条分支同时从同一登记版本领取时，远端只接受一次快进；另一方刷新后重新领号。以远端接受为取得编号的时点。合入时在最新 main 的合并候选上检查编号唯一、归属匹配、历史 SQL 未改，并从实际已发布库升级。对于本批，先合 e 的 00039，再将 a 同步到该 main，更新启动准入并从 00039 实测升至 00040。已发布编号永久保留，取消的预留显式登记去向。该流程为协作建议，本地候选尚未配置远端登记。现行规范见[005 多主机协作](../governance/005-branches-and-documents.md)。
