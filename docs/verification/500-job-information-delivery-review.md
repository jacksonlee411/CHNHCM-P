## 4 阶段 1 首任期与地点办理

`00041` 把旧首任职及撤销后补办的任期关联到本人同一份 0 号。`00042` 把首次办理的日期、依据及原采用移入准确修订，保留首次经办人与登记时刻。旧入职及撤销分别构成可定位的来源。旧单只记地点身份时，按当天及当前权限读取地点名称。新办地点变更保存采用的地点来源、修订、前后值及用工用途依据。经办人从原笔更正时，Go 保存被替换的值及准确前版。每次发布的任职来源保存成员及非重叠的日状态，回执和待发事件绑定当次修订。[迁移](../../db/migrations/00042_job_information_sources.sql) · [Go 办理](../../internal/contexts/staffing/infra/postgres/job_information.go)

- 真实 PostgreSQL 的 00040 旧结构放入同人的已撤销首单、替补首单、名单行、两层主选择及原回执，重复运行统一 upgrader。逐行比较十张旧表的原字段，两个任期属于同一份 0 号，旧采用及事件均可核对。[升级试件](../../internal/bootstrap/employment_record_upgrade_integration_test.go)
- 真实 API 以合成员工和四个地点办理。2027-04-30 仍为甲，5 月 1 日甲改乙，从原笔纠错为丙，原办理身份一致，原修订和原来源仍见乙。6 月 1 日第二笔独立生效；两个竞争更正一成一拒。注入事件写入失败，当前版本、动作数与日状态回滚。原提交重送及查回均保留首次准确修订，撤权后回执仅返回结果。获权任职查询按人去重，收回读权后名录和部门树都不披露该任职。[业务试件](../../internal/bootstrap/job_information_integration_test.go)
- 首轮来源成员写入的 UNION 参数类型推断失败，显式使用 UUID 后，在双连接首单、注入回执失败、撤销及重新读取的原测试通过。桌面菜单首轮走通地点更改、原笔更正和旧值读取，返回时发现虚拟表格重建后焦点丢失，进入列表复验。

- 五种常规视口（1440×900、1440×540、390×844、320×900、320×256）及 Chromium 原生 200% 实测，六项均通过。自正常人员菜单选业务日、查姓名、用键盘打开任职行，办理地点甲改乙、从原笔纠正为丙并读取甲至乙的旧修订，返回原查询且焦点落回原任职。复测中另发现快速改日期后搜索会因异步查询使用旧地址而丢失日期，现按最新查询地址合并条件。本地单浏览器六项共约 1.4 分钟。[菜单与缩放用例](../../tests/e2e/first-hire.spec.ts)
