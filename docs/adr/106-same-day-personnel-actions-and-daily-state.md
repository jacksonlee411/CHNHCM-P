# CHNHCM-106 M04同日人事动作、日级状态与统计口径

登记信息：[registry.json](../governance/registry.json)。适用范围：M04同日转正、晋升、调动的动作事实与日级任职资料，及相关统计、页面和跨域处理边界。

2026-11-23 按用户对当前负责人的授权，T03 首笔直接入职采纳第 8 节限定的日级状态、办理动作和准确来源。其余场景保留为后续专项的设计输入。上游依据为[一致性合同](../architecture/target/03-consistency-contracts.md)、[DDD合同](../architecture/target/10-ddd-and-state-contracts.md)、[M04目标设计](../architecture/target/modules/m04.md)、[M09目标设计](../architecture/target/modules/m09.md)及[文档管理规范](../governance/014-document-management.md)。本文不修改这些现行合同，也不替代M02的规则和验证结果。

## 1 背景与问题

### 1.1 需要表达的业务事实

同一员工、同一业务日可以发生多个真实人事动作，并存在明确业务先后。下例为虚构样本，假设原资料为“研发部／试用中／P5”，2026年12月2日依次转正、晋升、调动；日期是示例业务日，不表示该日事实已经发生。

| 动作标识简写 | 事件 | 动作前资料 | 动作后资料 | 业务前序 |
| --- | --- | --- | --- | --- |
| A1 | 转正 | 研发部／试用中／P5 | 研发部／已转正／P5 | 无 |
| A2 | 晋升 | 研发部／已转正／P5 | 研发部／已转正／P6 | A1 |
| A3 | 调动 | 研发部／已转正／P6 | 产品部／已转正／P6 | A2 |

需要同时回答：员工在哪里晋升、当天有哪些事件及其先后、指定业务日适用什么任职资料、各类事件发生几次，以及职级/组织任职年限和试用期时长。

### 1.2 当前约束与范围

现行目标合同采用日级有效区间及独立修订，M04保留BusinessActionRecord及依赖，不采用EFFSEQ，不提供日内任职状态查询或计量。Go是唯一业务权威，Staffing协调关系、任职、资源、主选择及Outbox；M09薪酬核定、M10工资采用各自持有事实。

当前仓库M02已有不可变来源、记录修订及来源成员的存储机制，可作为实现参考；这不证明M04已有相同实现。上表三元组只用于说明可观察资料，不预先决定试用状态必然属于Assignment；转正的权威归属须在M04专项设计中明确，不能为展示方便在多个任职复制维护同一试用事实。

## 2 拟议决策

### 2.1 分别保存日级状态、真实动作和修订

日级状态回答“该日适用什么资料”，业务动作回答“发生了什么、修改了什么及其依据”，修订和来源版本回答“某次保存确认了什么”。三者分别维护身份与引用，不相互替代。

一个晋升办理可以包含部门调整；不能仅因两个字段变化就制造两个独立事件。确有独立转正、晋升、调动事实时，按第1.1节分别保存。事件数量不决定日期区间数量，动作也不必各自占一段日期区间。

“当日最终状态”指按所选来源解释该业务日的适用结果，不是等到日终才保存，也不表示当日中间状态具有独立日内有效期。

### 2.2 日级状态使用daterange

同一任职、同一确切来源内，状态区间采用[start,end)，不得重叠、不得为空。假设样本原起点为2026年9月2日，且无后继变化，当前日级任职视图为：

| valid_range | 部门 | 试用状态 | 职级 |
| --- | --- | --- | --- |
| [2026-09-02,2026-12-02) | 研发部 | 试用中 | P5 |
| [2026-12-02,) | 产品部 | 已转正 | P6 |

“研发部／已转正／P5”和“研发部／已转正／P6”保存在动作前后证据中，不制造[2026-12-02,2026-12-02)空区间。转正的效果不会因晋升终止，P6的效果不会因调动终止。

适用的约束范围是具体任职及来源，不能按personId禁止所有工作关系或任职同日存在。若试用事实最终归属Employment或合同，其区间和修订由所属根维护，上表只作组合读取结果。

### 2.3 用准确的前序引用表达业务先后

动作ID使用系统生成的稳定标识；A1、A2、A3只是阅读别名。UUID大小、recordedAt、数据库插入次序和来源版本号均不决定业务先后。

对于本例的明确业务链，A2引用A1的准确动作修订，A3引用A2的准确动作修订，从而得到“转正→晋升→调动”。这是显式业务顺序；不使用数字EFFSEQ不等于取消顺序，也不等于获得日内时间能力。

前序引用应满足：

- 目标真实存在，关联主体、目标根、业务日期及读取/办理范围符合专项合同；不能借前序引用连接无关人员。
- 不允许自指或环路。已声明承接的前后资料必须衔接；类型、原因及相关资格规则同时成立。
- 无明确先后、互不依赖的动作不强制串成全员链表；其展示顺序不参与业务计算。
- 同日同一字段的矛盾变化必须明确承接、更正或替代关系，不能按最后录入者覆盖；无法确定则拒绝并要求核对。

“前序动作”与“该动作成立的必要条件”须区分。A3在A2后发生，不自动意味着取消晋升就必须取消调动；是否可以保留调动取决于目标岗位、职级等资格及明确业务依据。必要依赖应单独可识别，不能从链表顺序推断。

### 2.4 动作和来源版本的存储职责

以下为拟议逻辑结构，不是可执行迁移或已冻结的物理表名：

| 数据 | 核心内容 | 约束与用途 |
| --- | --- | --- |
| 目标聚合根 | instanceId、稳定身份、当前来源引用 | 按Employment/Assignment等实际事实主责定位，不能创建全员工跨域大聚合 |
| 来源版本 | sourceId、所属根、前一来源、提交与记录时间 | 一次成功且有事实变化的保存形成完整可引用版本；不是PostgreSQL事务号或外部文件编号 |
| 日期型记录修订 | recordId、revisionId、valid_range、适用资料 | 不可变修订；资料字段由所属根拥有 |
| 来源成员 | sourceId、recordId及准确revisionId | 确定该来源采用的记录集合；区间冗余值必须与修订内容一致 |
| 真实动作及动作修订 | actionId、actionRevisionId、日期、类型/原因、明确修改、前后证据、决定/政策引用 | 同一目标同一日期可有多项动作；更正保留原动作身份和原件，不能重新计为新事件 |
| 来源与动作关联 | sourceId、actionId及准确动作修订、处理关系 | 历史查询能确定该版采用哪些有效动作、哪些已更正或不再适用；不能累计全部历史原件 |
| 业务顺序/依赖关系 | 前后准确动作引用及关系含义 | 表达先后或必要依赖；具体字段或关系表由专项设计决定 |

前后证据记录本动作涉及的准确资料及来源；实际写入采用明确修改面，不能拿整份旧快照覆盖其他独立动作。Go在写入时核验并持久化日级结果，查询不依赖前端合成状态。

数据库示意约束应位于来源成员集合，并包含如下作用域：

```sql
EXCLUDE USING gist (
    instance_id   WITH =,
    assignment_id WITH =,
    source_id     WITH =,
    valid_range   WITH &&
)
```

区间列同时要求NOT NULL、非空、有确定下界及[start,end)语义；来源、记录和修订有准确外键。该约束只防重叠，不保证连续覆盖、动作无环、容量或资格合法。不能在动作表设置“任职＋生效日唯一”，也不能在全部历史修订间排斥相同日期区间。[现有BU来源成员](../../db/migrations/00002_organization.sql)可供实现参考，但其每条记录单一操作类型不能直接充当M04多动作模型。

### 2.5 来源版本与保存流程

若分别保存，S1表示晋升保存后的资料版本，S2表示后续调动保存后的资料版本；示例中的转正已在更早版本成立，或与晋升在同次专用办理中保存。S2继续引用已有转正、晋升及新调动的准确动作版本，不重复创建已有动作。当前来源指向S2，S1保持可读。

S1中的“研发部／已转正／P6”只有在当时完整候选合法时才允许保存；不能先存非法中间结果，再等待另一动作修复。共同成立才合法的变化，应由有明确业务目的的专用办理一次提交，而非开放任意联合编排。

一次专用办理保存三项动作时，只需一个新来源及一份最终日级状态；不为每项动作强制创建一次提交。来源版本可包含过去、当天或未来日期，来源版本号不是同日生效序号。

保存由Staffing在单一短事务内完成：固定锁序取得目标根及受影响资源/主选择/经理守卫，核对预期来源、组织和政策版本、当前权限及必要决定，计算完整合法候选，保存动作、修订、成员、资源变化、内容绑定的幂等结果及Outbox，再以预期旧来源推进head。任一失败整笔回滚；结果未知按原请求查询，不创建新动作重试。

反序补录必须引用真实前后依据，不能依录入顺序安排业务顺序。来源过期不得自动重放；更正或取消须重新核验受影响动作、日级结果及后续日期段，保留无关独立事实、旧来源和原采用。必要依赖无法满足时拒绝不完整处置，不恢复整份旧快照。

### 2.6 事件次数与人员数量

事件统计读取指定来源中适用的准确动作修订，按稳定动作身份去重，再按业务日期、类型、所选组织口径及授权范围归集；不按保存次数、来源数、修订行数或daterange行数计数。

| 指标 | 本例预期 |
| --- | --- |
| 转正、晋升、调动次数 | 各1次，共3项真实事件 |
| 去重员工人数 | 1人，不因三项动作算3人 |
| 研发部发生的晋升次数 | 按动作发生组织口径为1次，不能由当日最终产品部倒推为产品部晋升 |

更正不增加事件次数；误登记作废、未生效安排取消按当前修正事实排除，历史原件仍保留。实际发生后再反向调动是另一真实事件，不能冲掉原发生次数。已经发生、已确认但未来生效、待核准等口径分别统计；统计期包含未来日期不表示计划已发生。历史报告按其确切来源和口径解释，不因当前更正静默改写旧报告。

### 2.7 职级、组织年限与试用期时长

年限以已核定的有效区间与统计窗口求交后累计，不按动作条数或来源数计算。所有开区间先截到有限的统计结束边界；按日含统计截止日时，将该日次日作为窗口右边界。年/月展示采用明确的日历规则，不默认天数除以365。

| 指标 | 默认日级口径 | 必须区分的情况 |
| --- | --- | --- |
| 当前职级任职年限 | 该职级连续有效区间 | 调动不重置P6起点；跨多个资料切片须合并连续同职级期间，返回P6后的连续年限与历次累计分别定义 |
| 两次晋升间隔 | 两项有效晋升动作的业务日期差 | 与当前职级任职年限不同；不能用保存时间计算 |
| 组织任职年限 | 相应组织任职区间 | 晋升不重置部门任职起点；重复进入同一组织按连续/累计口径分别处理 |
| 实际试用期天数 | 已确认实际试用开始日至实际转正生效日，[start,end) | 起点不自动等同人员首次入职日，不用计划转正日替代实际日；适用关系、延期或中断事实须有明确合同，本文不判断其法律有效性 |

本例12月2日归属产品部，P6自该日起适用；研发部P6中间阶段有动作证据但无独立日级覆盖。按本日级口径，其覆盖天数为0，不能将该0解释为真实停留0小时或从未在研发部晋升。相应报表应说明日级口径；需要精确日内时长的指标不能用该0代替未知。

人员在多关系、多任职或重叠区间中的连续/累计年限、按人员去重还是按任职累计，须由指标合同明确，不能直接相加重复天数。转正、年资与工资/社保待遇不是同一个指标，本文不制定法定试用期限或待遇计算公式。

### 2.8 页面、薪酬及权限边界

员工详情尚未设计。拟议沿用BU“选中节点后查看资料”的体验，但人事记录与薪酬记录采用同页不同页签，各自维护；当前不另建第三条综合时间轴。人事按日期分组，真实动作分别可选，展示动作发生组织、变化和原因；有明确顺序时可按链展示，没有顺序时稳定排序但不赋予业务先后。

“动作前后资料”与“查看日适用资料”必须有明确标签，不能点击晋升就把该日最终部门误改成研发部。UUID、来源编号及前序外键不作为常驻用户字段，也不要求用户拖拽排序。人事和薪酬只对真实关联提供授权后的跳转，不因同人同日自动匹配，不复制成两条可维护事实。

人事已生效、薪酬待办理、工资影响待核分别呈现。M04、M09、M10按所属域提交和采用，不扩为一个员工跨域大事务；需要协调的清单复用现有M20目标合同。能查看人员不推出能查看全部关系、薪酬金额或调薪事件存在性；查询、历史、事件统计、关联链接、缓存及导出均执行当前授权。

### 2.9 同日离职与入职的对象边界

若实际业务明确为从用人单位A交接至B，旧关系的“离职生效日”表示该日起不再在职，新关系从同日起入职，则旧关系为[原起点,交接日)，新关系为[交接日,新结束边界)，不存在日级空档或重叠。若来源的离职日期表示最后在职日，必须按来源合同明确转换，不能混用两种含义。

新旧工作关系及任职分别保留身份，Person保持；BU不变不等于用人单位未变，合同及法律关系是否终结仍按真实事实判断，不能由组织字段变化自动推定。同日两项动作属于不同关系时，不受“同一对象同日一份状态”误拦截。连续交接由明确的Staffing专用业务协调新旧关系、资源和主选择，不要求通用联合编辑器；这不扩大本文为解除、新聘或合同办理的完整规格。

### 2.10 明确不具备的能力

本方案不能回答“当天10点在哪个部门/职级”，也不能计算同日中间阶段实际工作几小时。前序引用、EFFSEQ、recordedAt或修订号都不能凭空产生真实时长。

若业务要求精确日内任职及计量，须另立决策：采集可信的业务生效时刻与时区、考虑tstzrange等有效时间模型，联动资源容量、主选择、工时和工资归属，并重新验证。增加同日逻辑序号可以表达顺序，但仍不等于获得真实时长；该扩展不是本草案已采纳能力。

## 3 备选方案与取舍

| 方案 | 满足的需求 | 成本与局限 | 拟议选择 |
| --- | --- | --- | --- |
| 日期＋EFFSEQ的多条任职记录 | 表达同日多动作及逻辑先后 | 需规定消费者如何选用同日记录、撤回及补录语义；序号不提供真实时长 | 当前日级目标不引入；作为成熟替代路线保留比较，不宣称其天然不可靠 |
| 日级状态＋真实动作＋准确前序/依赖 | 日级读取、动作背景和次数、日期口径年限 | 必须实现动作修订、冲突/依赖、更正和来源关联；不能计量日内阶段 | 本文推荐提请评审 |
| 每次保存只覆盖一份任职资料 | 实现简单、当前资料易读 | 丢失同日真实动作、发生组织及原采用依据，无法满足历史和统计 | 不采用 |
| 仅存动作，读取时通用重放全部历史 | 可以记录动作 | 引入通用事件解释、政策重放和查询复杂度，超出本项目本次范围 | 不采用；Go写入时形成明确日级事实 |
| 真实生效时刻＋时间区间 | 精确日内状态及经核定的时长 | 需要可信时间、时区及全部消费者的对应约束，当前需求及实现尚未冻结 | 有实际需求时另立决策 |

不采用EFFSEQ不意味着天然更简单或自动鲁棒；本方案将复杂度集中在明确动作、依赖和日级候选校验，只有相关反例验证后才能声明实现满足要求。

## 4 影响与验证

### 4.1 业务与体验影响

真实转正、晋升和调动可同日留痕，用户不填写技术序号。状态、动作及办理完成分开；只有符合日级口径的指标可以直接使用本模型。草案不增加通用联合编辑器，也不将M02的“日期已占用即拒绝新增记录”机械应用于M04动作。

### 4.2 存储、接口与运行影响

后续专项规格须冻结动作权威归属、记录/修订/来源成员及动作关联、前序与必要依赖、读取与更正/取消协议、并发和幂等语义，以及Go与数据库各自守卫。不能以本文示意约束替代完整迁移、外键、应用角色写权限或事务实现。

本轮不新增表、迁移、API、页面或运行数据，不重建既有数据库；遵循[025全新实施策略](025-greenfield-implementation-policy.md)，不预建旧格式兼容，也不抹除当前模型业务历史。本文不制定备份、恢复或生产能力的新验收结论。

### 4.3 后续必须证明的反例

以下均为后续验收预期，本草案未执行Go、数据库、API或浏览器业务验证：

| 场景 | 必须证明的结果 |
| --- | --- |
| 同日转正→晋升→调动 | 准确保存研发部转正和晋升证据，最终为产品部／已转正／P6；次数各1，人数1 |
| 只有合法组合才能保存 | 任一单项导致岗位/职级非法时不生成成功中间来源；专用共同办理合法后整笔保存 |
| UUID顺序、登记时间与业务顺序不同 | 业务链仍按准确前序解释，不能按UUID或recordedAt重排 |
| 独立动作反序补录及同字段冲突 | 独立变化在合法条件下结果一致；矛盾变化要求明确承接/更正，不能最后写入者覆盖 |
| 无效引用、自指、环路和跨对象越权 | 安全拒绝，不泄露无权目标，不产生部分状态 |
| 两请求基于同一旧来源并发 | 过期依据被拒绝，无丢失更新或非法重复占用 |
| 任一写阶段失败、提交结果未知及重试 | 事务完整回滚或按原提交查回；动作、资源和事件不重复 |
| 只取消晋升 | 独立合法调动保留；存在必要依赖时拒绝不完整处置，不能整份恢复旧快照 |
| 来源切换和历史统计 | 旧来源维持原答案；更正、取消及多个来源引用不重复计数；真实反向调动另计一次 |
| 日期区间与年限 | 不重叠、非空；必要覆盖无空洞；同职级跨切片连续合并，统计窗口/闰日/截止日口径正确 |
| 同日中间阶段与未知时间 | 能查动作后证据，不伪造日内适用区间或小时数；日级0天不冒充真实0小时 |
| 多关系、多任职和权限变更 | 指标按明确粒度归集，避免重复天数；历史、摘要、计数和关联链接不扩大当前权限 |
| 人事成功而薪酬或工资步骤未完成 | 分步状态准确，重试不重新晋升；未形成薪酬事实不冒充已生效调薪 |

### 4.4 评审与完成边界

草案阶段已完成文档登记、格式和链接检查。首笔入职的采纳及验收范围见第 8 节；后续多动作、薪酬、工时与统计由相应专项评审和实测。现有M02或源系统验证不计入上述反例通过。

## 7 T02 对六项问题的处置

第 6 节的采纳决定由受影响维护者在 M04 开工前形成。首批确认首次入职采用日级状态、真实动作和原来源。其余事项在决定中明确所属专项，随实际接入验证。每笔入职只保存该动作真实的依据和系统已有的前后版本，日内时间未知时可按业务日办理。[401 业务规则](../specs/m04/401-direct-hire-requirements.md#m04-br-008) · [403 技术合同](../specs/m04/403-hire-technical-contract.md#hire-actions) · [400 分批准入](../plans/400-hire-readiness.md#hire-gates)

| 第 6 节问题 | T02 方案采用的口径 | 责任与实际关闭点 |
| --- | --- | --- |
| 查询及计量粒度 | 每个任职、每份来源在一个业务日有一份适用状态。当天可有多项事实。同日中间阶段只解释事件发生背景，不能给出日内工作小时。 | 人事、工时及工资维护者确认首批无日内状态诉求。需要小时归属的业务另立时间模型。 |
