# CHNHCM-009 M02 大陆组织角色与工作关系术语

登记信息：[registry.json](../governance/registry.json)。适用范围：M02 及其直接关联的 M04 工作关系、M14 付款主体、概念映射和设计图。CHNHCM-010—013 仅承接本批 M02 BU 后台维护，正文入口见[规格入口](../specs/README.md)；其他组织对象及 M04/M14 的具体业务、物理设计分别由后续所属领域专项规格承接，待立项明确文档编号。

## 1 背景与适用问题

大陆人事办理需要区分组织身份、允许用途、实际工作关系和资金责任。来源英文概念与中文产品译名不能直接确定全部法律或业务角色；本决策明确展示用语和事实归属，同时保留已有英文身份、来源及历史引用。

外部资料的核对范围来自 2026-10-30 原术语修订记录。本次按 014 统一章节和维护入口，保留原决定及其反例，没有重新核验政策时效或 Oracle 最新版本。

## 2 决定与用户任务

大陆人事办理、劳动关系与派遣管理使用“用人单位”作为首选中文；原 `m02-legal-employer` ID、英文 `Legal Employer` 及锚点保留。“法定雇主”“合法雇主”只作为 Oracle 对照及检索别名，不用别名推断法律关系。工作关系继续是上位系统概念。

| 概念 | 首选中文与边界 | 事实主责 |
| --- | --- | --- |
| Legal Entity | 法律实体；法律身份与具体允许用途分开，不能一概限定为独立法人公司 | M02 组织身份和用途资格 |
| Legal Employer 的大陆劳动关系语境 | 用人单位；与劳动者建立劳动关系并承担相应用人责任的组织主体，符合条件的分支机构可作为用人单位 | M02 提供身份及允许用途；M04 记录具体关系角色与依据 |
| 派遣接收方 | 用工单位；与派遣单位分别识别，不能仅按工作地点认定 | M02 提供身份和允许用途；M04 记录派遣/实际用工事实 |
| 非劳动或非工作关联中的组织 | 关联单位，或按事实使用委托方、服务接收方等具体角色名 | M04 按实际关系类型记录 |
| 工资资金实际付出方 | 付款主体；与用人单位、用工单位、扣缴义务人分别确定 | M14 付款运营事实；税务和参缴仍归 M11/M12 |

人员类型与组织责任是两个维度。“员工/非员工”是系统分类，不能替代劳动关系性质认定；不得依据 `Legal Employer` 字段存在、人员分类、合同签字、工作地点或付款账户之一自动推导全部责任。

## 3 工作关系与 entityId

`Work Relationship` 定义为人与组织之间按类型记录的一段系统关系，可承载劳动关系、非劳动工作关系及非工作关联。`Employment` 保留英文和身份，中文明确为“工作关系记录”，旧名“用工关系”保留为检索别名。

`Employment.entityId` 是本段关系关联的 M02 组织身份引用，不能仅凭此字段认定用人、用工、付款或扣缴角色。建立关系时记录实际关系性质及依据：劳动关系明确用人单位，派遣事实另外记录派遣单位和接收方，非劳动关联使用对应角色。实际用工方可以随具体派遣/任职事实变化，不强制压成工作关系上的单一永恒角色；这些人员关系的物理字段和事务设计由后续 M04 专项规格承接，待立项明确文档编号，不交给本批 M02 的 CHNHCM-013。

M02 声明组织可承担的用途及资格，不据此宣告某人与该单位已建立劳动关系；具体人员关系由 M04 维护。M11/M12/M14 通过自己的合同确定扣缴、参缴和付款责任，M04 不接管这些运营账户或资金事实。用人单位变化与仅用工地点、接收方变化分别办理，不能统一当作“换公司”。

工作关系包含非工作关联时，任职基数也须按关系类型解释：实际入职或派驻 Hire 仍原子创建首任职；明确的非工作关联由 M04 受控 RegisterAssociation 建立，可只有关系，按真实关联登记，无须补造职务或任职占编。非工作关联默认不要求主任职；某用途显式要求时，必须存在真实合格目标，否则拒绝。此取舍不把所有非劳动/Contingent 关系改成无任职，也不把 Oracle 的任职基数直接当作本项目的法律结论。

## 4 分支机构与签约边界

本项目的法律实体模型不把独立法人资格设为所有组织责任的统一前提。分支机构使用可区分的组织身份，保留设立单位、登记以及相关资格依据；普通部门或 BU 不因名称相同而自动具有用人资格。

《劳动合同法实施条例》第三条列明合伙组织、基金会等主体；第四条区分取得营业执照或登记证书的分支机构，以及未取得证照但受委托订约的情形。委托签约应记录代理/受托事实，不能由签字主体自动认定其独立承担用人责任。[实施条例](https://xzfg.moj.gov.cn/front/law/detail?LawID=284)

劳动关系建立时间与书面合同订立时间分别保存；不能把“尚未签书面合同”当成劳动关系必定不存在，也不能只以合同落款确定用人单位。[劳动合同法第七、十条](https://fgk.chinatax.gov.cn/zcfgk/c100009/c5193025/content.html)

## 5 备选、取舍与影响

以下归纳原决定中已排除的解释及采用代价，不补造新的选型或外部核验。

| 原决定中的解释选择 | 取舍及影响 |
| --- | --- |
| 将“法定雇主”“合法雇主”直接作为所有关系的统一名称 | 保留为 Oracle 对照及检索别名；大陆劳动关系使用“用人单位”，其他关系按实际性质命名，需维护别名与稳定 ID 的映射 |
| 用一个关联组织字段推导用人、用工、付款和税费角色 | 保留 `Employment.entityId` 的组织引用含义，各源域分别保存具体事实及依据；需要公开合同与跨域核对，不能靠字段存在自动完成责任判断 |
| 以独立法人资格、合同签字或统一任职基数简化全部关系 | 保留分支资格、委托、实际用工及非工作关联的区别；规格和验证必须覆盖相应反例，不能以占位任职或单一人员分类替代认定 |

## 6 Oracle 对照与原核对范围

原术语修订于 2026-10-30 核对官方 [HCM Readiness](https://docs.oracle.com/en/cloud/saas/readiness/hcm.html) 的 Human Resources 26D 入口和[当时书目入口](https://docs.oracle.com/en/cloud/saas/human-resources/books.html)。概念页使用该书目连接的累计文档渠道；未把失败的猜测式 `/26d/` 地址当作版本依据。

Oracle 将 Legal Employer 记录在工作关系层；其工作关系同时覆盖 Employee、Contingent Worker 和 Nonworker 等产品类型。因此，Oracle 关联字段到中国法律角色需要按事实解释，本项目的大陆用语不表示二者全语境等价。[Legal Employer](https://docs.oracle.com/en/cloud/saas/human-resources/faigh/what-s-a-legal-employer.html)、[Work Relationships](https://docs.oracle.com/en/cloud/saas/human-resources/fawhr/work-relationships.html)

该次核对的 Oracle 简中 Assignments 页面同时出现“合法雇主”和“法定雇主”。此证据支持保留检索别名，不构成统一中文界面译名的证明。[简中资料](https://docs.oracle.com/zh-cn/cloud/saas/human-resources/fawhr/assignments.html)

## 7 设计反例与验收要求

| 场景 | 必须保持的结果 |
| --- | --- |
| A 派遣公司与人员建立劳动关系，在 B 公司工作；B 系统标为非本单位员工 | A 是用人单位、B 是用工单位；B 的分类不改变 A/B 的法律角色，派遣记录分别引用两方 |
| C 使用其机构付款账户实际出款；另有操作方受托经办 | 资金付款主体 C 不自动成为用人单位或扣缴义务人；若 C 仅操作 A 的账户，不把 C 自动记为资金付款主体，付款与经办角色分别记录 |
| 符合条件的已登记分支机构承担用人角色 | 不因缺少独立法人资格被模型一律排除，保存资格依据和组织身份 |
| 未取得相应证照的分支机构受委托签约 | 记录委托和签约角色，不把签字单位直接升级为用人单位 |
| 已实际用工，书面合同稍后订立 | 关系起点与签约时间分别记录，不以合同文件缺失否定已确认的关系事实 |
| 已确认为非劳动关系的服务，或非工作关联 | 按事实命名关联单位与角色，不强制填“用人单位”；退休、志愿者等类别本身不替代个案认定 |
| 明确的非工作关联只有关系；另有实际工作的 Contingent 关系 | 前者允许没有任职，后者按工作及关系类型保留任职要求；required而缺少真实目标时拒绝，不制造占位记录 |
| 查询旧版本、采用记录或检索旧词 | 保留组织/关系稳定 ID、英文映射和历史引用；检索旧别名可定位新词条，不重写原冻结来源 |

以上是模型反例与后续实现验收要求。原术语修订的验证范围为文档语义、一致性、生成及图形，不代表业务场景已实现。保留来源包和初始采用 SHA；本仓修订另行记录，不回写 FSCR，不把原范围复核或本次格式评审扩张为 R25 后全部增量验证完成。
