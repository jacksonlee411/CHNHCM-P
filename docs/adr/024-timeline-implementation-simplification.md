这些要求增加了权限限制、执行路径和前置工作。本次以既有业务不变量及可观察风险决定实现和验证范围；不缩减已采纳的追溯新增、已生效删除/改日、有限联合、首条补全及分类纠错。

## 2 决策

### 2.1 结果读取与业务执行分权

已持久化终态的查回和同内容精确重试属于结果读取：核验提交所属实例/主体、当前对象/历史读取及输出字段读权，不要求重新具备原联合、子项动作或字段写权。原请求声明字段继续用于输入绑定、首次执行授权及审计。缺少终态且需要实际执行的重试必须完整核验当前写权限；not_applied仍按本人提交身份处理。对象或历史读权丢失时不返回受限内容，字段读权收窄时裁剪输出；不使用原allow替代当前读取授权。

### 2.2 同事务拒绝与显式查回

保留一个外层授权/提交身份锁及整笔业务savepoint。可恢复业务拒绝在原锁内撤销全部业务写入，再保存拒绝终态及安全诊断；COMMIT确定成功才返回确定拒绝。外层事务失效、取消或提交未知时保留待确认，由用户的显式resolve查回或在同锁确认无终态后封闭。

维护命令不在整笔事务结束后另起事务补写rejected，也不新增失败终结器。原请求、精确重试和resolve继续共享提交身份锁，已有终态优先；一次尝试失败不证明整个身份未保存。回滚清理只负责释放资源，不写终态、不重开业务预算。

### 2.3 按风险分配验证层次

保留023的257个案例编号、独立业务预期和参数矩阵。每例指定一个主要验证层，必要时附补充层及其独有断言。Go执行日期、状态、权限选择及项排列的完整规则矩阵；真实DB验证持久事实、约束和并发；API验证协议、授权及结果恢复；浏览器验证正常菜单关键旅程和特有交互。当前模型初始化及容量分别有专项验证；025退役的四项旧版本案例保留编号但不执行、不计通过。

补充层不自动重跑主要层的全部参数。案例表和执行约定明确代表输入及跨例关联；相同基线的一份真实证据可覆盖其实际验证的多个断言，未观测层次不推导通过。案例只有主要层和明确要求的补充断言通过才能关闭，完整业务切片仍须有真实DB/API及正常菜单证据。

### 2.4 本地升级要求的后续替代

本节原决定采用停服排空、前向升级、一次运行密码轮换及匹配程序检查，原制品清单等后置。用户随后明确全新实施不考虑向后兼容；这些旧库/旧程序要求已由[025](025-greenfield-implementation-policy.md)替代，不再作为M02前置或预设交付待办。

现按025直接安装当前模型，仅保留当前程序/存储匹配与严格结果解码。原决定和理由保存在[024受测输入快照](https://github.com/jacksonlee411/CHNHCM/blob/061d28105966bd10eb1e3b0032cf2976a6448de4/docs/verification/data/025-before-greenfield-policy.zip)，原验证报告保持；本文件其余第2.1—2.3、2.5节继续适用。

### 2.5 以取消延迟验证执行预算

保留整体截止时间、正文及SQL超时、有界回滚清理和扫描批次取消检查。排序先使用标准库实现，在进入和结束处检查取消；不预先要求自定义可取消排序。T01测量代表长当前时间线，T07测量承载边界，记录取消发起至本地停止的最大延迟及清理/DB锁释放观测。

013定义初始验收预算。若测量超出该预算，再针对实际瓶颈调整算法；不能只检查context存在，或以标准库不可中断为由放任延迟。技术超限仍不得拆笔、截断候选或跳过真实引用校验。
