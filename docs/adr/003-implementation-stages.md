# CHNHCM-003 全新实施的阶段与完成口径

登记信息：[registry.json](../governance/registry.json)。适用范围：从独立建仓到首个 M02 切片及后续交付能力的推进与验收口径。技术选择由 [002](002-technology-stack.md) 持有；当前切片边界见 [007](../architecture/007-m02-entry.md)。

## 1 背景与阶段选择

本仓采用用户已确定的全新 Go 内核路线，需要把来源资产保留、规格采纳、业务实现和实际验收分别记录。先建立自足工程和来源基线，再用选定的 M02 用户任务连接领域、存储、API 与正常页面，逐步扩展范围。

CubeBox 的 217/U1/U2 属于来源项目阶段治理。本仓不继承它们作为开工门槛，旧原型完成记录也不成为本仓验收。采用技术方向不等于后续所有业务实施已获范围确认。

## 2 阶段输入、交付与退出证据

下表持有阶段口径。具体任务和受影响场景由相应计划/规格维护，实际执行结果由验证报告记录，不在此建立第二份产品进度台账。

| 阶段 | 输入与范围 | 交付及退出证据 | 维护与交接 |
| --- | --- | --- | --- |
| 建仓 | 独立工程、来源基线及协作规则 | 独立历史、可构建骨架、来源/资产登记与导航检查；记录见 [001](../archive/plans/001-repository-bootstrap.md) 和[建仓验证](../verification/bootstrap.md) | Repository maintainer 交接未结事项到 008 |
| M02 规格 | 007、目标设计、三类来源资产及可见待决项 | 010 明确首批范围；011—013 连通用户任务、规则、页面与技术合同，记录审阅范围和未决影响 | [008](../archive/plans/008-next-steps.md) 组织编写；Organization lead 协调受影响维护者 |
| M02 垂直实现 | 选定范围内的业务/页面/技术合同已采纳；直接影响本任务的关键待决项已解决，暂缓项及其依赖任务已移出本次实现范围 | 同批连接 Go 领域、事务/数据库、API、正常菜单页面与新模型样本；逐项记录实际结果及异常/历史覆盖 | 010 持有任务及范围，011—013 持有合同；领域实现者交付对应验证证据 |
| M02 验收 | 可复现的切片、独立预期及明确验收条件 | 正常入口、异常/撤销/更正/历史，并发/鉴权/数据库约束及来源追溯按实际切片实测；失败或未覆盖项有明确结论与去向 | 010 明确验收角色，验证报告关联 011—013；有证据后推进后续领域 |
| 交付能力 | 已明确的客户部署、升级/恢复、离线与生产安全要求 | 对本次交付方式和支持范围实测安装、升级、恢复等合同，保存失败处理与限制 | 另行建立相应计划和运行指南；未实现能力不提前编写成可执行指南 |

010—013 的路径及正文存在情况见[规格入口](../specs/README.md)和登记表。阶段表不要求先完成全产品、全地域政策或所有来源增量；010 应区分影响当前切片的依赖与不在本次范围的事项。关键业务问题不能以空目录、mock 或技术占位代替关闭。

全项目现阶段的业务由具备相应权限的管理员直接办理。按日维护的记录一次保存，按指定生效日期采用，其他业务按所属对象的既定生效条件执行。本阶段无人工复核或双人审批流程。各模块按同一规则设计页面、命令和验收场景。[管理员维护与业务生效](213-administrator-maintenance-and-effectivity.md)

## 3 选择的影响与代价

采用分范围的垂直切片，需要先把旧页面、旧测试及原状态中的隐含预期提炼成独立场景，再连接新内核；这增加规格和资产追踪工作，但能明确正常业务事实、例外及历史保护的责任。旧流程继续提供来源线索，不能直接作为新模型的完成证明。

将来源项目阶段原样复制，或把目录、健康接口及页面存在作为业务完成判据，均不能表达本仓所选交付范围；本仓按上表和实际场景证据推进。这是既有实施路线的明确化，没有新增全域开工门槛。

## 4 完成与证据规则

文档状态、计划执行进度、资产采用状态和验证结果按 [014](../governance/014-document-management.md) 分开管理；资产登记、提取、实现、验证按 [006](../assets/006-preservation-contract.md)。未开始、待接线、范围通过及整项通过应分开。

旧 store/transition 驱动不能直接证明新内核；新代码和新测试也不能共享一个未经审查的错误业务假设。验收必须说明角色、正常入口、前置、业务事实和页面结果、异常及历史保护，保留不在范围内的事项。

新仓运行只使用当前模型。按[025](025-greenfield-implementation-policy.md)，不承担旧开发实现的数据库、协议或二进制向后兼容；可同步整理尚未对外交付的代码、迁移及合成样本，在隔离空库验证。开发提交或合并不构成正式发布。当前模型内的业务历史、版本及采用证据仍须保护；已有持久库和历史报告不因本决定被自动清除。实际客户数据升级需求在交付范围明确后另行设计。

<a id="development-environment-cleanup"></a>
### 4.1 开发与测试环境资源收尾

本节是各模块开发、测试及阶段交付的通用要求，由创建资源的任务执行者负责落实。新建隔离环境前，必须盘点本任务已有的 profile、容器及配套进程，明确用途、所属工作树、端口、卷和保留方式；不得以“保留数据”为由让已结束的历史验证环境持续运行。切换验证批次、容量测量结束、任务完成或取消时必须执行收尾，不等到下次资源不足再集中处理。

每个工作树通常保留一个当前模型的开发/手工验证环境；同一模型内普通代码修改复用该环境，空库、数据独占或模型变化才新建。自动浏览器验收默认使用创建时明确可丢弃的独占临时环境，结束后回收容器、网络和卷。需复查故障、容量或特定现场时才单独留存；保存报告、源码及业务历史不意味着每个批次永久保存一套运行环境。已有持久环境不自动变为临时环境，不按存活天数自动删除。

| 资源类别 | 默认收尾 | 保留条件 |
| --- | --- | --- |
| 持久开发或手工验证 profile | 停止已不再使用的 Web/API 等配套进程和容器，保留容器、数据卷及恢复所需配置/凭据/原程序或可重建来源 | 当前用户验证、其他进行中任务或确需继续运行的环境，记录用途、责任人或角色及复查节点；只需留证的数据停机保存 |
| 创建时已明确可丢弃的浏览器验收、Testcontainers、CI等临时资源 | 通过框架清理钩子或 finally/always 路径停止并回收本任务临时容器、网络和卷 | 确需保留失败现场时先保存安全诊断，记录保留范围与后续处置；不能默认无限期保留所有失败环境 |

执行时必须满足以下要求：

1. 核对 Compose 项目/服务标签、配置文件所属工作树、profile、容器ID、端口和卷挂载；配套进程核对 PID、启动标记、工作目录及进程组。结合任务是否结束、当前依赖和活动请求判断可否停止，不能仅凭运行时间长或数据库连接空闲认定无人使用。归属不明或存在活动工作时保留现场，确认具体归属后再处理；其他工作树、仓库或共享环境只有已明确纳入本次清理范围且归属核对通过时才处理。
2. 优先使用任务的受控启停入口。停止持久 profile 不包含删除卷、重建库或迁移授权；不得使用全局 prune、全容器批量停止或模糊进程匹配代替归属核验。已明确为可丢弃且由本测试独占的临时资源，按既定清理范围回收，无需逐次另行确认。不得从一般停止操作推定删除持久数据的权限。
3. 资源分配后立即登记清理，创建返回错误但已分配部分资源时也须定向收尾。正常结束、断言失败、超时及可处理取消均须进入资源清理路径；先终止本任务测试客户端/配套应用，再停止数据库。强制终止留下的资源须在下一次任务开始或交接时核查。清理失败须单独记录并继续处理，不得把遗留运行资源记为已清理，也不改变原业务检查结论。
4. 停止前保存必要的非敏感诊断和原始证据；旧存储若仍需按原程序复现，先确认匹配的程序文件或构建来源及启动信息可恢复。不得为停止或恢复而改写历史、补造配置、将新程序接入旧库或清空数据。凭据保持仓外保护，不进入日志、截图、清理清单或仓库。
5. 收尾后核对目标容器状态、配套进程/端口及卷保留或临时资源回收结果，验证所保留入口仍可用。交付记录须列明停止/回收对象、仍在运行的对象及理由、数据保留位置与恢复依据、核验结果和未解决事项。原有容器总数可包含其他任务，不能以全机容器数量归零作为完成条件。

本地已实现的启停与核验步骤由[017](../guides/017-local-bu-development.md#local-runtime-cleanup)持有；实施计划和验证报告按相应[模板](../templates/README.md)记录收尾。上述要求只管理开发测试资源，不新增业务失败终结器、兼容层或生产运维平台。

宿主机统一配置不与Windows/WSL、VPN及虚拟机路由重叠的Docker地址池，开发环境按小网段自动分配；不为每个验收批次手工指定网段。持久环境的`stop`保留网络，因此仅停机不能代替临时环境回收。使用Docker/Compose及现有脚本即可，不建设独立IP分配或环境归档平台；实际配置与验证见[本次记录](../verification/017-docker-runtime-lifecycle.md)。

### 4.2 开发完成后更新手工验收环境

每次完成影响可运行产品的开发并通过相应验证后，负责该项开发的工作树在交付前，将已验证的版本更新到本工作树负责、供用户手工验收的环境。常规更新按本规则执行，无需用户逐次提出。用户明确要求暂留某个版本时，按其要求办理，并在交接中说明该地址的实际版本。纯文档调整无需重启服务。

1. 按交接记录和实际运行归属核对工作树、profile、地址、数据库及数据卷。用户已有验收链接时沿用原地址。其他工作树负责的环境由其责任方办理。首次交付还没有验收入口时，按运行指南建立并交接本工作树的环境。
2. 按实际变更更新页面、服务及所需数据库迁移。更新持久环境前保留可恢复的原构建及相关数据，保护已有业务档案、历史和权限。
3. 更新后从用户实际使用的地址，以相应业务角色走正常菜单核对改动。有指定链接或旧档案时，一并打开复查。记录地址、运行版本、业务结果及保留责任。更新或复查失败时，交接中写明该地址实际可用的版本和待解决事项。

此规则适用于本地手工验收环境。远程合并及正式发布继续遵循现行交付规定。[本地运行指南](../guides/017-local-bu-development.md#local-runtime-cleanup) · [验证与发布](../governance/137-actions-and-validation.md)

### 4.3 手工验收的业务样本

按经办人和受限读者实际能完成的任务准备少量合成事实。交接写明服务端业务日、入口、角色、可辨认的样本、预期结果，以及到期后需要复查的日期。样本数量以能区分各项预期为准。大数据量、并发和性能指标按对象容量合同另测。

| 任务 | 样本如何体现差异 |
| --- | --- |
| 查询当前业务 | 主流程应有在验收日已生效且可办理或查阅的记录。人员名录应有首聘已开始且当天仍在任的人员，并保留适量未来首聘以核对「尚未生效」。专查未来、离职或历史的任务按各自日期另设样本。主数据首次新建的默认日期沿用 [202](202-master-data-default-effective-date.md)。 |
| 在层级中定位 | 深层定位场景推荐准备五级业务部门，从实际业务根计第一级，「全部」是查询入口。安排两个能查出不同记录的同级分支。右表按部门归属查业务记录时，再留一条祖先无直属记录、叶子有记录的路径，验证直属和含下级的差别。五级是手工示例深度，产品容量与实际可浏览深度按对象合同验证。 |
| 看清行、字段与权限 | 用同一组事实给不同角色查。人员名录可用一人多任职、仅有档案及按职务／按岗位管理的任职，事先列明每个范围的行数、去重人数和可见字段。[人员名录联验](../specs/m01/502-person-directory-interactions.md#m01-directory-scope-acceptance) |

持久环境通过正式业务入口补充样本，记录业务身份及原办理回执，使中断后可接续、重跑可查回同一结果。保留原档案、日期、修订和授权范围，新增授权限于样本办理所需。样本跨过有效期后，先按新的业务日复核预期，再按需要追加业务事实。[持久环境交接](#acceptance-environment-update) · [历史保留](025-greenfield-implementation-policy.md#single-current-implementation)
