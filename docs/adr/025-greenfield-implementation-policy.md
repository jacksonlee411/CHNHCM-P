# CHNHCM-025 全新实施与当前模型交付策略

登记信息：[registry.json](../governance/registry.json)。适用范围：全仓开发实施及 M02 首批交付的历史决策。依据用户 2026-11-01 的全新实施决定及 2026-11-27 对唯一性和旧接口退出规则的采纳，承接[003](003-implementation-stages.md)、[024](024-timeline-implementation-simplification.md)及根目录[工作约定](../../AGENTS.md)。

## 1 背景与问题

2026-11-01 首批决策时只接通BU创建/查询，记录维护尚未实施。此前方案仍要求从00004升级、保留旧CREATE空元数据及摘要、并存两代事件格式，并通过停服排空及密码轮换隔离旧程序。这些要求把开发期实现当成已对外承诺的存量版本，增加了与本批用户任务无关的分支和验证。

用户明确取消这些向后兼容义务。已有代码可按业务价值复用或直接重构，已有通过报告只证明其受测基线；二者都不冻结下一批的内部模型和接口。

## 2 决策

<a id="single-current-implementation"></a>

### 2.1 只交付一套当前模型

同一项业务事实必须由一个领域负责，对象合同写明怎样识别同一个业务对象。同一业务动作由该领域的一套 Go 规则判定和写入。页面、导入、后台作业和跨域调用共用该操作。办理、查看历史、查回提交结果各有用途，可以分别提供入口。[领域与数据归属](../architecture/004-repository-layout.md#3-分层与跨域合同)

并行开发先核对主线和在途工作。多个分支涉及同一事实的身份、写入规则或接口时，必须先确定负责分支、受影响的调用方、迁移编号（如需）和合入次序。由一个分支交付共同实现，其他分支在此基础上扩展。[并行开发约定](../governance/005-branches-and-documents.md#6-并行开发与跨主机协作)

替换接口应在同次交付撤下旧路由及公开声明，同步更新受影响的 Go 实现、数据库、sqlc、OpenAPI、生成客户端、消息、页面、后台作业及测试。不得为旧程序保留字段别名、双写或旧算法回退。

仅当有效交付约定明确要求原接口，或已核实某个在用调用方无法同批切换时，才可暂留旧接口。对应合同或计划必须写明调用方或约定、暂留原因、允许的操作、切换负责人、退出条件和复查日期。只供查回的旧写接口必须核对原主体、提交号和内容，按当前权限返回已记录的结果，拒绝新提交和同号改内容。退出条件满足后撤下路由及其公开声明，验证调用方已切换。

开发期允许整理未对外交付的迁移基线，在隔离空库安装当前结构。只有旧软件才使用的字段、协议解码、事件格式及二进制可以退役。已办理业务的修订、来源和结果按第 2.2 节保护。请求、诊断和事件各采用一个明确的当前格式标识，严格拒绝损坏或不符合当前合同的内容，不建设多版本转换层。

M02 的创建、更正和固定启停操作共用资料、修订、影响及提交结果规则。业务单元涉及两条记录的一次办理只保留“插入停用与重新启用”和“删除停用与重新启用”。首条先更正，需保留原日期资料时再新增一条，每步独立保存。分类纠错在单条更正中进行。[固定启停](../specs/m02/011-m02-business-requirements.md#m02-br-019) · [首条维护](../specs/m02/011-m02-business-requirements.md#m02-br-020) · [分类更正](../specs/m02/011-m02-business-requirements.md#m02-br-021)

记录身份只承载稳定归属，日期和业务分类由所选来源修订解释；首次登记信息从首份不可变修订追溯，不为旧表保留initial_effective_date或initial_kind。

### 2.2 保留当前业务历史与失败保护

同一当前模型内，旧sourceVersion、修订、原分类/日期、采用和已终结提交结果仍不可改写。原子提交、当前授权、显式结果查回、安全诊断及有界执行继续实施。取消旧软件版本兼容不影响用户查看既有业务历史，也不允许用当前头伪造原结果。

原提交人必须能在当前权限范围内，通过现行入口凭原提交号查回当次结果。不得重新办理或根据最新值重算原结果。存储结构变更涉及须保留的持久数据时，由 upgrader 前向迁移，核对迁移前后的来源、修订、原采用和回执。已正式交付的迁移不得原地改写。[SQL 与迁移约束](../architecture/004-repository-layout.md#4-sql-与迁移约束)

产品明确某项用途及其历史可丢弃时，前向迁移在同一事务中直接删除其专属数据和退役结构。共享表按用途及对象身份清理，逐项核对保留的来源、版本、事件和回执。2026-11-23 的岗位职能协作退役按此执行。[岗位合同](../specs/m03/312-position-contract.md) · [升级对账](../verification/315-department-quota-allocation.md#quota-start-gates)

开发/测试使用隔离的合成样本。本文不授权清空现有持久库、共享环境或历史证据；新实现优先使用新的任务数据库。已有报告、来源资产和本次修改前的024输入保留，不能用新模型的测试替换历史失败或宣称旧库升级已通过。

### 2.3 2026-11-01 首批实施安排（历史）

以下四项记录当时如何安排 T01—T08，供追溯旧计划及证据。现行业务操作以第 2.1 节所引合同为准。[首批计划](../archive/plans/010-m02-scope-and-plan.md)

1. T01—T03 一起交付 Go 候选模型、存储和页面，先支持新增与普通更正。
2. T04 交付停用、重新启用和相应的时间线校验。
3. T05、T06、T08 原定复用删除、改日和分类规则，曾安排联合编辑、首条补全及多目标分类纠错。这些旧入口后来退出，现行操作见第 2.1 节。
4. T07 汇总当批已验证的业务、故障和容量范围。

各批分别记录预览、保存、审计与 Outbox、查回、历史和菜单证据。当时未设旧库升级或旧 CREATE 协议适配的独立前置批次。

## 3 备选方案与取舍

| 方案 | 收益与成本 | 决定 |
| --- | --- | --- |
| 维持旧库和两代协议 | 保留开发样本的原地升级路径，但增加字段、解码和旧程序隔离工作 | 不采用；当前没有该兼容义务 |
| 同步更新当前实现与合成样本 | 可直接落实目标模型，需重新验证创建/查询和维护能力 | 采用 |
| 借重构放松历史、事务或授权 | 会改变已采纳的业务规则并失去可靠恢复 | 不采用 |

## 4 影响与验证

2026-11-01 的首批验证中，013以当前结构的空库安装、重复初始化、失败保持关闭及单一格式严格解码替代旧库升级方案；仅检查当前程序与当前存储是否匹配，不建立兼容矩阵、制品准入平台或密码轮换机制。以后存在真实客户交付需求时再制定升级/恢复方案。

当时，011的AC029缩减为当前模型初始化与格式一致性；023保留全部257个编号，其中TL-241、242、246、247的旧版本专项退役，253例仍为当前待验。涉及旧格式的混合案例仅去除兼容参数，保留当前模型内的业务历史、权限、诊断和恢复断言；退役不算通过。

2026-11-01 首批仅修改文档和策略，未修改运行代码、执行数据库迁移或重建数据。文档检查及证据保护见[修订验证](../verification/025-greenfield-implementation-policy.md)。后续实现的结果按各批报告查阅。

接口替换须验证旧路由和公开声明已撤下、办理走现行入口、原提交按当前权限可查且不会重复写入。岗位核编举例，先核定 2 人，后来更正为 3 人，查第一次提交仍能打开核定 2 人的原件。若有获准的暂留例外，还须按其允许范围验证拒绝条件。[岗位核编整改与复验](../verification/025-position-quota-interface-retirement.md)
