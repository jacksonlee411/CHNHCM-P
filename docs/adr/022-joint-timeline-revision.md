# CHNHCM-022 M02 有限联合修订与历史补全

登记信息：[registry.json](../governance/registry.json)。适用范围：同一BU的有限联合修订、首条历史补全及业务分类录错处置。承接[021](021-bu-lifecycle-and-record-maintenance.md)、[020](020-effective-record-delete-and-redate.md)与[018](018-effective-records-and-source-history.md)；[011](../specs/m02/011-m02-business-requirements.md)持有规则，[010](../archive/plans/010-m02-scope-and-plan.md)持有待办。本文保留原决策与后续替代，联合实现见T08；单条分类入口按104、首条维护按107收敛。结果授权、失败恢复和实现/验证前置已由[024](024-timeline-implementation-simplification.md)部分替代，精确范围见第5节。

当前范围补充：[109](../archive/plans/109-lifecycle-pair-maintenance.md)已按用户决定替代公开通用联合办理：仅保留插入停用与重新启用、删除停用与重新启用。旧任意项目、跨节点交换及多目标分类纠错退出；首条两步、单条组合更正及旧历史读取保持。以下原决定和评审过程保留时点含义，当前办理以011—013及109为准。

## 1 背景与问题

2026-11-01，用户采纳：只要目标时间线合法，将有限联合修订提前纳入M02，同时决定首条历史补全、分类录错处置，并补入“已有后继时补一整段启停”和“部分字段更正后后继快照保持”两组验收。

单条命令要求每次提交合法，无法直接在“1月新建→6月更名”中补入“3月停用→4月重新启用”：先加停用会使后继更名非法，先加恢复又缺少停用前提。分类不可改和首条不可删的组合也使首条原因录错没有修复入口。应由一个明确的候选集合处理这些变化，而非要求管理员先发布错误的中间事实。

## 2 原决策及后续替代

### 2.1 有限联合修订

允许针对同一BU、同一当前来源，显式提交有限的新增、更新、删除项。更新项可同时包含资料更正、新日期及分类纠错；同一既有记录只出现一个项，多个修改面合并在该项中。新增项取得新记录身份，更新保留身份，删除保留原件。请求项的排列顺序不表示业务执行顺序。

Go先构造全部变更后的候选集合，再按最终日期解析资料、启停转换及完整区间。中间集合不得对外提交，也不得因其暂时违反相邻依赖而拒绝最终合法结果。最终仍须通过日期唯一、企业范围、固定首条最早且不可删除、字段/分类组合、完整状态转换、当前授权、准确版本与真实引用守卫；“目标合法”不取消这些条件。失败整笔不产生业务变化，成功只产生一个完整新来源、一份汇总审计和一个Outbox事件，各项保留前后目标及处理明细。

“有限”限定为同一BU、明确列举的项和固定操作集合；不引入跨BU事务、条件脚本、循环、隐式级联或通用导入引擎。可从一个分类纠错项开始，也可组合多个关联变化；不另设未经业务论证的记录条数上限，技术请求预算与容量测量由013持有。原单条入口继续使用单项候选校验，不额外要求联合入口权限。

### 2.2 首条历史资料维护

原首条补全的专用入口、保留原日期选择及强制联合要求由[107](107-first-record-maintenance.md)替代。首条日期和名称可直接CORRECT，后续原日资料按需另次普通ADD，两步独立保存。first_record_id不变、首条仍CREATE且最早、企业范围及旧来源保护保持。109已退出自愿通用联合的补充路径；首条只保留普通两步维护。

### 2.3 分类录错处置

单条分类按[104](../archive/plans/104-unified-record-correction.md)在“更正记录→业务分类”内使用CORRECT，与名称/日期可一次保存且不要求联合权；只有多目标关联操作使用本决策联合协议。首条只能在CREATE内改原因；非首条可在CHANGE、DEACTIVATE、REACTIVATE间纠正类型及相应原因，最终时间线必须合法，不能把非首条改成CREATE。

更正记录未编辑分类时、仅日期API和删除继续继承原分类；显式分类面保存新类型/原因及服务端名称快照，并保留旧分类。新选分类按适用固定目录校验；未改分类的记录不受旧原因下架影响。不增加自由文本处理原因、备注或另一套撤销动作。

分类纠错保留recordId，但记录的有效类型随不可变修订保存。按025，记录身份表不保留兼容初始kind；当前及历史查询分别从所选修订的operation_type解释资料/停用/重新启用，不以初始kind覆盖后来更正。转为停用时按最终前序继承资料，不接受同时提交名称变化；停用改为资料或重新启用时，以原目标在基准来源中的解析资料为默认，允许明确调整并保存独立快照。转换及原因纠错分别校验原/新类别的专用权，不能借分类变化绕过生命周期权限。

### 2.4 快照与原子结果

已有普通资料与重新启用的完整快照保持独立：未列为显式修改目标的字段不因前序更正自动传播。新资料项按最终候选中的前序资料合并输入；停用按最终前序继承。部分字段更正若让后继继续保留旧字段值，预览必须说明，只有用户显式增加后继更正项才一起更新。

原结果精确重试按同一提交身份及规范化完整项内容返回，不能逐项重放；响应丢失使用既有resolve协议。无变化项按013反馈，不制造直接修订或新身份；全部无变化才返回整笔no_change。结构、日期、分类或资料实际改变均计入影响，原来源、原采用和历史授权证据保持。

### 2.5 完备性评审补充

按本轮评审修订，将下列细节固定为后续实现合同；013持有字段、存储及协议，011持有独立验收，不能由实现自行选择相互冲突的解释。

| 问题 | 采纳的规则与取舍 |
| --- | --- |
| 停用值相同但前序变化 | 继承引用表示所选来源最终紧邻前序的准确记录/修订；引用变化本身须产生派生修订，即使值和停用期间相同。旧来源继续保留原继承，不将历史取值出处混为当前继承 |
| 无正文查回与原声明 | 原方案要求查回重核原声明的写权；该要求已由024第2.1节替代。现按当前对象/历史及输出字段读权返回已存终态，仅撤写权不阻断；原声明含同值/null继续用于原执行授权和审计，不保存表单值，原allow不替代当前读权 |
| 分离区间与纯结构变化 | 影响同时含业务值准确区间集合和记录结构差异；不以外包区间吞掉未变间隙，不以数据差异为空判无变化。创建、单条/联合维护均使用同一当前影响及事件合同；原保留创建v1的要求由025取消 |
| 暂缺内容或暂时非法的联合预览 | 区分可加入编辑与整笔可保存；预览明确incomplete/invalid/valid及安全项问题，只有完整合法候选可保存，正式提交仍严格必填。Go共用算法，无持久草稿或前端状态引擎 |
| 写入跨午夜后的原办理说明 | 写前最后采样时刻和业务日随终态不可变保存，实际登记时间另记；查回按原办理日解释过去/当天/未来，不用登记日或查回日重标，不恢复时间截点设施 |
| 组合验收不足 | 增补混合ADD/UPDATE/DELETE、已有启停后继的首条保留/不保留、六向分类转换及改日/字段组合、同值项派生变化、撤权恢复和午夜案例；每组有独立输入/预期 |

同值项不产生直接修订，但其记录可因其他项引起期间/继承关系变化而产生派生修订；两类结果分别留证。新增合同均属原有限联合范围的落实，不改变首条删除保护或扩大跨BU/同日多记录等范围。

### 2.6 健壮性评审补充

原健壮性评审对五项失败路径形成下表决定；024后续收敛其中的二次终结、升级及算法前置，当前承接逐行注明。013持有现行合同，011的AC025—029持有修订后预期；旧报告仍仅证明当时的文档检查。

| 发现 | 必须落实的规则 |
| --- | --- |
| 业务错误可能越过写入回滚边界 | 全部业务写入使用同一savepoint，显式提交意图决定外层事务是否提交；400/409、5xx、取消均不得留下记录身份或半份来源。现有创建的嵌套保护不等于维护可直接复用通用事务回调 |
| 回滚后终结与重试/查回竞争 | 原方案引入回滚后重新取锁补拒绝；024第2.2节将该路径移除。可恢复拒绝在原锁内保存，整体失败保持待确认，由显式resolve查回/封闭；已有终态优先、同锁唯一和未知保护继续落实 |
| 原拒绝无法无正文准确恢复 | 终态保存版本化安全诊断、稳定itemId/相对字段及原请求依据，原内容只由摘要绑定；查回不重跑当前校验、不按数组位置绑定、不另存表单值，并执行当前授权 |
| 局部SQL超时不足以限制整次执行 | 整体预算覆盖正文、锁、Go算法、SQL及COMMIT，清理有界。024第2.5节以取消延迟实测替代预定可取消排序要求；超限不拆笔或截断，不增加业务条数上限 |
| 旧程序误入新存储格式 | 原前向升级、旧结果兼容及024第2.4节换密隔离均由[025](025-greenfield-implementation-policy.md)取消。当前只在隔离空库安装现行模型，检查当前程序/存储一致性并严格解码，不建设旧版本支持 |

首条删除保护、联合项明确性、同日唯一、完整时间线、真实引用及当前授权保持；本轮不增加持久草稿、后台重试作业或新业务审批。
