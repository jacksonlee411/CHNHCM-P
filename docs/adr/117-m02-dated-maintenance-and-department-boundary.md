# CHNHCM-117 M02共用按日维护与部门边界

登记信息：[registry.json](../governance/registry.json)。适用范围：116的R0及后续BU/部门接入。依据用户2026-11-04采纳方案及四项明确指令；承接[116路线图](../archive/plans/116-m02-shared-dated-maintenance-roadmap.md)、[025全新实施](025-greenfield-implementation-policy.md)、[109固定启停](../archive/plans/109-lifecycle-pair-maintenance.md)和[M02目标](../architecture/target/modules/m02.md)。实际R0检查见[报告](../verification/116-r0-contract-preparation.md)，不表示R1—R6实现完成。

当前普通维护日期语义由[123](../adr/123-current-maintenance-and-dated-query-boundary.md)调整：列表按服务端D，详情按所选记录，取消通用查看日期；原阶段完成及验证记录保留。部门仍待116 R4/R5实现。

## 1 背景与目标

当前BU已接通按日维护、可靠提交、历史及查询选择/CSV；部门尚未接线。提炼目标是M02内两个真实对象使用一套Go时间线、标准生命周期、页面办理与提交恢复实现。对象保留强类型资料、关系、授权、引用和独立存储适配；共用算法不改变事实主责。

部门路径现纳入路线图，需要最小行政上级关系、日期资格、历史及权限保护。Hierarchy拥有行政边，不能在Department和Hierarchy分别维护两份上级。完整多用途组织树、岗位/任职主管、预算、人数、审批及外域消费者继续后置。

## 2 决策

### 2.1 对象与存储

BU、部门共用按日维护规则集；同部门、同业务日最多一条当前有效业务事件/生效记录。普通更正形成独立修订及审计，不增加第二条同日业务事件或EFFSEQ。固定启停两条使用不同生效日；109退出的任意编排、跨节点改日、首条保留开关继续退出。

BU与部门的身份、记录、修订、来源、日志、Outbox和提交终态分别使用独立物理表。最小部门行政层级使用Hierarchy自己拥有、只存部门关系的独立表组，不把BU与部门事实混存其中。企业身份及X03仍各自持有已有事实；分表不要求分库、拆服务或共享结果登记表。详见[120技术合同](../specs/m02/120-dated-maintenance-technical-contract.md)。

### 2.2 BU归属与期间

每个部门在其有效资料中必须归属一个BU；一个BU可管理多个部门，是部门到BU的多对一。部门企业内编码唯一，改BU不改部门身份或编码。当前标准不支持同一部门跨BU使用，不新增可用BU集合、共享标志或M02适用白名单；X02对其他对象的长期目标不由本决策删除，也不据此宣称部门共享已支持。

部门启用且归属关系发挥业务效力的全部期间，BU必须存在并启用。停用部门保留的BU是历史资料，不构成永久活跃引用。部门重新启用、更正/改日/删除、BU维护都核验完整最终候选及受影响期间，旧来源和原采用保持。两对象先后调整使用合法单步，不引入跨对象联合办理。

### 2.3 部门路径

首版支持单一行政上级关系，每个部门在每个启用日恰有一个有效父边，指向同BU部门或企业根；停用期间及首条前没有有效父边。未来有效区间可以提前登记。有效父子必须同企业、同BU，启用子部门的全部期间须由启用上级覆盖；拒绝自指、循环及未来日期段循环。停用修订继承准确历史成员引用，该成员不必继续覆盖停用期间，也不形成永久活跃引用。路径为企业名称和行政祖先部门名称依次连接，以` / `分隔，例如“高谷集团 / 组织效能中心 / 组织发展部”，不强行插入BU节点。

Hierarchy是上级边的唯一权威；部门表单中的上级输入由应用命令委托本部门关系聚合维护，与本次部门记录、来源及结果同事务。停用结束有效父边，恢复重建合格父边；删除或改日停用记录先通过共用生命周期，再按最终候选重算全部关系期间和双向资格。父部门更名或上级调整不批量改写后代部门记录、不制造后代新业务事件。跨BU搬迁有下级的部门须先合法调整所有仍发挥效力的关系，包括未来启用安排；仅保留的停用历史引用不阻断，不新增整树搬迁操作。

当前列表路径按服务端D（未来首条按首日）、停用前路径按停用前一日；详情按所选记录期间分段，显式来源按封存证据。具体读取/字段权及分段由119/120持有，沿用123且不提供通用查看日期。

2026-11-05用户采纳R4简化：关系来源只包含一个部门自己的按日行政父边，可覆盖该部门各BU期间；不保存整BU成员快照，也不把整树版本交给客户端。当前行政森林由各部门关系头组合，Go校验和BU范围共同守卫继续保护并发成环、启停覆盖及空集合竞争。仅本部门关系实际变化才形成关系新源，其他部门来源保持；准确成员与路径证据不因此删除。具体结构和验收见120/121及[范围复核](../verification/116-r4-relation-simplification.md)。

### 2.4 资料、用语与分类

部门主名称必填、简称选填；首版不启用部门英文名及英文简称。BU已有英文资料继续由BU定义提供；字段差异不改变共用规则。负责人、岗位/人员主管、地点和成本等不作为本批必填资料。

M02对用户显示的“业务状态”统一称“状态”，仍表示原有启用/停用及服务端D派生的未生效，不改API `status`、枚举、转换、筛选谓词或权限。该显示调整在R0实施到当前BU页面、筛选和CSV；源包、既有验证报告、原业务分类快照以及其他领域描述不回写。

下一阶段共用Go目录采用下表。技术类型码CREATE/CHANGE/DEACTIVATE/REACTIVATE保持；原因码和显示名由本表明确。它是R1接入时切换的目标目录，R0不改变当前BU正在执行的原因准入目录，不把文档采纳记为该目录已运行。

| 操作类型码及名称 | 原因码 | 操作原因 | 适用对象 |
| --- | --- | --- | --- |
| CREATE 新建 | NEW_ORGANIZATION | 新设组织 | BU、部门 |
| CHANGE 数据更改 | NAME_ADJUSTMENT | 名称调整 | BU、部门 |
| CHANGE 数据更改 | ORGANIZATION_REASSIGNMENT | 变更归属组织 | 部门的BU或行政上级变化；BU当前无可变归属，不显示该原因 |
| CHANGE 数据更改 | OTHER_DATA_ADJUSTMENT | 其他数据调整 | BU、部门的本批获权资料 |
| DEACTIVATE 停用 | ORG_RESTRUCTURING | 机构撤并 | BU、部门 |
| DEACTIVATE 停用 | BUSINESS_CLOSURE | 业务终止 | BU、部门 |
| REACTIVATE 重新启用 | BUSINESS_RESUMPTION | 业务恢复 | BU、部门 |

新建/新增事件必须有合法原因；仅有一个合法原因时由Go目录标明默认，页面直接呈现，多项由用户选择，零项不能办理。前端不按数量推断默认，原有合法选择保持；同日多个资料面合并一条事件。普通更正、改日和删除继承准确目标分类，不另填处理原因；显式分类纠错需专门授权。旧修订的类型/原因码及名称快照保持，不能用新目录重解释原历史；已存终态重放不重新判断当前原因目录。

新增CHANGE事件调整BU/上级时选择ORGANIZATION_REASSIGNMENT；该要求不强迫已有记录更正改变分类。首条归属纠错仍为CREATE并继承原原因；重新启用可调整获权完整资料，仍为REACTIVATE并使用恢复原因。显式分类纠错继续按原/新类别和目录核验，不借归属调整自动授予分类权。

### 2.5 权限、可靠提交和范围

操作、部门范围、字段及导出分别授权；部门读取不自动授予BU完整读取。只提供引用所需的BU编码、名称及必要资格摘要，上级和路径也按当前授权输出。跨BU管理归属调整核验原/目标范围；“不支持跨BU使用”不禁止合法按日变更归属。

BU范围授权使用本次服务端执行日D及部门当前来源：D已有资料时取覆盖D的管理BU，停用时仍取继承保留的BU；D早于首条时取当前来源固定首条最新修订的BU。该事实由M02解析交给X03判定，不新增可维护的授权归属字段，不把未来资料提前生效。所选记录、旧来源及创建者身份不改变该口径；未来转入不提前授权，更正未生效首条BU则保存后立即改变授权归属。停用BU仍可作范围标识，业务启用资格与读取授权分别判断。创建准入须包含保存后read和查回所需history.read；真实撤权/转出后的查回仍执行当前读取授权，不保留创建者例外。

新增、更正、删除或改日导致BU/上级实际归属改变时，核验本次动作及归属调整权、受影响原/新范围和关系字段权。纯启停关闭/重开同一关系不额外要求归属调整权，因期间重算产生的引用版本变化只计结构修订。具体候选差异、完整Grant及跨日读取规则由120持有。

提交身份在对象类型命名空间中隔离；各自写所属终态表，原请求、重试和resolve共用相同逻辑锁。BU现有引用集合明确属于BU，保持可查回，不改写已有摘要。具体键、路由、待确认阻塞和失权行为由120唯一规定。

## 3 备选与取舍

| 方案 | 价值与成本 | 决定 |
| --- | --- | --- |
| 同一部门多BU或共享使用 | 可表达矩阵共享，但引入适用、授权和多方管理问题 | 不纳入当前标准；每部门一个管理BU |
| 保存可编辑路径字符串或在部门表维护第二套父边 | 实现表面简单，但更名/改日后路径和历史失真 | 不采用；Hierarchy唯一事实，Go派生并保存只读历史证据 |
| 每次局部调整保存整BU完整关系来源，并由客户端提交树版本 | 提供全树状态标识，但使无关调整互相冲突、扩大隐藏变化可见性及成员写入；当前没有整套组织结构发布/审批/固定采用需求 | 不采用；关系来源按部门独立保存，树级标识只作内部守卫，准确历史与路径证据继续保留 |
| 为路径交付完整多用途组织树平台 | 超出本轮两个对象接入的验证需要 | 仅采纳最小行政关系与路径 |
| 共享物理结果、审计或Outbox | 简化查表但违反用户分表约束 | 不采用；复用机制，物理表独立 |

## 5 适用与替代关系

本决策关闭116中部门关系、编码、字段、分类及路径范围待决项，并部分替代其部门路径后置和跨BU使用评估的原提议。010原BU批次、109固定操作及既往报告不重开。011—013继续持有现行BU规则，R1切换目录时同步其合同和实现；118只定义新增部门规则并引用共性，不复制或重编旧稳定ID。

2026-11-04按用户采纳的评审方案补充未生效授权、有效父边/历史引用及启停路径口径，并同步澄清归属更正/恢复的分类继承；原R0报告保留当时结果，本次修订及检查见[补充报告](../verification/116-r0-authorization-and-hierarchy-review-fixes.md)。本轮只修订合同和独立预期，R1—R6未开始。
