登记信息：[registry.json](../../governance/registry.json)。本合同承接[M03目标](../../architecture/target/modules/m03.md)及[309实施方案](../../archive/plans/309-m03-grade-ladder.md)，按[124接入模板](../../templates/dated-object-admission.md)定义Grade、GradeLadder及Job可用职级。页面标准仍由012／026持有，首批Job／Family未受本合同明确扩展的规则仍由[308](308-job-foundation-contract.md)持有。G1 Grade已完成实施及独立环境验收，实际状态见[职级实施记录](../../verification/309-grade-g1-implementation.md)；G2阶梯及Job关联已完成全栈实施、三轮主代理评审及本地完整验收；正式CI、推送／合并和人工业务验收未执行，见[G2实施记录](../../verification/309-grade-g2-implementation.md)。

## 1 角色、对象与适用范围

<a id="m03-br-015"></a>
### 1.1 M03-BR-015 独立身份与范围

Grade为职级定义；GradeLadder为同企业职级的有序进阶结构，两者独立UUID、编码、按日记录、修订、来源及启停。管理员办理获权动作，查询者只读，导出单独授权；角色名称不代替X03 Grant。正常菜单为“设置 → 职务配置 → 职级／职级阶梯”，路由为`/settings/staffing/grades`与`/settings/staffing/grade-ladders`；Job关联在现有职务维护中直接办理。

企业身份来自认证上下文，不接受客户端另传企业绕过范围。所有引用同企业；企业只提供身份和首条日期下界，其停用不级联本目录。BU、部门、职务系列、默认来源与访问权限不构成职级作用域，不引入SetID／TableSet。G1只开放Grade；G2才开放Ladder及Job关联。

Grade没有全局排序、工资金额或人员档次。Ladder只组织职级之间的顺序；级内档次、自动晋级、岗位定义、人员任职、容量及M09 GradeRate均后置。既有Job不会因为未配置职级而变为非法或隐藏；未来带职级岗位／任职须另核明确关系，不能把本批结构当作实际采用回执。

## 2 字段、目录与集合输入

<a id="m03-br-016"></a>
### 2.1 M03-BR-016 类型与输入语义

| 字段 | 对象／输入 | 默认及Go规则 |
| --- | --- | --- |
| code | Grade／Ladder创建时输入 | 必填，沿308编码规则：ASCII大写归一、1—30字符、企业＋类型唯一；创建后不可改，跨类型同码允许 |
| name／nameEn | 两对象文本 | name必填，nameEn可空；沿013名称NFC／200码点准入，非ASCII英文名允许；不重新归一化旧源 |

| gradeIds | G2 Job可用职级集合 | 创建缺省为`[]`；维护缺省保持，`[]`明确清空，`null`拒绝；UUID数组，无重复、无顺序业务意义，由Go按ID规范化 |

Grade与Ladder公开类型区分，即使成员字段同名也不共用无判别数组DTO。Job关系是无序集合，调换请求顺序不生成新修订；Ladder顺序变化生成新修订。Ladder显示顺序由Go返回连续的1…N；不接受客户端另传rank，不按编码／名称／金额排序，不留重复位次或空洞。数组整体替换而非逐成员立即落库，编辑增删及上下移动只修改草稿，保存一次提交。

两对象CREATE原因为NEW_GRADE／NEW_GRADE_LADDER；CHANGE共同支持NAME_ADJUSTMENT、DESCRIPTION_ADJUSTMENT、OTHER_DATA_ADJUSTMENT，Ladder另支持GRADE_MEMBERSHIP_ADJUSTMENT、GRADE_ORDER_ADJUSTMENT；DEACTIVATE为GRADE_CLOSURE／GRADE_LADDER_CLOSURE，REACTIVATE为GRADE_RESUMPTION／GRADE_LADDER_RESUMPTION。Job新增GRADE_SCOPE_ADJUSTMENT原因，其原原因保留。Go核对目录并封存当时标签，不用当前目录改写历史。

## 3 职务关联与阶梯结构

<a id="m03-br-017"></a>
### 3.1 M03-BR-017 职务可用职级

一个Job在一段启用资料中可配置零至多个Grade，一个Grade可用于多个Job；关系归Job，跟随Job记录日期和修订，不另建一条不同步的关联时间线。空集合显示“未配置可用职级”，不是全部职级、默认职级或任何人员的实际等级。没有默认选择和隐式第一项。

允许同一Job同时使用来自不同Ladder的Grade，也允许不属于任何Ladder的Grade。Job不绑定Ladder，JobFamily不传播可用职级。Ladder调整不会改写Job集合；后续岗位如果同时选择Job、Grade及Ladder，须由该批合同明确在同一业务日验证Job可用集合与Ladder成员交集，不能本批提前生成岗位。

<a id="m03-br-018"></a>
### 3.2 M03-BR-018 阶梯成员及排序

Ladder是线性低至高列表，至少一个职级即可建立；一个Grade在同一资料记录最多一次，可以同时属于多个Ladder。同一Grade在不同阶梯的位置可不同，不推导全局偏序、环路或一条企业晋级链。重排不改变Grade身份，不调整Job或人员数据。

成员增删与重排均按日维护。历史来源显示当次成员及顺序；今天的阶梯调整不回写旧来源。停用Ladder保留其原资料及成员证据，重新启用须确认完整成员和当前资格。没有空壳阶梯、嵌套阶梯或级内Step；删除全部成员应被定位到“职级成员”，需要结束使用时办理停用。

## 5 引用资格、准确采用和反向保护

<a id="m03-br-020"></a>
### 5.1 M03-BR-020 全期间与逐成员采用

Job／Ladder每个最终启用资料区间内的每个Grade必须同企业且连续启用覆盖整个区间，不只核记录起日或今天。包含过去、未来、停用空档、删除回退、首条改日、固定期间扩大与恢复。反向校验Grade候选时读取所有受影响Job／Ladder当前头，包括未来引用和用户不可见引用；不以旧归档来源阻断合法维护。纯Grade更名无需扫描全部引用，不产生消费者新来源。

引用冲突整笔拒绝，无自动停用、移除成员、级联或替换。先明确调整Job可用集合／Ladder成员或结束其期间，再调整Grade；隐藏依赖只给安全拒绝，不披露对象名称、身份或数量。没有合法覆盖的源不可被候选标为可选，保存再次核验。

新建Ladder及带职级的Job只有开放首条，故已排定永久停用的Grade不能覆盖该开放尾段。不得暗加停用记录；需要有限期间时先建立合法资料，再明确办理消费者截止与Grade截止。若既定Grade截止不能调整，本批拒绝开放创建；插入到已有有限空档可以选择完整覆盖该有限区间的Grade。

每个成员保存Grade稳定ID、`businessAt`、`sourceVersion`、`recordId`、`revision`；这些由Go解析，客户端只交稳定ID。集合资格与准确采用分开：当前资格变化不能悄悄刷新历史证据。

| 动作 | 逐成员准确采用 |
| --- | --- |
| CREATE、新增成员、重新启用／新固定恢复端 | 按最终记录日新采用；恢复核全部成员 |
| 新CHANGE／插入 | 保留成员继承最终前序采用，新增成员新采用；仍重验完整期间 |
| 普通资料更正／仅重排／仅更原因 | 未变成员保留原采用；成员增删只增删对应当前快照关系，旧来源不变 |
| 既有非停用记录改日或改变类型后仍启用 | 全部最终成员按最终记录日重新采用 |
| 停用／改为停用 | 继承最终前序成员及采用，不取停用日新源 |
| 固定期间仅改停用端 | 既有恢复端日期／类型／成员不变时保持原采用；仍核最终全期间 |
| 删除记录／删除固定期间 | 独立后继保持原采用，停用重继承前序；回退资料的证据继承，扩大区间另验资格 |

普通当前展示按308业务日规则解析Grade当前修订名称：今日D、未来首条日、停用前一日；详情显式选启用记录用记录日，停用记录用前一日。准确来源显示封存采用和当时顺序，不以当前名称填补缺失或无权的旧名。源更名只改变当前展示；引用不存在或不可见不给最新名兜底。

## 6 权限、历史与可靠提交

<a id="m03-br-021"></a>
### 6.1 M03-BR-021 当前授权与恢复边界

创建缺少必填字段写权时不开放能力；Ladder成员必填，Job省略可选集合则保持合法空集合，不暗增配置。显式传入集合先核字段权，最终候选再核全部隐式变化。

X03新增grade／gradeladder的read、history.read、export、create、record.add、record.correct、record.redate、record.delete、deactivate、reactivate、lifecycle.pair；字段含共有资料、日期、状态、分类，Ladder另含gradeIds。Job新增gradeIds读写字段，沿现有job动作。集合重排也是Ladder.gradeIds写入；删除／改日／分类造成的隐式集合变化须检查最终字段写权。

新采用须有Grade.read及名称／日期／状态的必要读权，非今日采用另需Grade.history.read；纯继承未变采用不强加历史读权。当前普通过去记录按本对象read投影，明确旧源及changes日志才要求本对象history.read。当前源引用的非今日标签和准确采用独立执行Grade历史权，不用Job／Ladder权限替代。

集合字段不可读则不返回成员、数量、位次或可据此推断的日志差异。集合字段可读但某成员Grade不可读时，整体显示“职级资料受限”，不输出隐藏ID、成员数或残缺顺序；纯资料维护可以省略集合原样继承。整体替换／重排要求原集合与目标集合可完整读取并具写权，不能用当前可见子集覆盖隐藏成员；无权限用户不能通过`[]`清掉不知情的关系。Grade停用反向拒绝仍执行完整内部验证。

错误、候选、筛选、日志、原件、摘要和CSV均按当前权。失权清理已加载成员、草稿与日志缓存，保留仍获权资料；503或迟到响应不能带回旧标签。显式无权条件／排序拒绝，不静默扩大列表。admin／reader是本地身份，测试还须用精确Grant覆盖字段撤权和历史撤权。

保存使用类型／主体／提交号及规范化摘要，既有对象携expectedSource与目标修订；创建不伪造来源。确定提交后才报告成功／拒绝；响应未知沿308原身份resolve，不能新号重发。跨类型同提交号隔离，重试不重复历史，变摘要拒绝。未提交取消零业务写入，已提交未知的离开不能宣称取消保存；换账号及权限收窄不泄露原主体结果。

## 7 领域、存储、API及并发接入

<a id="m03-br-022"></a>
### 7.1 M03-BR-022 强类型扩展与事实归属

309方案基线时[Staffing内核](../../../internal/contexts/staffing/domain/timeline.go)只有Family／Job；G1现通过[GradeData／GradePatch](../../../internal/contexts/staffing/domain/grade.go)接入本域标量时间线。文字映射仍不能承载G2关系集合。本批在Staffing拥有Grade／Ladder资料与Patch、强类型成员及逐成员Adoption；深克隆、归一化、Apply、业务相等、修订相等及实际变化字段分别验证。禁止将数组JSON编码成文字字段、逗号分隔ID或前端维护第二套排序／资格算法。具体类型文件由实施产出，不先造占位域包。

Grade／Ladder各自拥有身份、当前头、不可变来源／记录修订、日志、Outbox、提交终态和选择草稿表组。Job可用职级与Ladder成员是所属来源／记录的不可变成员快照；独立关系表以对象、来源、记录和Grade为键，Ladder另存该版序位。Job原来源没有成员行明确表示当时未配置，不改原快照字节、不补造采用；当前和历史统一走同一关系读取模型，不保留两套读写格式。建立新来源时连同其全部成员快照同事务封存；缺失新源的必需完整性信息必须报错，不能当空集合。

来源封口须区分“合法空集合”和“未完成成员写入”：Job／Ladder每个来源内的每条记录都有唯一成员清单，记录成员数和规范化摘要，与成员同事务封口。Job允许显式零成员，Ladder至少一个；清单缺失、摘要不符或重复一律报错，不按缺行回退为空。G2迁移为全部既有Job来源／记录补建明确的零成员清单，依据是此前产品根本没有职级关联；只增加关系索引元数据，不修改原来源字节、修订、采用或回执，不制造业务变更。迁移后新旧来源统一按清单读取，无版本猜测或旧格式回退。Grade没有成员不需要此封口。所有原来源、回执和旧采用逐份保持；本批不迁移4380。

SQL归`db/queries/staffing`，sqlc产物归本域infra；迁移全局追加且仅upgrader执行。公共企业反向最早日期端口加入Grade／Ladder，包括已停用对象，不直接查询别域表。源事件与本域事实同事务落Outbox，事件身份／来源／动作明确，不宣布未接入消费者投递或采用成功。

成员的数据库结构引用可按语句批量检查清单、Grade原来源和修订是否存在；不能减少成员行、丢弃来源或放松Go全期间资格。采用该方式时，所引父事实必须不可更新／删除且应用没有TRUNCATE权，完整性条件在事务提交后单调保持；同事务先写父事实再写成员，其他事务未提交的来源不得采用。缺失任一引用使整个语句失败，COPY及INSERT同样适用；运行准入必须检查批量检查和不可变守卫均启用。当前00020只调整结构约束，不改变00019成员／封口格式或原数据。

### 7.2 HTTP及生成合同

资源为`/api/v1/grades`、`/api/v1/grade-ladders`；独立Grade／GradeLadder输入和结果，OpenAPI为唯一HTTP生成源。Job在现有资源扩展强类型gradeIds；不新增脱离Job来源的成员增删写端点。

| 方法／资源相对路径 | 输入与结果 |
| --- | --- |

### 7.3 共同守卫与最终候选

保持308既有锁序前缀：类型提交锁 → 企业共同守卫 → 按ID排序的Family守卫 → 按ID排序的Grade守卫 → 目标Job／Ladder对象锁。Family／Grade自身写入在相应阶段持排他守卫与对象版本锁，不能取得后段对象锁后补取前段关系锁。所有锁键带实例及类型；新身份、空引用集合也有守卫，不依赖已存在关系行防幻影。

Job写入取得原／新全时间线涉及的Family及Grade共享守卫，Ladder写入取得原／新Grade共享守卫；Grade资格变化取自身排他守卫。Grade反向校验在锁内读Job／Ladder头及全部受影响启用区间，不反向取得它们的写锁；Family反向验证也不取得Job／Grade锁。由消费者写入必取源共享锁保证源资格串行；纯名称维护不锁无关依赖。

沿现有READ COMMITTED短事务，在全部守卫取得后重新读依赖、来源与权限；不得复用锁外旧头／候选缓存。发现集合变化须回滚后按新排序锁组重规划，同一总预算内退出，不在后锁上升级／补前锁。企业端口同物理连接与事务；不能以外部HTTP核验或异步事件补救。事实、成员、采用、日志、投影、Outbox及终态原子提交；任何业务失败无部分事实，未知COMMIT先查回，不能当拒绝。

### 10.2 视口、原生缩放与权限专项

职级、职级阶梯及职务可用职级按共享桌面视口核对相应布局。后续变更在原生 200% 下验证受影响的关键流程，例如维护长成员集合并保存或取消、从日志查看原采用并返回。按实际路径选择代表对象和角色。原生 400% 按触发条件专项验证。[012 视口与缩放](../m02/012-m02-functional-and-interaction-design.md#m02-ui-viewport-matrix)

原 G1 批次的 Grade 为 2 角色 × 7 条件，共 14 单元。原 G2 批次的 Ladder／Job 为 2 对象 × 2 角色 × 7 条件，共 28 单元，另重验受影响的 Grade 14 单元。上述 56 个单元分别归属原执行批次。原批次每单元均经正常菜单到列表、筛选、详情、日志／历史；admin另走新建／更正、启停或固定期间、全部字段／错误／保存取消／离开弹窗，reader检查无写入口。Ladder／Job用长名称及至少20成员核最后一行可达；Grade无成员不伪造此输入。

日志直接维护及筛选后退在所有适用单元执行；更正实际保存及取消核业务来源数量，不只截图。使用正常滚轮、Tab／Shift+Tab、Enter／Escape，焦点可见；禁止强制点击、脚本滚动或CSS缩放充当可达证据。精确Grant专项另验“有read无history”“有资料写权无集合写权”“集合可读但源受限”“保存前撤权”“历史页撤权”“候选迟到”，按对象适用性记录，不以admin／reader两名账号覆盖全部权限。
