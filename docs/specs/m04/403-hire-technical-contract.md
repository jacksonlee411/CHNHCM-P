## 3 一笔办理的事务

1. 核当前会话，以同客户、主体、命令和提交号核对显式输入与原终态。返回结果按当前读权裁剪。可定位的任用决定或原单人员行另按第 5 节防重。
2. 采用一笔 PostgreSQL 短事务，在既有 Staffing 锁序中只协调本人的选择、所用来源与受影响的关系及资源。同层按稳定身份排序。提交时重读权限、准确来源和实际用到的规则，目标集合变化时按完整集合重验。仅按职务的办理无需锁无关岗位或读取招聘用量。
3. 在拟任区间按实际采用的主体用途、组织、职务、岗位模式及主选择边界划段。按岗段另核岗位和补员，新增占编的段再核额度与用量。开放任期采用 M02/M03 已配置的开放尾段。经办人无需填写边界或证明。已读的权威来源过期按对应合同返回冲突。
4. 同笔保存关系、首任职、两层必要选择、适用占用、确切采用、业务动作、幂等终态与对应源域 Outbox。任一守卫失败、写入失败或在提交前取消均不能产生部分业务事实。后续消费方各自维护其采用与 Inbox，以事件身份去重。M01 的独立档案仍在。M05 录用交接另依 T06 的份额守卫，工资、合同等按各自命令办理。[共同事务与锁序](../../architecture/target/10-ddd-and-state-contracts.md#staffing-quota-transaction)

仅按职务也须取得明确政策。岗位免占仍锁该岗位、检查补员状态并保留免占任职。新占一编时重读同期间的 M04/M05 可信覆盖、占编及预留，受控新岗须有设岗版本和来源接管证据才可确认零使用。存量岗空表及部门待分配数均不足以证明零。已履职补录依单独事实及原因选择 313 的实况路径。当前 `CheckRegularUse` 只处理其输入区间上的常规用量，不独自承担已履职补录或全部人事资格。[313 使用来源](../m03/313-position-capacity-contract.md#m03-ac-095) · [履职差额](../m03/313-position-capacity-contract.md#m03-br-036)

**同一任期跨模式。** 现有请求只有一个 Position。先在事务内固定政策版本和所有目标，按模式／岗位边界划出连续、不重叠且恰好覆盖原任期的子段。仅按职务段传空岗位并验 M02 部门与 M03 职务，按岗位段传该段的稳定岗位。M03 在各段继续拆分额度、暂停和占编边界。收齐所有结果才一次写入同一首任职。只有职务模式已交付时，遇后续按岗段应说明尚无法办理整段。不得截掉原单期间或生成两个入职动作。[跨模式验收](401-direct-hire-requirements.md#m04-ac-008)

同一人员首次办理也取得人员守卫。锁内用本人、用人主体与角色、关系性质、重叠期间和拟任安排核对已有工作关系，包括已安排的未来关系。同一安排再次录入只提示或定位原办理。原关系内增任职走原关系。另一份真实独立关系可凭能区别它的依据办理，同人同日不设全局唯一。该检查也适用于无编号通知和两个人事经办人并发保存。

## 4 更正、同日依赖与撤销

动作修订保存实际修改的字段及该事项适用的发生依据。存在业务前序或必要依赖时分别保存其引用。Go 验证引用的客户、人、目标和日期，防止自指、环路及相互矛盾的修改。对晚录或撤销，从受影响日的基准、保留动作及后继的独立变化生成候选。每次只应用动作声明修改的字段。若必要依赖失效，须明确替换、同步处置或拒绝。必要处置超出当前授权则拒绝整笔。原来源仍可还原原动作和当时采用的状态。事件统计按该来源仍有效的稳定动作身份去重。[同日业务规则](401-direct-hire-requirements.md#m04-br-008)

更正 A 时，只重验真实受影响的后项。若 B 依赖 A，且原业务条件、决定与修改在新版本上仍成立，系统随保存为 B 追加指向新依据的修订。独立动作保留原业务效果。前后状态引用也未改变时直接沿用原修订。只有条件已变、确需替换或结束 B 时才请有权人处置，无法合法处置则拒绝。旧来源继续沿原修订重现。[同日动作与日级状态](../../architecture/target/03-consistency-contracts.md)

未来首次入职撤销定位原办理，按需锁定已绑定的原单、关系、首任职、必要选择及所用资源。以服务端业务日判定尚未生效，重验其他关系与后继。可以合法处置时仅撤去原办理的效果，追加撤销记录、回执与 Outbox。撤销或改期后重送旧成功请求，只能查回该笔原终态，新的占用和选择保持其各自来源。

## 5 恢复、历史与故障

所有路径复用提交号恢复。同号同内容返回原终态，同号异内容冲突。查回与执行串行。查明未执行时封闭原号，晚到请求不能再写。结果仍未知则沿原号查回。仅失写权仍可按读权查看结果，其他主体不能凭号枚举回执。T02 的用途与任职政策按当前读权及原经办人查回，成功和无变更指向当时的准确版本。两种结果及未发布的拒绝、未执行均按原经办人查回。

有稳定来源时，在客户内对入职用途下的源决定或原单行加唯一约束。单人通知只取原单，名单取来源已有的稳定人员行，同一出具来源的编号按原规则识别。换提交号或换经办人仍只定位同一次办理。原单行绑定的人、日期或拟任安排不一致时回原办理核对。按初办时已存的业务内容比对，当前读权决定能否展现原办理，私人提交回执仍属原提交者。旧来源已更正或撤销时，重送不得复活。

无稳定编号或来源行的人工依据只保存可追溯的说明，使用原提交号和第 3 节的已有关系检查。说明文字、姓名与生成的行号均不构成跨提交唯一键。系统无法从两段文字认定同一外部决定。发现已办安排时回到原办理，只有确有另一安排才新建。系统已定位原单或已有安排时沿用原引用，换成文字说明仍按该办理核对。

权限拒绝、非法值、来源／资源／后继冲突、暂时不可用和结果未知分别处理。使用已建立的 HTTP 400、403／按防枚举约定的不可用、409、503 及原提交查回语义。必要业务决定与最小安全操作留痕。X03 的逐次匹配轨迹不作永久档案。[当前授权及留痕](../../adr/128-authorization-evidence-removal.md) · [日期规范](../../adr/026-date-display-and-input-format.md)

### 8.2 T04 同日晋升、调动与撤销的写入

T04 拟用 `POST /api/v1/assignments/{id}/promotions` 提交普通晋升，用 `POST /api/v1/assignments/{id}/promotion-transfers` 一次提交晋升与调动。两页撤销误记晋升共用 `POST /api/v1/employment-actions/{id}/cancel`，以原晋升为目标。这些办理拟从 `POST /api/v1/employment-actions/submissions/{id}/resolve` 按原命令与提交号查回，采用第 5 节的原经办人及当前披露规则。实施时同步 OpenAPI 和生成客户端。

| 命令或读取 | 提交目标、计算与可见结果 |
| --- | --- |
| 办理晋升 | 使用 M04 的 `ExecuteEmploymentAction` 办理所选任期的晋升。输入生效日、拟任职级、原因、依据、期望来源及本项决定附带的任职调整。Go 从动作前的任职修订取原职级和发生部门，逐段核对 M03 的职级、目标职务可用集合、适用的岗位资格及其确切版本。同一事务保存个人实际职级、晋升身份、前后证据及适用的资源变化。一项晋升决定附带的字段变化均归同一动作。 |
| 晋升并调动 | 同一实际任期、同一业务日的一次专用请求含两项各自的变更。有共用通知时传一次，两项各有独立通知时按事项传各自来源。Go 分别解析原因及来源，核对来源对各自事项的覆盖、跨岗授权和必要依赖，按整组职级与目标职务或岗位校验最终安排。在同一短事务内协调岗位用量及受影响对象，保存两个稳定动作身份及准确修订。每笔原件固定实际采用的来源，共用时引用同一通知版本。该任职只有一个新来源和一份该日适用状态，回执可定位两笔。 |
| 撤销误记晋升 | 两个入口共用原办理的 `CancelAction`。接受能说明误录的已有通知引用，或一条可追溯的误录原因，任一项即可。Go 核撤销权，锁定目标、期望修订和有关来源，从当日基准重算保留动作及后继期间。独立调动继续使用原身份。其前后职级或前序引用有变化时追加调动修订，保留原通知和旧修订。若调入岗位必须具备新职级且缺少合法后继处置，返回冲突，业务来源、动作及用量保持原值。 |

**补录与顺序。** Go 从已有记录或本次业务依据取得明确先后。从「在本次调动前补录」登记已知事实时，客户端带入所选后项及期望修订。Go 校验客户、人员、关系、任期、业务日及适用授权，保存确切动作修订引用，将资格依赖另记。同日独立事项允许省略前序。只有不同解释会改变业务结果、资格或授权时才返回具体待核项。共同生效的两项关联同次办理，资格按完整候选核定。补到已有后项之前，同一事务中重算该日与受影响后继，对前序或前后值已变的后项追加修订。自指、环路、未解决的同字段矛盾或缺失的必要依赖整笔拒绝。时间轴依业务先后展示，独立项稳定列出。事务列表依第 8.1 节按登记时刻倒序。[同日规则](401-direct-hire-requirements.md#m04-br-008) · [动作顺序与修订](#hire-actions)

接入转正时，现有 00037 首单动作必填任职的约束须按真实目标演进。实际试用开始和转正均可仅以工作关系为目标，从哪份任职进入只决定返回位置。已有实际试用起点沿用准确来源，补录时由 Go 核对关系、权限及实际开始日，记录一笔关系事实。晋升读取的原职级则来自实际任期；验资格确需而旧任期缺记时，允许据原任用事实从相应日期补入其任职资料。升级旧首单保留原来已知的值，不能批量推定试用开始日或个人职级。[业务前置与样本](506-job-information-records.md#m04-scn-018)

**关系级转正。** 在工作关系的写入守卫内核对关系转正权、适用组织范围、试用期、依据及已有办理。多份任职展示同一关系结果，各页、原件及部门字段按当前读权披露。两处并发提交同一安排只产生一笔转正。重复请求按权定位原笔，内容冲突时回原笔核对。通知载有业务发生部门时固定通知及有效部门来源，否则按动作前本关系的人事管理主任职确定，保留当时的主选择与部门修订。仅统计归属不明时，系统保存「发生部门未确定」及可推知的原因，例如「通知未载部门，同日调动先后未知」，允许省略人工说明。具名部门只匹配已确定且可披露的归属。资格或授权取决于该部门而无法核实时，返回获准披露的缺项，零业务写入。后续有据补录或更正推进新修订，旧来源保留原答案。[部门取值顺序](506-job-information-records.md#m04-br-014)

**提交和历史。** 按期望来源在既有守卫内一次推进所有受影响的根。同一旧来源上的并发写入须重核，过期请求返回冲突。可定位的通知按其在本人任期上的原事项核对。整组已办时定位原两笔，只定位到一项已办时回原笔核对。无稳定编号的通知沿第 5 节按原提交号和已有安排核对。共同办理的两个动作、任职日状态、适用的资源变化、回执与 Outbox 同时提交。任一阶段写入失败时全部业务变化回滚。响应丢失时按原提交号查回，同号同内容返回原来两笔，同号异内容按已有协议拒绝。更正或撤销后重送成功的旧请求仍只查回原终态。[原提交恢复](#hire-recovery)
