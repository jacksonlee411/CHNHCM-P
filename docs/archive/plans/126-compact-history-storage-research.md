## 1 研究结论与目标口径

2026-11-07用户追加决定：不再要求一定达到200MB；本次实施及效果验证收尾后提交，随后另以B&B万科全量组织验证。200MB保留为原研究参考值，不再作为本轮交付阻断条件。原始空间/延迟结果不改写；列表及集中写入性能问题继续由125持有。

用户要求深入研究并尝试将本案例控制在200m左右。本轮已做独占PostgreSQL物理实验：最终候选约191.5 MB（182.6 MiB），不是压缩包大小。它证明此合成案例存在约200 MB的存储表示，尚未证明现行产品可在该布局上满足全部业务、并发和性能要求。实际结果、重建范围与失败候选见[126报告](../../verification/126-storage-feasibility.md)。

2026-11-07用户明确批准“请按该方案执行，验证效果”，S126-02—06进入实施。正式Go存储、迁移与013/120/122合同同步调整；原125容量P1保持，旧持久库和原研究证据保留。191.5 MB仍是研究结果，不能作为新实现的容量结果。

| 项目 | 本文采用的口径 |
| --- | --- |
| 空间单位及参考值 | MB为十进制，同时报告MiB；原200MB仅作研究参考，按用户最新决定不设固定容量门槛 |
| 实测指标 | `pg_database_size`，含该库普通表、TOAST、所有实际索引、系统目录和空页 |
| 内容 | 当前案例的背景规模、附加样本、全部历史表示、实际审计与辅助数据；不删除旧源、不只保留当前头 |
| 运行磁盘 | WAL、其它数据库、镜像、备份和并存对照副本另报；整个PostgreSQL实例磁盘不能承诺为200 MB |
| 数据边界 | 22000个背景对象按原种子映射重建，2127个附加对象及36490条审计从原库读取；不是55 GiB数据库逐行迁移证明 |
| 业务边界 | 191.5MB仅属原研究；当前实施接入Go/API并另测，见[实施报告](../../verification/126-compact-history-implementation.md) |

不得将191.5 MB乘一个通用比例估算任意客户。该种子的50份历史高度重复；约110万来源也不等于约110万次独立真实操作的审计，原背景复制复用了原型证据引用，实际安全事件只有36490条。当摘要、名称、时刻独立变化时，敏感性实验的业务字面值本身已超过221 MB，尚未计数据库页、索引和审计。持续增加的不可丢弃历史也不可能无限保持固定200 MB。

## 2 为什么会出现55 GiB

### 2.1 可核实的直接原因

本轮原库为59,139,962,559字节，约55.08 GiB。部门成员、路径段、路径节点和路径边四张表连同索引约47.91 GiB，占86.98%。该数据源及逐表大小见[原库统计](https://github.com/jacksonlee411/CHNHCM/blob/061d28105966bd10eb1e3b0032cf2976a6448de4/docs/verification/data/126-storage-research/source-storage.json)。

背景每对象由一次创建、19次新增和30次更正形成50来源、当前20成员；历史来源成员合计810行，记录修订仅69行。简单更名也重新保存完整成员集合与路径结构。同一个实例、企业、部门、来源、记录、修订等UUID在行和多列索引中反复出现。

013第2节已选择完整来源清单；120第2.3节要求成功写入封存完整来源时间线的路径证据，第3节进一步把准确引用落实为多张表、宽复合外键及相应唯一索引。必要的“能精确重现旧源”由此被落实成了昂贵的“每源重新展开全部结构”。

### 2.2 设计为何没有及时收敛

| 诱因 | 结果 | 本次纠正 |
| --- | --- | --- |
| 历史可复原与物理全量复制绑定 | 不变成员和共同路径也反复落行 | 逻辑上完整，物理上共享；不可变值只保存一次 |
| 每个局部引用都选择宽行和宽索引防护 | 历史放大后，索引重复同步放大 | 外部身份完整保留，块内使用局部编号；逐项说明保护如何迁移 |
| 当前查询、历史还原、审计查证使用近似同一展开表示 | 为读方便付出每次写入和永久存储成本 | 当前投影、历史块、审计证据按用途编码，但共享原始值 |
| 先完成完整性、再到R6才看规定规模 | 小样本正确性检查不能暴露约千万行的物理成本 | 存储预算、单次增量和规定规模实验前置 |
| 未设整库空间预算 | 单项设计都能说明理由，合起来失控 | 把索引、TOAST、审计、维护后的增长一起测量 |

以上是合同、实现和样本能够支持的因果分析，不推测个人动机。此前取消整树版本已经减少一层放大，但[单部门关系简化](../../verification/116-r4-relation-simplification.md)仍保留每部门的完整来源证据。三份对照数据库属于测量流程的额外物理复制，减少副本数能降低峰值，不能解决单库55 GiB的根因。

## 3 推荐技术路线

### 3.1 完整逻辑来源与共享不可变内容

保留稳定对象、记录、修订、来源、提交和事件身份。每个来源仍能独立解析为完整成员集合和当时冻结的路径事实，但以局部编号、不可变块引用和紧凑序列表示，不再为每个版本重复插入一组宽成员/路径行。

首选按对象拥有的强类型布局：来源目录、记录修订字典、成员序列、关系修订、冻结路径片段、提交结果、事件内容。相同值或结构可在同一所有者范围内共享；对象间可以共享不含对象字面值的编码结构。UUID仍以完整16字节保存，块内重复使用小整数引用；不是从种子编号再生成业务身份。

每个来源固定自己的成员根和路径证据根。路径节点必须携带当时使用的确切资料/关系来源；不能在历史读取时访问今天的组织树，也不能用`recorded_at`拼凑不存在的全局历史快照。停用前日期、未来首条、改日和合法回溯更正沿现有Go规则。

不引入通用事件溯源平台、EAV或跨域业务解释器。BU、Department和X03分别拥有强类型编码器、表、权限和事务适配；研究脚本中的通用JSON编码器只服务空间实验。

### 3.2 当前读取复用历史值，不重复保存UUID

当前头维护单独的小投影，引用同一不可变值池，并保存完整日期轴所需定位。当前读不展开全部50或1000份历史。服务端Go选择业务日、判断未来/停用状态、授权并组装路径；不把字节编解码做成第二套业务内核。

对象稳定ID、规范编码保留B-tree查找；所有者范围进入实际键。直接用于列表筛选的字段、日志分页键、Outbox待投递和原提交查回必须逐一列出查询计划，新增索引全部重新计入预算。原型未证明所有这些查询均已支持。

不能为了200 MB把正常列表变成整库历史扫描。若真实API实测表明还需关系式读取投影，应计入它的真实成本后重新判断目标，而不是只报告压缩历史表大小。

### 3.3 提交查回使用短哈希预筛选与完整身份核对

原型保留完整`submission_id`数组，仅给16位哈希标签数组建立原生GIN索引。标签碰撞允许产生候选，随后用完整UUID确认；完整产品还须核对`instance + subject + submission + object type`及当前读权。短哈希既不是身份，也不是权限票据。

最终1000次暖态SQL探针平均16.36个候选、最多31个，均精确命中一项；同标签但不存在的UUID产生13个候选，精确结果为零。该结果只验证本规模查找的可行性，不是HTTP延迟、并发唯一性或对抗输入保证。

提交唯一性仍须在事务中由原完整身份锁与终态查回共同保护。GIN数组不能独立提供现有复合唯一约束，必须在实施前明确新的数据库保护与Go责任，验证相同提交并发、跨主体复用、超时、取消和未知提交结果。哈希位数是存储参数，不修改业务身份；增长后的候选分布和拒绝服务边界另测。

### 3.4 原X03完整过程共享方案（已由128局部替代）

以下是126当时采用并测量的方案，仅保留历史解释；后续不得继续据此要求完整判权存档，当前整改目标见128第2节。

授权输入、策略依据、逐项结果和操作者快照全部保留。把重复的策略依据、目标列和大数组片段保存成不可变内容块，事件封套引用这些块。共享范围必须包含实例及相应证据所有权；内容摘要用于完整性校验和共享查找，不能授权读取。

本案例已有19条`deflate-json-v1`大输入，原压缩载荷约45 MB。直接在外层再压缩几乎无益。本轮验证了：解压长度及原SHA-256一致、保留JSON成员顺序、再次使用同版Go算法能够逐字节生成原压缩载荷。共享其原始内容后，全部审计的物理表及索引约15.76 MB。

正式布局应拥有一种明确的当前证据编码格式，保存完整语义事实及必要原摘要；历史证据迁移必须用全量还原比较证明。实验的旧压缩字节重建仅作为额外保真证据，不建议长期依赖重新执行某版本压缩器才能解释审计，也不允许遇到不支持的编码便丢弃载荷。

### 3.5 有界历史读取和封口

禁止把无限增长的对象历史塞进一个不断重写的大JSON。以最多64个来源且最多256 KiB编码内容作为首轮分块实验参数，二者先到者切块；大路径/审计数组再切片。维护对象内来源目录、准确块号和偏移，读取指定来源不回放全部过去命令，也不读取无关对象。

上述参数是待验证候选，不是已测通过值。当前原型仍按整个对象编码；1000来源样本的Python整史解码约0.9秒，是必须消除的限制。分块引入的目录、边界值重复和索引成本也必须补测，不能沿用191.5 MB作为其完成结果。

正常写入先在Go形成完整候选和冻结证据，再原子提交新内容、来源目录、当前头、事件、审计及终态。尾块物理追加或封口不得改变旧逻辑来源的摘要；封口后的块禁止业务角色修改和删除。任何重排/重压缩都须核对原来源的逻辑内容，不能以“整理空间”为由覆盖历史。

### 3.6 完整性保护的实际变化

现行宽复合外键能让数据库检查成员归属、期间、修订和来源的逐行关系。压入块后，这些细粒度关系不能继续由原外键直接证明；这是真实的权衡。

建议保留数据库对所有者、块目录、当前头、终态边界、事务原子性和封口的约束；Go对块内成员、日期、关系和路径引用执行统一候选校验。保存前检查引用闭包、范围、计数、摘要；封套同时绑定实例、企业、对象、来源、格式版本、字典和内容根，不能只分别哈希两个可以被错配的合法块。读取时拒绝损坏、缺块、错误所有者和不支持的编码。不把摘要相等冒充业务资格相等。

必须先形成逐条保护映射，覆盖013/120现有FK、唯一、期间排斥和封口要求，再决定是否采用。原型的哈希/截断反例不等于这些约束已完整替代。如果不能证明相同业务保护，就不能仅凭空间结果切换。

## 4 实测预算及不成立的捷径

| 候选 | 实测/估算字节 | 判断 |
| --- | ---: | --- |
| 每对象列编码并压缩，使用共享常量 | 246,114,000，仅名义背景载荷 | 未计页、索引和审计已超过目标 |
| 共享历史结构，但独立当前投影、完整UUID GIN | 342,603,455，整库 | 仍超目标 |
| 当前投影共享字典、18位标签GIN | 234,501,823，整库 | 仍超目标 |
| 再共享审计内容并精确保留19条原封装的可还原性 | 203,634,367，整库 | 接近目标 |
| 标签GIN调整为16位，重新核验碰撞 | 191,469,247，整库 | 本案例物理可行性成立，产品验收未运行 |

最后一项中，BU/部门主体表及其索引合计约165.42 MB，审计约15.76 MB，结构/字典约0.86 MB，辅助表及原辅助索引空间预留约0.48 MB，其余为系统目录等。TOAST及其索引计入表体积，不能另将它们排除。

不采用删除历史、仅保留最近版本、将审计搬到库外、只计算压缩包、删除必要查找能力或关闭持久性来达标。本轮PG保持`fsync=on`、`synchronous_commit=on`。也不声称换SQLite或调`VACUUM`就能自动获得此结果：主要收益来自表示方式和重复结构共享。

PostgreSQL的普通行与索引存在页和元组成本；TOAST对可变长度值做压缩或外置，不会自动把跨行重复的完整业务结构变成共享事实。[官方页布局](https://www.postgresql.org/docs/18/storage-page-layout.html)、[官方TOAST说明](https://www.postgresql.org/docs/18/storage-toast.html)解释其物理机制；这些机制不能代替本案例实测。

## 6 验收与失败退出条件

1. **S126-A01 内容**：当前日期与任意确切来源的成员、资料、路径、分类、操作者、事件和提交结果，与独立原事实一致；深度100、扇出2000、1000来源、未来/停用/改日均覆盖。
2. **S126-A02 完整性**：错实例、错对象、错成员、历史改写、缺块、错误摘要、超限数据和未知格式失败关闭；权限不足不泄露隐藏节点或候选数。
3. **S126-A03 事务**：两个原提交并发、关系资格变化、双向维护、锁超时、取消、提交后断连和原身份查回仍正确；不能借缩小数据删除共同守卫。
4. **S126-A04 性能**：现行读300ms、确切源/保存500ms的p95目标及取锁预算保持；所有计时纳入解码、授权、审计和持久化。单SQL微测不替代端到端验收。
5. **S126-A05 空间**：规定案例按完整`pg_database_size`报告；原200MB按用户最新决定仅作参考。逐项列索引及辅助信息，记录首次、混合写入后、正常维护后的大小，禁止把数据移出统计口径；不改写原测量及当时的判定。
6. **S126-A06 代表性**：独立摘要、不同名称/时间和不同操作分布另测；给出每增加一个对象/来源/审计请求的成本，不把高度重复样本推广到客户容量承诺。
7. **S126-A07 收尾**：只回收本任务临时容器、卷及原始导出；原容量profile停机保留，原报告和未跟踪资产保持；收尾事实单列。

若有界块、必要索引或完整保护使整库超过目标，先报告实际成本，再决定业务规模预算或更简洁的布局。不得为保住200这个数字增加通用存储平台，或牺牲历史真实性、写入可靠性和可维护性。

## 7 进度与交接
