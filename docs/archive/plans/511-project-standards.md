## 1 规范应涵盖哪些方面

下表给出修订项目标准时需要回答的问题。每次变更选取受影响的行，规则落到对应的共享合同或对象合同。各主题的现行条款和参考实现见[规范导航](../../governance/README.md)。

| 范围 | 应在合同中说清的决定 | 评审时核对什么 |
| --- | --- | --- |
| 业务规则与术语 | 对象身份、事实归属、角色、办理前置、状态转换、金额或数量口径、更正与撤销。涉及政策时写明适用地区、期间和依据 | 一组正常输入和一个边界或拒绝样本，各自产生什么事实。相同业务名称在接口、页面和报表中含义一致 |
| 数据、日期与历史 | 字段含义、单位、默认来源、生效区间、修订、采用和追溯。区分业务日、记录时刻和读取原件的版本 | 主数据首建、后续更改、同日办理分别取得正确日期。更正后可按准确来源查到当时的值 |
| 权限与隐私 | 操作、对象、字段、用途和数据范围，覆盖搜索、计数、导出、原件及审计 | 受限角色从菜单、直达地址、返回历史和 API 得到一致的获权范围，可见计数随撤权更新 |
| 页面布局与视觉 | 菜单及路由归属、主题、字号间距、顶栏与控制区、正文滚动、列表、详情、表单及字段分组 | 在同一构建的参考页和本页对照。桌面短屏能到达末字段、错误和操作区 |
| 交互与可访问性 | 查询草稿与应用、选择、提交、取消、并发冲突、未明结果、未保存保护、键盘和焦点、返回原位置 | 从正常入口走完一次操作和异常返回，核对事实、输入、当前行和焦点。关键流程按共享合同实测原生缩放 |
| 共用组件与页面组合 | 组件用途、输入输出、状态及键盘行为，主题和布局由谁提供，列表、表单、页签与日期轴如何组合。列出共用实现、实际消费者及对象差异 | 能定位一处实现和一个已接入的参考页面。共享修改同时验证原消费者与本次改动页面的可见行为 |
| 领域、接口与工程实现 | Go 领域判断、跨域公开端口、API 与事件、事务与幂等、数据迁移及生成物，明确源域和消费方责任 | 一个失败、并发或重试样本可验证事实与回执，能从公开合同追到所属域的实现 |
| 验证、容量与运行交付 | 独立验收预期、按影响选层、性能样本与阈值、受测构建、首败和复验，以及升级、验收环境和资源交接 | 评审能说明哪些用例实际通过、未通过或未测，容量数字有样本、负载和适用范围 |
| 文档、来源与变更治理 | 权威位置、适用范围、责任角色、稳定条目标识、文档状态及转换条件、来源资产、归档前的规则提炼 | 能用证据判定文档状态，从现行条款追到原规则和适用范围，从归档原文找到今天应遵循的标准 |

## 3 标准写在哪里，变更由谁决定

1. **入口按任务组织。** 建议首页提供“查现行标准”“查在办及拟议方案”“查验收记录”“查历史”四类入口。规范导航直接链接条款和对象差异。计划清单从登记表筛选 `type=plan`，按执行状态区分待办、在办与已关闭，另列文档采纳状态。已关闭计划可从历史入口检索，物理位置取登记路径和归档字段。报告按关联文档号和受测基线查。导航只维护主题和链接。[005 编号与登记](../../governance/005-branches-and-documents.md) · [014 分类](../../governance/014-document-management.md#2-分类目录与权威归属)
2. **长期决定写回负责的合同。** 业务对象的事实、场景与验收进模块规格。共享页面行为进 012 的共享章节，对象的业务差异进对象页面合同。组件用法补“使用条件、状态、实现、参考页、消费者、验收”对照，样式值由主题和组件实现维护。跨模块技术约束进架构文档，关键取舍进 ADR，文档及交付规则进治理规范。确有缺项且现有合同均无法承接时，由对应维护者按 005 领号、按 014 选择类型和模板，经评审采纳后接入现行导航。计划记录本批范围、顺序与未结项，验证记录保存受测结果。[领域边界](../../architecture/004-repository-layout.md) · [功能规格模板](../../templates/functional-design.md) · [组件与参考页对照样本](../../specs/m03/308-job-foundation-contract.md#m03-page-inheritance)
3. **把条款写到能判定。** 一条约定写清触发条件、适用对象、必须／应／可的行为及可观察结果。需要追踪的业务规则、场景、验收条件沿用模块内的 BR、SCN、AC 标识和显式锚点。共享体验条款沿用已有语义锚点。对象合同只补具体业务差异、原因及验收样本。[014 标识与引用](../../governance/014-document-management.md#42-稳定规则场景和验收-id) · [页面差异模板](../../templates/dated-object-admission.md#page-inheritance)
4. **按影响处理冲突与例外。** 作者先核对两条约定的适用对象、采纳范围和明确替代关系。单对象差异由对象维护者说明业务理由、影响、验收依据，临时偏离另记截止或复查条件。改变共同行为时由共享合同维护者与受影响的消费方审阅同一份修订，同批更新条款、引用及预期。局部替代要指出旧条款剩余的适用范围，整体替代才登记 `superseded_by`。仍有分歧的部分在计划中列明裁定角色和处理节点，已采纳合同继续作为判断依据。[014 新建及修订](../../governance/014-document-management.md#81-新建及修订)

## 5 文档归档前的规则和标准提炼

**每份拟归档文档必须先提炼其中的规则和标准，包括有关文档状态判定和转换的条款。** 原文维护者逐条梳理，承接规范的维护者核对内容与范围。仍有效的条款全部有了已采纳的长期维护位置，原结论与证据也能查回，方可登记归档。适用对象按 014 确定，包括执行已完成或取消的临时计划，以及已替代、废止或取消的文档。[014 归档流程](../../governance/014-document-management.md#82-归档)

### 5.1 每份文档的提炼与判定

1. **从原文提炼条款。** 检查正文、表格、示例和验收条件中的业务规则、页面布局、交互、组件用法、技术约束和评审标准。每项在归档交接说明中列出原文位置或稳定 ID、当时的采纳依据、适用对象与触发条件、应遵循的做法或可核验结果。一次性实施步骤、当批实测和未结事项分别指向原证据或接续任务。通读后确无长期规则的，记录“无可提炼条款”、核对范围和理由。
2. **逐条确定当前效力。** 已有现行条款完整覆盖的，直接链接具体条款。仍有效但缺少承接的，由对应维护者补入长期业务、功能、技术或治理规范，在交接说明中关联目标条款及其审阅采纳依据。部分适用的写明保留范围和差异。已替代或废止的给出替代位置或废止依据。已否决的提议保留原结论，仍待决定的提议交给接续任务。还有条款的效力待定、有效内容只在旧文中或承接规范尚待采纳时，整份文档暂缓归档，写明负责角色和复查条件。
3. **提炼文档状态的判定规则。** 凡原文涉及文档状态的判定或转换，必须写清适用文档、状态含义、转换前后的状态、触发条件、判定角色及所需证据，逐项对照 014。例如，评审要求修改时由在审退回草稿，是 014 持有的通用规则。511 初稿退回草稿是一次具体判定，可查当次评审。文档采纳看 `status` 和审阅结论，计划完成看 `execution_status` 和关闭原因，实际验收看关联报告的逐项结果，物理归档看 `archive`。交接说明引用相应基线的登记与证据。新发现且需要全仓适用的状态规则，由仓库维护者修订 014 并完成审阅。[014 生命周期](../../governance/014-document-management.md#6-生命周期与完成口径) · [511 初稿评审](../../verification/511-project-standards-review.md)
