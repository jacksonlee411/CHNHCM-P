## 1 用户目标

### 1.1 目标与可观察结果

在 M02 内，让 BU、部门共用一套按日维护实现，通过两个真实对象验证页面、时间线、可靠提交和接入标准，再评估跨域推广。共用交互或标准时间线规则修复后，两个对象直接使用该修复，并分别提供实际回归结果。

组织管理员从“设置 → 组织配置 → 业务单元”或“设置 → 组织配置 → 部门”直接进入列表；查询者使用各自获权列表、详情与历史。部门菜单按119功能合同在R5接通，不增加中转工作台。两个对象均通过对象定义和强类型适配器接入列表、详情、表单、生效记录、固定启停维护及结果恢复；对象独有字段、关系、授权及引用约束由对象显式实现。

按日维护继续使用过去、当天和未来业务日期、独立记录修订及确切来源。BU 与部门采纳同一标准生命周期规则集；对象专属约束在最终候选上追加核验。页面只消费 Go 返回的能力、位置范围和影响，保存时由 Go 重新核验当前权限、来源与引用。

### 3.3 分表下的提交与恢复

下列合同已由120冻结，R2在BU接入时验证，R4/R5以部门和跨对象反例复验：

1. 提交归属必须包含实例、主体、对象类型和submissionId；对象类型可由受控端口及对象专属浏览器存储命名空间明确。命名空间按对象类型隔离，同一字符串编号跨类型不能互相读取或封闭；120规定BU原锁编码保持，部门加固定类型参数。
2. 原请求、原内容重试及无正文resolve对同一逻辑身份使用同一事务锁。对象适配器确定自己的结果表；无终态的resolve只向该对象结果表写not_applied，不探遍结果表猜归属，不新增共享结果或封闭登记表。若同编号跨类型采用独立命名空间，其独立性及互不查回必须有测试。
3. 内容摘要绑定实际端口/对象、目标、预期来源、声明字段及全部输入。提炼不得改写已有BU摘要、终态或确切来源；原BU端口与原引用已有明确归属时由BU适配器解释，不依赖重算当前事实补造原结果。
4. 浏览器只保存查回所需的最小非敏感引用；对象归属可以来自明确存储命名空间，不保存名称、日期、关系正文或凭据。保留当前已有BU待确认引用的可查回性，不能通过清空本地引用完成提炼。120已明确同类型未明确认阻塞本类型新写、另一类型独立；类型/主体/会话代次隔离迟到响应。
5. accepted/rejected/no_change/not_applied只能在外层提交确认后交付；pending和通信未明保持待确认。业务savepoint撤销、未知COMMIT、取消、清理及迟到响应继续采用013现行语义。仅写权撤销不阻断获权终态读取；对象/历史或字段读权变化继续安全裁剪。

事务锁可使用现有PostgreSQL事务级advisory机制及受控行锁，无需为锁新建共享业务表。具体锁键和取得顺序必须统一实现，并用真实多连接验证；锁机制本身不替代业务不变量。技术依据：[PostgreSQL 18 显式锁与advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS)，2026-11-04核对。

### 3.4 部门关系与共同守卫

部门—BU关系纳入第二个真实对象的验证：必填单值、多对一、按日变更，编码企业内唯一且换BU保持；部门启用及关系发挥效力的完整期间BU须启用，停用旧资料不永久阻断。行政父子同BU、单父无环，当前和确切旧源路径分别解释，依据117/118。不得仅凭下拉框结果通过，也不得预设BU停用后自动停用部门。

有效父边只覆盖启用期间，停用修订保留准确历史引用。当前停用资料的路径按停用日前一日的最新事实读取，显式来源按当次封存证据读取。部门BU范围授权取执行日当前资料；首条尚未生效时取当前来源固定首条BU，停用时保留BU。所选记录及确切来源不改变授权范围，未来转入、首条归属纠错、启停及停用记录删除/改日分别按118/120检查最终候选。

对象应用服务在事务内取得关系事实和必要版本，纯Go内核构造完整最终候选，再校验对象专属关系和全部受影响期间；现有单条自动辅助/预览使用相同候选及关系规则，保存重新取得当前守卫。部门写入与会改变相关资格的BU停用、改日、更正、删除及固定两条操作都必须接入共同守卫，覆盖新增关系的空集合竞争，不能只锁已经存在的引用行。
